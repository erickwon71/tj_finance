## 결론 — 원인은 "컬럼 오선택"이 아니라 `_split_label_amounts()`의 주석번호 가드 오탐

기존 triage(§1-2)의 "4열 비교표에서 전기 3개월 열이 선택됐다"는 서술은 **증상 관찰은
맞았지만 메커니즘 서술이 틀렸다** — cum_map(누적컬럼 판정)은 정상적으로 계산됐다. 진짜
원인은 `parser/xml/table_extractor.py::_split_label_amounts()`의 "6-column 금융업 IS 주석번호
스킵" 가드가, **당기(첫) 컬럼 값이 콤마 없는 1~3자리 숫자일 때 그 값 자체를 "주석번호"로
오인해 통째로 드롭**하는 것이다.

## 1. 재현 — 대상: 00163673 한진중공업홀딩스 별도 IS, `20250814001174.xml`(2025 반기)

원문 XML(`raw_report/KOSPI/00163673_한진중공업홀딩스/half/2025/20250814001174.xml:15016~15037`)의
"Ⅰ.영업수익" 행 물리적 셀 5개:

```
['Ⅰ.영업수익', '654', '9,097', '629', '9,069']
  (라벨)        당기3개월  당기누적   전기3개월  전기누적
```

`_split_label_amounts(cells)` 직접 호출 결과:
```
label = 'Ⅰ.영업수익'
amount_cells = ['9,097', '629', '9,069']   ← '654'가 사라짐(라벨에도 안 붙음, 그냥 소실)
```

이후 `extract_rows()`가 만드는 `amounts`(4칸, cum_map={1:0, 3:1} 적용 전 원시 배열):
```
[9097000000, 629000000, 9069000000, None]   ← 정답 [654M, 9097M, 629M, 9069M] 대비 왼쪽으로 1칸씩 밀림
```

`cum_map`(헤더 "3개월"/"누적" 토큰 위치로 정상 계산됨, `{1: 0, 3: 1}`)을 이 밀린 배열에
적용하면 `amounts[1]=629000000`이 "당기 누적(col_index=0)"으로 채택된다 — 이게 DB에 실제로
적재된 값(629,000,000원)과 정확히 일치. **cum_map 로직 자체는 무죄** — 입력(`row.amounts`)이
이미 밀려 있었다.

## 2. 근본원인 코드 — `parser/xml/table_extractor.py:490-497`

```python
if (not amount_cells
        and _NOTE_REF_PATTERN.match(cell_nospace)
        and not _AMOUNT_GROUPED_PATTERN.match(cell_nospace)):
    continue
```

- `_NOTE_REF_PATTERN = r'^[1-9]\d{0,2}(,[1-9]\d{0,2})*$'` — 1~3자리 숫자(그룹 반복 가능,
  "34", "4,28", "2,4,32,34,35,36" 같은 **주석 다중참조 표기**를 잡기 위한 패턴)와
  `"654"`가 **완전히 같은 모양**이라 매치된다.
- `_AMOUNT_GROUPED_PATTERN = r'^\(?\d{1,3}(,\d{3})+\)?$'` — 3자리 콤마구분 금액(예:
  "1,521")만 "진짜 금액"으로 인정해 위 스킵에서 **보호**한다. 그런데 `"654"`는 1,000
  미만이라 **콤마 자체가 없다**(DART 관행상 1,000 미만 금액은 콤마를 안 찍는다) → 이
  보호막을 통과하지 못한다.
- `not amount_cells` 조건 — **이 행에서 아직 금액 셀을 하나도 못 찾았을 때만** 발동한다.
  즉 **당기(첫) 컬럼 값**이 콤마 없는 1~3자리 숫자인 행만 걸린다. "Ⅱ.영업비용" 행처럼
  당기 값이 "1,521"(콤마 있음)이면 `_AMOUNT_GROUPED_PATTERN`이 보호해 정상 처리된다
  (직접 확인: `amounts=[1521000000, 2630000000, 1521000000, 2673000000]` — 밀림 없음).

이 가드의 원래 설계 의도(함수 docstring)는 **보험/증권 6-column IS 구조**
(`[계정과목명, 주석번호, 당기명세, 당기합계, 전기명세, 전기합계]`)에서 두 번째 셀에 오는
진짜 "주석번호"(34, 4,28 등)를 걸러내기 위함이었다. 그런데 실제 구현은 **셀 개수(6인지
아닌지)를 전혀 확인하지 않고**, 임의의 표 구조에서도 "첫 금액후보 셀이 1~3자리 콤마없는
숫자"이기만 하면 무조건 스킵한다 — 이번 사례(4열 반기 비교표, 라벨+금액 5셀)처럼 6-column
구조가 아닌 표에도 오적용된다.

## 3. 파급 범위 — 확정된 것과 미확정인 것

- **확정**: Gate B fail_a 잔여 revenue 미매치 22건 중 한진중공업홀딩스 2건(H1·Q3 각 1건,
  [`gate_b_faila_residual_triage_2026-08-14.md`](gate_b_faila_residual_triage_2026-08-14.md)
  §4)이 이 메커니즘. H1(`20250814001174`)은 이번에 직접 원문·코드 추적으로 검증 완료. Q3는
  같은 회사·같은 계정이라 **같은 원인으로 추정**하나 원문 재확인은 아직 안 함.
- **구조적으로 넓을 수 있는 이유**: 이 가드는 표 종류(BS/IS/CF)나 반기/분기 여부와 무관하게
  `_split_label_amounts()`를 거치는 **모든 본문·주석 행**에 적용된다 — "당기(첫) 컬럼 값이
  100~999원(단위 적용 전 표시값 기준, 즉 억/백만원 단위 표에서 100~999) 사이이고 콤마가
  없는" 조합이면 어디서든 재현 가능한 일반 결함이다.
- **왜 Gate B에서 지금까지 2건만 잡혔나(미확정 이유)**: Gate B fail_a는 XBRL 크로스체크
  근거가 있는 2024+ Track A 필링에만 걸린다. 이 조건(당기 첫 컬럼 값이 100~999원대) 자체가
  드물어(대부분 계정은 첫 컬럼이 1,000 이상) 실제 발생 빈도가 낮았을 가능성이 높지만,
  **전수 스캔은 하지 않았다** — DB 전체에서 이 시그니처(같은 rcept·행이 인접 행 대비
  1칸씩 밀린 패턴)를 찾는 별도 쿼리가 필요하다(미착수, 짐작 금지 원칙상 다음 단계로
  남겨둠).

## 4. 수정 방향(제안, 미구현 — 승인 필요)

가장 좁고 안전한 수정은 **함수 docstring이 이미 명시한 전제(6-column 구조)를 코드에도
그대로 강제**하는 것 — 가드 조건에 `len(cells) >= 6`(또는 이에 준하는, 실제 6-column 표만
겨냥하는 조건)을 추가해, 이번 사례처럼 5셀(라벨+4금액) 구조에는 애초에 이 가드가 발동하지
않게 한다. 이러면:
- 보험/증권 6-column 표의 원래 의도된 동작(주석번호 스킵)은 그대로 유지.
- 4/5셀 표(대다수 일반 기업의 BS/IS/CF)에서는 이 가드가 아예 안 걸려, 콤마 없는
  100~999원대 당기 값이 더 이상 소실되지 않음.

**미검증 리스크**: 이 조건 변경이 실제 6-column 표(보험/증권)의 셀 개수와 항상 일치하는지
직접 표본 확인이 안 됐다(추정만 함) — 구현 전 보험/증권 6-column 표 1~2건 원문 재확인
권장(R16 설계 문서의 검증 기준과 동일 원칙).

(`scratchpad/note_ref_scan_sample_shard{0..4}.csv`, 샤드당 최대 1,000행) 원문 대조로
추가 확인이 필요하며 아직 하지 않았다.
