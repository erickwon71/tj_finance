### ★ 근본원인 규명 (원문 직접 대조)

34건 전부 공통 패턴: **"부채와자본총계"(결합 총계 행)는 항상 자산총계와 정확히 일치**하는데,
**분리된 "부채총계"/"자본총계" 개별 행만** 이상한 값을 보임. 예 `20030814000816`(KG케미칼
2003 반기 연결):

```
자산총계        118,690,610,298
부채총계       (125,630,854,796)   ← 괄호가 있는데도 DB엔 음수 아닌 절대값 계열로 안 들어감
자본총계       (-)6,940,244,498    ← "(-)" 접두라는 비표준 표기 — 정규식이 못 읽음
부채와자본총계  118,690,610,298    ← 이건 정확
```

`_AMOUNT_CELL_RE`(`parser/xml/section_detector.py`)는 `(N)`(괄호=음수) 표기만 인식하고
`(-)N`(괄호+명시적 마이너스 접두, 이 filer 특유의 이중 표기) 은 매치하지 못해 그 셀이
**파싱 실패(None) 처리**된다. `_emit_section_lines`(`fin2/extract/report_lines.py`)의
컬럼 압축 로직(`lead = 0; while amts[lead] is None: lead += 1`)이 "앞쪽 None = 과거 미보고
기간"이라는 가정으로 **왼쪽으로 당겨 채우는데**, 이 경우는 미보고가 아니라 **파싱 실패**라
전기(col1) 값이 당기(col0) 자리로 밀려 들어간다 — 그 결과 "부채총계"/"자본총계" 값이
엉뚱한 기간 열에 붙는다.

**★ 이건 Phase 3(pre-2015 신규 모듈)의 결함이 아니다.** `_emit_section_lines`/
`_AMOUNT_CELL_RE`는 2015+ 도 포함해 **연도 무관 공용 코드**이고, 이번 트랙에서 한 줄도
안 건드렸다 — pre-2015 K-GAAP 서식에 `(-)N` 같은 비표준 셀 표기가 상대적으로 더 자주 나와
드러난 **기존(연도무관) 컬럼압축 로직의 사각지대**다. 기존 이상치 탐지(`detect_anomalies`)
도 이 34건을 하나도 잡지 못했다(SIGN/OTHER 68건과 겹치지 않음) — 항등식 기반 체크가 없기
때문.

**영향 범위**: 34/2,032 filing(1.7%) · **4개 corp에 집중**(KG케미칼 31건·PKC/에스엠/
동신건설 각 1건, 26개 corp 중 4개=15.4%). KG케미칼이 압도적 — 이 filer(또는 그 시기 담당
제출대행사)가 `(-)N` 표기를 반복 사용한 것으로 추정.

## 3. `(-)N` 버그 수정 + 재검증 (2026-08-10, 사용자 승인 후)

**수정 2곳**(둘 다 필요 — 하나만 고치면 값이 안 바뀜, 직접 확인함):
1. `parser/common/amount_normalizer.py::parse_amount` — `(-)N` 표기를 음수로 인식하도록
   분기 추가.
2. `parser/xml/table_extractor.py::_NUMBER_PATTERN` — **`parse_amount`보다 먼저 도는 게이트**
   (표의 각 셀이 "금액 후보"인지부터 판정). 이걸 안 넓히면 `(-)N` 셀이 여기서 이미 "숫자
   아님"으로 버려져 `parse_amount`까지 가지도 못한다 — 1차 수정(parse_amount만) 후 재적재
   했을 때 DB 값이 그대로였던 것으로 직접 확인.

회귀 테스트 9건 신설(`fin2/tests/test_amount_normalizer_parse.py`) + `pytest tests/
fin2/tests/` 전체 통과(464 passed, 무관 기존 실패 1건 제외). 26개사 파일럿 재적재
(`--recheck`, 오류0) 후 재검증:

- **자본총계 셀 자체는 정확히 고쳐짐** — 예 KG케미칼 `20030814000816`: 수정 전 자본총계
  col0=1,718,661,826(전기값이 밀려들어온 오염값) → 수정 후 -6,940,244,498(원문 `(-)6,940,244,498`
  그대로, 정확).
- **항등식 위반 총건수 45→40건으로 감소**(5건 해소).
- **그러나 큰 위반(자산 대비 0.1%+) 34건은 그대로 남음** — 원인이 하나가 아니었다. KG케미칼
  전 filing(2003~2008)에서 **"부채총계" col0(당기) 만 항상 괄호로 감싸여 있고 전기·전전기는
  안 감싸임**(`(125,630,854,796)` vs `121,796,449,099`/`116,474,382,200`) — 표준 괄호=음수
  관례로 읽으면 매번 부채가 음수가 되는데, 부채와자본총계(결합행)는 매번 정확히 자산과
  일치하므로 **진짜 값은 양수**다. 31개 filing 전부 같은 모양이라 무작위 오타가 아니라
  **이 filer(또는 그 시기 제출대행사)의 반복된 서식 습관**으로 보이지만, 정확한 원인(수식
  셀 스타일링 등)은 원문만으로 확정할 수 없다.

**★이 잔여 패턴은 고치지 않기로 판단**(R0 원칙): "결합행과 안 맞으면 부호를 뒤집는다"는
규칙은 원문에 없는 걸 추론하는 것이라 계층2("판단 없이 전사")의 R0 원칙에 어긋난다 — 이건
계층3 항등식 보정 영역이거나, 최소한 이상치 탐지(`detect_anomalies`)에 "BS 항등식 위반"
종류를 추가하는 **별도 스코프**로 다뤄야 한다(이번 파일럿에서 그런 검사가 아예 없다는 것도
확인됨 — SIGN/OTHER 68건과 전혀 안 겹침). 영향은 4개사(26개 중, KG케미칼이 31/34건)로 좁다.

## 4. 이상치 탐지 보강 (2026-08-10, 사용자 요청 — Phase5 착수 전제조건)

§3 잔여 패턴을 "값은 안 고치되 표시는 한다"는 기존 SCE↔BS 교차대조와 같은 원칙으로
`fin2/audit/line_anomaly.py::detect_bs_identity_anomalies` 신설(회귀 테스트 7건,
`fin2/tests/test_bs_identity_anomaly.py`). 자산≠부채+자본인 (basis, col_index) 를 표시하되,
**"부채와자본총계"(결합행)가 따로 있고 그게 자산과 일치할 때만** 항등식이 함의하는 값을
`suggested_value` 로 제안하고 `confidence="high"` — 결합행이 없거나 그것도 안 맞으면 "뭔가
안 맞는다"만 `confidence="low"` 로 표시하고 어느 쪽이 틀렸는지는 추측하지 않는다.

파일럿 재적재(`--recheck`)로 검증: **KG케미칼 `20030814000816` 부채총계 행이 정확히
`bs_identity_confirmed`/`SIGN`/`high`/제안값 125,630,854,796(항등식대로 정확)** 로 잡힘.
파일럿 전체 신규 이상치 134건(bs_identity_confirmed 107건[SIGN 76·OTHER 31] + bs_identity
27건, 기존 bs_crosscheck 68건과 안 겹침) — pytest 전체 통과(471 passed, 무관 기존 실패
1건 제외).

## 5. 최종 결론

- **Phase3(파서 신규 모듈) 자체는 건전** — 잔여 미탐지(§1)는 전부 설계 단계부터 예정된
  범위이거나 원문 자체 문제(손상·절단·요약전용)이지, 신규 모듈의 새 결함이 아님.
- **`(-)N` 컬럼압축 버그는 수정+검증 완료**(연도무관 공용코드, 2015+ 에도 이론상 이득).
- **잔여 34건(부채총계 부호 관례 추정)은 값 수정 없이 이상치 탐지로 안전망 확보**(§4) —
  R0 원칙 유지(계층2 는 판단 없이 전사), 계층3/사용자가 `confidence`·`suggested_value`
  보고 보정 여부 판단.
- **Phase5(전량 백필 79,283건) 착수 전제조건 충족** — 실행 여부·방식은 규모(파일럿의 약
  39배, 추정 5시간대) 감안해 별도 확인.
