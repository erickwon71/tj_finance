# DART 웹뷰어 HTML 추출기 설계 (Track C PDF-only 잔여 93건 대상)

**상태**: 설계만, 구현 미착수(계획 후 대기 원칙).
**전제 문서**: `docs/plans/pdf_track_c_parser_robustness_2026-09-06.md`
§"검토 후보"+§"검토 후보 §1~3 실측 확인" — 이 설계가 근거로 삼는 실측 증거
(KD·동성제약 2건 교차검증, offset/eleId 등 실제 요청 파라미터)는 전부 그
문서에 있다. 여기서는 반복하지 않고 설계만 다룬다.

## 1. 왜 필요한가 (한 줄 요약)

PDF는 좌표 기반 텍스트라 "표" 개념이 없어 R76/§4(KD류 라벨-숫자 밀림)/R78(라벨
줄바꿈) 세 계열 버그가 반복 발생했다. 같은 필링을 DART 웹뷰어 내부 API
(`report/viewer.do`)로 받으면 원본 SGML/XML이 실제로 갖고 있던 `<TABLE><TR>
<TD>` 구조가 그대로 나와, 이 버그 계열이 원천적으로 발생하지 않음을 2개사
교차검증으로 확인했다.

## 2. 스코프 (중요 — 전면 교체 아님)

- **1차 대상**: `docs/plans/pdf_track_c_parser_robustness_2026-09-06.md`가
  추적 중인 **잔여 93건(41개사)**만. 이미 `ok`로 확정된 필링은 손대지 않는다.
- **PDF 경로는 유지**: R78 설계 원칙과 동일 — "정상 동작하는 경로를 검증
  없이 전면 교체하지 않는다." HTML 추출기는 PDF 추출기와 **나란히** 두고,
  PDF가 이미 성공한 필링에는 적용하지 않는다(적용 대상은 census가 `fail`/
  `missing`으로 표시한 필링뿐).
- **적용 범위 확대(1999~2003년대 전체)는 이번 설계 밖** — 93건에서 먼저
  검증한 뒤 사용자가 별도로 결정.

## 3. 아키텍처 개요

```
dsaf001/main.do (TOC 트리, 세션쿠키)
        │  ① _parse_toc_tree()  — 신설
        ▼
   TocNode 리스트 (text/eleId/offset/length/dtd/dcmNo)
        │  ② _find_statement_section() — 신설(재무제표/연결재무제표 매칭)
        ▼
report/viewer.do?eleId=...&offset=...&length=...  (섹션 HTML)
        │  ③ extract_html_facts() — 신설, fin2/extract/html_viewer.py
        │     ├─ 표 탐색: <P class='table-group'> 직후 <TABLE border='1'>
        │     ├─ 레이아웃 감지: 거대-셀형(KD류) vs 행별-TR형(동성제약류)
        │     ├─ 라벨/값 페어링 → (label, [amounts]) 스트림
        │     ├─ normalize_account_name() 재사용(라벨 정규화, pdf.py와 동일)
        │     └─ 기간 헤더(<TH>) 파싱 → basis/period_kind/col_index
        ▼
   list[ExtractedFact]  (fin2.extract.xbrl.ExtractedFact, source_format='html')
        │  ④ facts_to_report_lines() 재사용(pdf_lines_sync.py, 무변경)
        ▼
   ReportLineRow → store_report_lines() → build_corp()  (기존 v3 파이프라인)
```

기존 `collector/legacy_downloader.py::LegacyDartScraper`의 `_get_view_params()`
/`_fetch_html()`은 그대로 재사용하되, `_get_view_params()`는 "표지만 반환"하는
지금 동작을 안 건드리고 **새 메서드**(`get_toc_tree()` 등)를 추가하는 방식을
제안한다 — 기존 PDF 폴백 흐름(`fetch()`)이 `_get_view_params()`에 의존하므로
그 동작을 바꾸면 회귀 위험이 있다.

## 4. 상세 설계

### 4-1. TOC 트리 파서 (`collector/legacy_downloader.py` 확장 제안)

`dsaf001/main.do` 응답 텍스트에서 `node1`/`node2` 블록을 정규식으로 파싱해
`(text, eleId, offset, length, dtd, dcmNo)` 튜플 리스트로 만든다. 실측 확인된
필드 리터럴 패턴(`node2['text'] = "..."`, `node2['offset'] = "..."` 등)을
그대로 파싱 대상으로 삼는다 — TOC는 트리(`children.push`)지만, 우리가 필요한
건 평면 리스트뿐이라 계층 구조는 버려도 된다.

**미해결 질문(구현 시 확인 필요)**:
- `node2['text']`에 특수문자(따옴표 등)가 이스케이프된 사례가 있는지 —
  KD·동성제약 표본에서는 없었으나 전수는 아님.
- `dart3.xsd`(신형) 문서도 같은 트리 포맷인지(신형은 XBRL이 있어 우선순위
  낮음 — 확인만 하고 급하지 않으면 스킵 가능).

### 4-2. 재무제표 섹션 매칭 (`_find_statement_section()`)

TOC 노드 `text` 중 다음을 **포함**하되 제외 패턴에 걸리지 않는 것을 찾는다:

- 포함: `"재무제표"`
- 제외: `"이용상의 유의점"`(동성제약 예시의 "2. 재무제표 이용상의 유의점"),
  `"합병전"`(6번 항목류)
- `"연결재무제표"`는 별도 노드로 존재(동성제약 예시의 "4. 연결재무제표") —
  별도(`separate`)/연결(`consolidated`) 각각 다른 노드를 따로 찾아 각각
  fetch. **연결 노드가 없으면** 원문에 "해당사항 없음"이 명시된 경우이므로
  (§4-보강에서 이미 확인된 정책) `basis_fallback` 처리는 하위 파이프라인
  (build_corp)에 이미 있는 정책을 그대로 따르고, 이 추출기가 직접 만들지
  않는다.

이 매칭 자체가 PDF의 `_TITLE_RE`/`_PERIOD_MARK_RE`류와 성격이 같은 "정규식
유지보수 부채"라는 점을 인지 — 목차명이 보고서 유형(사업/반기/분기)·시대별로
달라질 수 있어 93건 롤아웃 중 새 변형이 나올 가능성을 열어둔다(발견 시 이
문서에 사례 추가하는 방식으로 진행 — 프로젝트의 기존 관례와 동일).

### 4-3. 표 리더 — 두 레이아웃 대응

섹션 HTML 안에서 `<P class='table-group'>{제목}</P>` 직후 `<TABLE border='1'>`
을 찾아 `{제목}`으로 statement(BS/IS/CF/SCE) 판별(`_TITLE_NAMES`와 동일 어휘
재사용 가능 — "대차대조표"/"손익계산서"/"재무상태표"/"현금흐름표"/
"자본변동표"). 표 안에서 두 레이아웃을 모두 처리:

**레이아웃 A(KD류, 거대-셀형)**: `<TBODY><TR>` 하나에 `<TD>`가 `[라벨,
값1, 값2, …]` 개수만큼만 있고, 각 셀 내부가 `<BR/>`로 조인된 다항목. 파싱:
`td.contents`를 순회하며 `<br>` 노드를 구분자로 텍스트 세그먼트 리스트로
쪼갠 뒤(이번 조사의 `verify_alignment2.py` 프로브와 동일 방식), 라벨
세그먼트 리스트와 각 값 세그먼트 리스트를 **인덱스로 zip**한다. 세그먼트
수가 라벨과 값 사이에 다르면(이론상 가능 — 아직 실측 안 됨) 그 표는
스킵하고 로그만 남긴다(자신 없는 표는 억지로 파싱하지 않음 — 이 프로젝트의
"짐작 금지" 원칙).

**레이아웃 B(동성제약류, 행별-TR형)**: `<TBODY>`의 각 `<TR>`이 한 항목.
첫 `<TD>`가 라벨, 나머지가 값 컬럼들이나 실측에서 보였듯 **플레이스홀더로
빈 `<TD><BR/><BR/></TD>`가 실제 값 컬럼 사이사이에 끼어 있다**(헤더의
`colspan='2'` 쌍과 대응 — 폭 조정용으로 추정). 빈 TD는 버리고 남은 값만
순서대로 취해, `<THEAD>`에서 뽑은 기간 라벨(순서 보존) 수와 맞춰 zip한다.

**레이아웃 감지 순서**: 표 하나를 볼 때 먼저 B(행별) 시도 — `<TBODY>`
`<TR>` 개수가 라벨 항목 수와 비슷하면(예: 40개 안팎) B, `<TR>`이 1~2개뿐이면
A로 판정. 정확한 임계치는 93건 표본으로 조정 필요(설계 단계에서 확정 안 함).

### 4-4. 기간/컬럼 헤더 파싱

`<THEAD>`의 `<TH>` 텍스트(`"제 45 반기"`, `"금액"` 등)에서 기수·기간종류를
뽑는다. PDF의 `_PERIOD_MARK_RE`(`제\s*\d+(?:-\d+)?\s*(?:\([^)]{1,4}\)\s*)?
(?:기|분기)`)가 이 텍스트에도 그대로 맞는지 확인됨(예시 텍스트 "제 45 반기"는
정규식 상 "제 N 기" 패턴과 "분기"만 다르지만, 정규식이 이미 `기|분기` 둘 다
허용). R77이 고친 하이픈·괄호 변형도 이 헤더 텍스트에 나타날 수 있어 같은
정규식을 그대로 재사용할 수 있을 것으로 보임(검증 필요 — 아직 헤더 쪽에서
그 변형이 실제로 나온 표본은 못 봤음).

`<TABLE class='nb'>`(표 제목 위, 클래스로 구분되는 무테두리 표)에 있는
"(단위 :천원)" 같은 단위 선언도 `_UNIT_RE`/`_UNIT_FACTOR` 그대로 재사용
가능해 보임(같은 어휘).

### 4-5. 라벨→계정 매핑, 값 파싱

- 라벨 정규화: `parser.common.amount_normalizer.normalize_account_name()`
  그대로 재사용(라벨 텍스트 관행이 PDF와 동일한 한글 인쇄 관례 — 다만
  `&nbsp;`를 공백으로 치환하는 전처리가 먼저 필요, `_SUBTOTAL_HEADER_RE`류
  로마숫자/괄호번호 접두 처리도 그대로 재사용 가능해 보임).
- 값 파싱: `parse_number()`(pdf.py) 그대로 재사용 가능 — 괄호/△/콤마 관행
  동일.
- `ExtractedFact.source_format`은 `'html'`로 신설(기존 `'pdf'`/`'xbrl'`과
  구분 — 하류에서 `unit_source` 등에 이미 `'pdf'` 문자열을 쓰는 관례가 있어
  이것도 `'html'`로 맞춰야 함, `collector/pdf_lines_sync.py:63` 참고).

## 5. 파이프라인 편입 지점

★2026-09-07 후속(§8-8) — 사용자 지시로 **HTML을 PDF보다 먼저 시도**하는
순서로 확정됐다. "언제 다음 방법(PDF)으로 넘어가는가"의 구체적 조건은
§8-8에 실측 근거와 함께 정리돼 있다 — 여기 아래 항목들은 그 순서가
확정되기 전에 쓴 큰 틀(런북 체크리스트 항목)이라 그대로 유효하다.

프로젝트 규칙(`docs/runbook_new_parser_pipeline_integration.md`)에 따라
구현 단계에서 **반드시**:

1. `collector/pdf_lines_sync.py::recover_one()` — 지금 `fmt != "pdf"`면
   그냥 raw_bytes만 보존하고 리턴하는 분기를, `fmt == "html"`이면
   `extract_html_facts()`를 호출하도록 확장. 이 함수를 부르는 **두 call
   site**(메인 + `--standardize-only` 재개, `scripts/collect_new.py`)는
   기존 인터페이스(`recover_one()` 반환 타입)를 그대로 쓰므로 이 지점만
   고치면 배선은 자동으로 따라온다 — 다만 실제 배선 여부는 구현 단계에서
   런북 체크리스트로 재확인.
2. 과거 93건 소급 백필은 자동이 아니다 — `scripts/backfill_pdf_multiline_195_
   2026-09-06.py`류의 전용 스크립트를 새로 만들어 수동 실행.
3. 검증: 회귀 테스트(`pytest fin2/tests/ tests/`) + 원문대조(이 프로젝트
   관례상 최소 KD·동성제약 포함 표본 재검증) + Gate B 영향 확인.

## 7. 리스크 · 미해결 질문 (구현 전 남겨둠)

- 레이아웃이 A/B 둘 뿐인지, 93건 안에 제3의 레이아웃이 있을지 — 표본 2건
  뿐이라 모름. **구현 1단계는 반드시 93건 표본 우선 스캔(파싱 시도만, DB
  적재 전)으로 레이아웃 분포부터 확인**하는 걸 제안(짐작으로 A/B 두 갈래만
  만들고 나머지를 실패 처리하면 됨 — R78 폴백 원칙과 동일하게 "모르면 스킵").
- 목차명 매칭 정규식의 유지보수 부채(§4-2) — PDF 쪽 R77류 갭이 여기서도
  재현될 가능성.
- 서버 부하: `WEB_INTERVAL=2.0초` 기준 필링당 요청 2회(main.do+viewer.do) ×
  basis 2개(별도/연결) = 최대 4회 → 93건이면 약 12분. 실측은 안 함(추정치).
- `dart3.xsd`(신형) 문서 호환성은 미확인·저우선순위(XBRL 시대라 이 경로
  자체가 불필요).

## 8-7. "웹뷰어가 최선인가?" — 원본 XML 직접경로 조사(2026-09-07, 같은날 후속)

**결론: 없다.**

1. `report/viewer.do`는 `Accept: application/xml` 헤더를 줘도 콘텐츠 협상을
   무시하고 항상 `text/html`만 반환(응답 헤더 실측 확인).
2. URL에 `.xml` 확장자를 붙여도 원본 데이터가 아니라 무관한 기본 페이지가
   나옴.
3. `dsaf001/main.do`의 JS 소스 전체(원본 dsaf001 main.do 페이지)에 "원문
   다운로드"류 함수가 없음 — PDF 다운로드(`pdf/download/*`)·XBRL 뷰어
   (`dsaf002`)·HTML 뷰어(`report/viewer.do`) 세 갈래뿐.
4. XBRL 뷰어(`dsaf002/main.do`)는 이 시대(K-GAAP, XBRL 의무화 이전) 필링엔
   해당 데이터 자체가 없어 빈 응답(0B) — 대상 밖.
5. 이미 알려진 사실과 종합: OpenDART `document.xml` API(공식 원본 XML API)는
   이 코호트(fy1999~2003)에서 이미 구조적으로 절단돼 온다는 게
   `collector/pdf_lines_sync.py` 문서에 확정돼 있음(Track C/PDF가 애초에
   존재하는 이유) — "더 원본에 가까운" 경로긴 하지만 이미 실패가 확인된
   상태라 대안이 아님.

**판단**: `report/viewer.do`(HTML)가 이 코호트에 공개적으로 접근 가능한
경로 중 사실상 원본에 가장 가까운 것 — 렌더링을 한 단계 거치지만, PDF
(좌표 텍스트, 표 개념 자체 없음)보다는 원본 `<table>` 구조를 훨씬 충실히
보존한다는 게 §8-4~8-6의 93건 실측(48% 항등식 검증 성공)으로 뒷받침됨.
"최선인가"라는 질문에 대한 답: 네, 공개적으로 시도 가능한 경로 중에서는
이게 최선이다 — 다만 렌더링 손실 자체가 없어지는 건 아니라서(레이아웃
A/B 구분, 원인A/B류 잔여 이슈) 100%는 아니고, 그 한계는 §8-4~8-6에 이미
정직하게 기록해뒀다.

## 8-8. HTML→PDF 순서 확정 + "언제 다음으로 넘어가나" 조건 설계(2026-09-07, 같은날 후속 — 사용자 지시)

### 배경

현재 파이프라인 우선순위(`collector/downloader.py` 상단 주석 +
`_EXT_PRIORITY`)는 `XML(document.xml) > XBRL(ifrs.do) > PDF > HTML`이다
— PDF가 HTML보다 먼저다(`LegacyDartScraper.fetch()`: "PDF 우선 → HTML
폴백"). 사용자 지시: **Track C 잔여 93건 스코프에 한해**(§2 스코프 그대로
— 전체 파이프라인 순서를 바꾸는 게 아니다) HTML을 PDF보다 먼저 시도하도록
바꾼다. 문제는 PDF의 `[014]`처럼 "실패"를 명확히 알려주는 에러 코드가
HTML엔 없다는 것 — HTML은 항상 200 OK를 반환하고, 파싱 자체는 "성공"해도
값이 틀렸거나(원인A/B급) 불완전할 수 있다(§8-4~8-6 실측: fail19+missing74
93건 중 완전한 항등식 성립 45건/부분 15건/완전실패 25건). 그래서 "다음
방법으로 넘어가는 조건"을 **HTML 응답 유무가 아니라 결과의 신뢰도**로
정의해야 한다.

### 신뢰도 등급 — 93건 실측(§8-4~8-6)에서 실제로 관찰된 패턴 그대로

| 등급 | 조건 | 실측 근거 | 처리 |
|---|---|---|---|
| **T1 확신** | 별도(separate) 기준 자산총계=부채총계+자본총계 항등식이 정확히 성립 | fail19의 9건·missing74의 36건 전부 이 조건으로 걸러졌고, 그중 다수가 "기존에 이미 맞았던 값은 그대로 보존한 채 나머지만 정확히 채움"(우연 아님, §8-6) | **HTML 채택, PDF 시도 안 함**(계산 절약) |
| **T2 완전공백** | 그 statement/basis 에서 facts 가 0건(그랜드토탈 3개 다 없음) | fail19의 2건(원인B, 일성건설·일진디스플)·missing74의 23건 | **PDF로 폴백**(HTML이 아예 못 찾았으니 PDF가 더 나을 수도 있음 — 실제로 fail19 2건은 PDF가 이미 이 상태보다 나은 값을 갖고 있었을 수 있어 폴백이 안전) |
| **T3 애매함** | 값이 일부 나왔으나 항등식 불성립(자산≠부채+자본), 또는 연결(consolidated) 기준(항등식이 원래도 3자 분할(외부주주지분 등)로 불성립할 수 있어 이 검증 자체가 무력 — 제일기획 연결 3건이 실증) | missing74의 15건(partial) + fail19의 제일기획 연결 3건 | **T1/T2 어느 쪽도 아님 — 자동 채택 금지.** 아래 "T3 처리" 참고 |

### T3(애매함) 처리 — 자동으로 하나를 고르지 않는다

이게 사용자가 지적한 "문제 조건"의 핵심이다. T3는 **HTML도 PDF도 자체
신뢰 등급만으로는 정답을 못 고른다** — 실측으로 이미 확인된 반례(제일기획
연결)가 있어서, "항등식 불성립=오류"로 단정하면 안 된다. 제안:

1. **PDF도 같은 필링에 대해 마저 돌린다**(T3에서만 — T1/T2는 이미 결정됨).
2. PDF 쪽도 T1(항등식 성립) 등급이면 → **PDF 채택**(이 필링 한정, HTML
   포기). 이건 원래 우선순위(PDF가 이미 성공)를 그대로 존중하는 것.
3. 둘 다 T1이 아니면(HTML도 PDF도 항등식 불성립·값 불완전) → **자동 채택
   안 함.** `report_line_anomalies`류 기존 DQ 테이블(이미 프로젝트에 있는
   메커니즘, `docs/PARSING_RULES.md` 참고)에 "HTML/PDF 두 후보값 모두"
   기록만 하고, 사람이 원문대조로 확정하기 전엔 `std_financials_v3`에
   싣지 않는다 — **"결측이 오염보다 낫다"** 원칙을 필링 선택 단계에도
   그대로 적용.
4. 연결(consolidated) basis는 항등식 검증 자체가 원리적으로 약하므로
   (외부주주지분 등 3자 분할 가능), T1 판정 기준을 별도(separate)와
   다르게 완화할지(예: "총계 3개 다 존재 + 크기 상식 범위"만으로 T1 승격)
   는 **미결정 — 다음 세션에 논의**. 지금은 연결은 전부 T3로 보수적으로
   묶어둔다(제일기획 3건이 실제로 T3에 남아있는 게 이 보수적 선택의 결과).

### 결과로 나오는 순서 (Track C 93건 스코프 한정)

```
HTML 시도
  ├─ T1(항등식 성립) → 채택, 종료
  ├─ T2(완전공백)     → PDF 시도
  │                       ├─ PDF 도 공백 → 결측 유지
  │                       └─ PDF 값 있음 → PDF 채택(기존 동작과 동일)
  └─ T3(애매함)        → PDF 도 시도
                            ├─ PDF 가 T1 → PDF 채택
                            └─ PDF 도 T1 아님 → 자동채택 보류, DQ 후보 등록(사람 확인 대기)
```

**주의**: 이 순서는 §2 스코프(잔여 93건)에 한정된다. 전체 파이프라인의
`XML > XBRL > PDF > HTML` 순서(`collector/downloader.py`)는 그대로 —
XML/XBRL이 이미 있는 필링에는 이 HTML-먼저 로직 자체가 발동하지 않는다
(그쪽은 애초에 Track A/B가 성공해서 Track C 자체가 안 열림).

## 8-9. T3 처리 구현 완료(2026-09-07, 같은날 후속 — 사용자 지시 "T3 애매함 처리부터 구현해줘")

## 8-10. DQ 후보 영속화 구현(2026-09-07, 같은날 후속 — 사용자 지시 "구현하고 확인해")

§8-8 "미결정" 3가지 중 DQ 등록 스키마를 구현했다. `dq_assertions` 재사용을
먼저 검토했으나 **저장소가 아님을 확인**(`scripts/dq_assertions.py` 는
SQL COUNT 쿼리를 매번 라이브로 실행만 하고 아무것도 INSERT 하지 않는 stateless
야간 점검 스크립트)해 재사용 불가로 판단, 신규 테이블로 결정. 기존
`CuratedKeyCandidate`(Gate B curated-key 재생성기 리뷰 큐) 패턴을 그대로
따랐다 — 복합 자연키 PK, `status`(new/reviewed/applied/rejected) 사람이
갱신, JSONB detail, first_seen_at/last_seen_at, upsert 시 사람 판정 필드는
덮어쓰지 않음.

**신규 테이블 `report_recon_candidates`**(`collector/models.py::ReconCandidate`,
create_all 로 생성 확인): PK=(corp_code, rcept_no, basis, check_kind).
`check_kind`는 확장용(지금은 `bs_grand_total_identity` 하나뿐). html/pdf
confidence(T1/T2/T3)+values(JSONB, 그랜드토탈 3종)+decision+reason, 그리고
`source_pipeline`(track_c_backfill/daily — daily 는 이상신호, 클래스독스트링
참고), status/resolution/resolution_note(사람이 원문대조 후 갱신).

**쓰기 정책**: `decision == "unresolved"`인 것만 적재(CuratedKeyCandidate의
"①일치는 로그만" 원칙과 동일 — html/pdf로 자동 채택된 건 리뷰 큐에 넣을
이유가 없다). `reconcile()` 자체는 순수 함수로 유지(§8-8/§8-9 원칙 그대로) —
DB 경계를 넘는 건 신설 `fin2/extract/reconcile_store.py`

## 8-11. T3에서 "PDF T1이면 채택" 기본값 재검토 — 교차검증 도입(2026-09-07, 같은날 후속 — 사용자 지시 "3번으로 하고 좀더 파서 확인까지 해")

§8-8 "미결정" 나머지 하나("T3에서 PDF도 T1이면 PDF 채택이 맞는 기본값인지")
를 다뤘다. 문제의식: **"항등식 성립"은 필요조건일 뿐 충분조건이 아니다** —
라벨-값이 뒤바뀌어도(swap-bug) 세 숫자가 우연히 셈이 맞아떨어질 수 있다.
이 프로젝트가 이미 KD 필링에서 확인한 PDF swap-bug 패턴(자본금 자리에
부채총계가, 자산총계 자리에 유동부채가 들어가는 식, [[pdf-multiline-layout-
handoff-2026-09-06]])이 실증 사례다. 그래서 "PDF가 T1이면 무조건 채택"
대신, **HTML과 PDF가 겹치는 항목(둘 다 값을 찾은 그랜드토탈)의 값이 서로
일치하는지 교차검증한 뒤에만 채택**하는 절충안(3번 선택지)으로 결정.

### 구현

`fin2/extract/reconcile.py`:
- `_conflicting_totals(html_facts, pdf_facts, basis)` 신설 — 둘 다 non-None
  인 그랜드토탈 항목 중 값이 다른 것만 리스트로 반환. HTML 이 T3 판정을
  받은 이상 최소 1개는 값을 찾은 상태라(T2 는 0개일 때만 성립) 겹치는
  항목은 항상 최소 1개 존재.
- `reconcile_basis()`의 T3(html)+T1(pdf) 분기: 충돌이 없으면 기존처럼 PDF
  채택(reason 에 "교차검증 통과" 명시), 충돌이 하나라도 있으면 `unresolved`
  로 강등(reason 에 어느 canonical_account 가 불일치했는지 명시) — PDF 의
  "확신"을 못 믿는다는 뜻.

### 테스트

기존 `test_t3_html_t1_pdf_picks_pdf`가 사실은 **충돌 케이스**였다는 걸
발견했다(html 자본총계 150 vs pdf 자본총계 200, 자산·부채는 일치) — 정확히
이번에 막으려는 그 패턴이었다. 두 개로 쪼갬:
- `test_t3_html_t1_pdf_picks_pdf_when_overlap_agrees` — html 이 부분적으로만
  찾았는데(2/3) PDF 와 겹치는 항목이 전부 일치 → PDF 채택.
- `test_t3_html_t1_pdf_stays_unresolved_when_overlap_conflicts` — 겹치는
  항목(자본총계) 하나가 불일치 → unresolved(원래 테스트의 픽스처 그대로,
  기대값만 "pdf"→"unresolved"로 수정).

`pytest fin2/tests/ tests/` 811 passed(무관 기존실패 1건 그대로, 회귀 0).

### 실측 검증 — 93건 전체 스캔

"이 시나리오(HTML T3 + PDF T1)가 실제로 얼마나 나오는지, 새 로직이 실측
데이터에서 뭘 하는지" 확인하려고 검증대장 93건 전체(고유 필링, 중복
제거)를 `reconcile()`로 스캔(읽기 전용, DB 미변경, 에러 0건).

**결과: 93건 중 "HTML T3 + PDF T1" 조합이 0건.** 지금까지 관찰된 T3
케이스는 전부 "PDF도 T3"(제일기획류, 둘 다 애매함) 또는 "PDF도 T2"(원인B,
완전공백) 조합이었지, "PDF만 T1"인 경우는 실측에 한 번도 없었다.

**해석**: 이번에 만든 교차검증 로직은 **이 93건 스코프에선 한 번도 발동할
기회가 없었다** — 합성 데이터(단위테스트)로는 검증됐지만 실제 충돌 사례로
검증된 건 아니다. 그렇다고 불필요한 코드는 아니다 — 코드/성능 비용이
거의 없고("결측이 오염보다 낫다" 원칙상 값싼 방어장치는 남겨두는 게
합리적), daily 파이프라인 확장 등 앞으로 이 조합이 나올 여지가 있는 한
방어막으로 유지한다. **"실측 확인 완료"가 아니라 "이론적 방어장치, 실제
발동 사례 아직 0건"으로 정직하게 기록**.

**남은 것**: §8-8 "미결정" 3가지 전부 처리(오차허용치=도입안함 결정,
T3 PDF우선 기본값=교차검증 절충안 구현). 파이프라인 배선(§5)만 유일하게
남음. 커밋 안 함.
