## 0. 배경 — 왜 "전체 재구성"이 아니라 "total_assets 한정"인가

R70 세션에서 (A-3)를 "숫자를 정규식으로 잘라 재구성"이라고 막연히 적었으나,
이번 세션 실측으로 **전체 라인아이템 재구성은 안전하게 할 수 없다**는 게
명확해졌다. 반면 **딱 하나의 값(`total_assets`)만은 위치와 무관하게 안전하게
복구할 수 있는 회계항등식 근거**를 찾았다. 이 문서는 그 좁지만 확실한 스코프만
다룬다.

## 1. 실측 — 이 포맷이 실제로 얼마나 크고 무엇인가

### 1-1. 규모 재확인 (R70 세션의 "2/2 표본"보다 훨씬 큼)

R70 종료 시점엔 호텔신라·한국팩키지 2건만 원문대조했다. 이번에 fy2004~2006
후보(861건, `docs/plans/category_c_fy2004_2006_section3_and_summary_prefix_
design_2026-09-05.md` §3의 후보 목록 재사용) 중 무작위 60건 재조사 —
"대차대조표"/"재무상태표" SECTION-3가 있는 문서 60건 전부에서, **`table_has_
amount_rows()`가 통과하는(=정상 다행표) 표를 가진 문서는 2/60(3.3%)뿐**이고
**나머지 58/60(96.7%)이 통짜-셀 포맷**이다. 즉 (A-3)는 예외적 변종이 아니라
**이 잔존 버킷의 지배적 구조**다 — (A-1)+(A-2)만으로 943건 중 11건만 회수된
이유가 바로 이것.

### 1-2. 통짜-셀 포맷의 원문 구조 (3개사 원문 XML 직접 확인)

호텔신라(`20050915000066`)·한국팩키지(`20040528000335`)·삼표시멘트
(`20051214000337`) 원문에서 `<TD>` 자체가 **자식 요소 없이 순수 텍스트 한
덩어리**임을 확인(`etree.tostring()`으로 raw XML 직접 출력, 숨은 구분자
없음 — `<BR/>`도 여러 텍스트노드도 없다):

```xml
<TD>자      산    Ⅰ. 유동자산    (1) 당좌자산    1. 현금 및 현금등가물   2. 단기금융상품   ...</TD>
<TD>21,659,879,433 16,230,501,000 1,583,346,073 ...(콤마구분 숫자가 구분자 없이 이어짐)</TD>
```

라벨 셀 안의 **항목 간 공백 폭이 일정하지 않다** — 실측: "미착자재"와 다음
항목 "Ⅱ." 사이는 공백 **1칸**인데, 다른 항목 경계는 3~7칸이다(원본 인쇄
고정폭 컬럼에서 라벨 길이에 따라 남는 패딩이 달라진 흔적으로 추정 — 짐작
아니라 실측: 호텔신라·한국팩키지·삼표시멘트 3건 모두 이 불규칙성 확인).
**⟹ 공백 폭으로 항목 경계를 자르는 방법은 신뢰할 수 없다** — 실제로 이
방법을 시도하면 "미착자재 Ⅱ. 고정자산"이 한 항목으로 잘못 합쳐진다(실측
확인, 아래 §2 참고).

### 1-3. 값 쪽은 콤마-그룹 정규식으로 안전하게 토큰화된다

금액은 전부 "콤마 3자리 그룹"(예`21,659,879,433`)이고, 음수는 **원문 자체에
이미 부호가 박혀있다** — 실측 두 가지 표기: ASCII `-`(호텔신라
`-11,347,503,582`) 및 `△`(삼표시멘트 `△4,417,236,179`). 즉
`re.findall(r'[△\-]?\d{1,3}(?:,\d{3})*', text)`로 셀 하나를 토큰화하면 **개별
숫자 경계는 정확히 갈린다**(콤마 자체가 확실한 경계 마커이기 때문 — 다음
숫자가 어디서 새로 시작하는지는 "콤마 뒤 정확히 3자리"라는 서식 규칙이
보장). 라벨과 달리 **이쪽은 안전**하다.

### 1-4. 발견한 핵심 사실 — "마지막 숫자 = `총계`"가 위치 무관하게 성립

라벨 셀 전체를 공백 제거 후 이어붙이면, **3개사 전부** 끝이 정확히
`...자본총계부채와자본총계`로 끝난다(호텔신라 라벨 641자 중 "부채와자본총계"가
634~641번째 글자 = 문자 그대로 맨 끝, 한국팩키지·삼표시멘트도 동일 확인).
**"부채와자본총계"가 대차대조표의 항상 마지막 줄**이라는 건 회계원칙이 아니라
DART 서식 관행이지만, 이번 무작위 80건 재확인(§1-5)에서 **75/75(100%)**
일치했다 — 예외 0건.

값 쪽에서도 각 기간열(컬럼)의 **마지막 토큰**이 바로 이 "부채와자본총계"의
값이다. 그리고 회계항등식(자산=부채+자본)에 의해 **이 값은 곧 `자산총계`와
같다** — 그래서 "부채와자본총계"가 어디 있는지, "자산총계"가 정확히 몇 번째
항목인지 셀 필요가 **전혀 없다**. 그냥 각 컬럼의 마지막 숫자 토큰을 취하면
그게 `total_assets`(=`total_liabilities_and_equity`)다.

**실측 교차검증(추측 아님)**: 한국팩키지(`20040528000335`, fy2004 Q1) 컬럼0의
마지막 토큰 = `35,292,944,214`. DB의 인접 기간 실측값 — fy2004 H1(같은 회사,
정상표) `total_assets=36,908,500,244`, fy2004 Q3
`total_assets=37,700,319,350`. **Q1(35.3B) < H1(36.9B) < Q3(37.7B)** — 완만한
우상향 추세와 정확히 일치(우연한 근사가 아니라 인접분기 성장궤적 자체가
들어맞음). 호텔신라(fy2005 H1) 컬럼0 마지막 토큰 = `667,863,760,114`, 1년 뒤
fy2006 H1 실측값 `701,723,563,576` — 같은 회사 반기 성장률(약 +5%/년)로
타당한 범위.

### 1-5. 안전장치(구조 게이트) 재현율 — 무작위 80건 재확인

fy2004~2006 후보 무작위 80건 중 통짜-셀 BS 75건에서, 라벨 전체(공백제거)의
**꼬리가 "자산총계" 또는 "부채와자본총계"로 끝나는 케이스 = 75/75(100%)**.
즉 이 문서 §2 의 "라벨 꼬리 총계매치" 게이트를 통과 조건으로 걸어도 회수율
손실이 거의 없다(게이트 자체가 이미 거의 항상 참).

## 2. 이번 스코프에서 뺀 것 — 왜 위험한지 실측으로 확인

### 2-1. 개별 라인아이템(전체 재구성) — 라벨 분리가 근본적으로 불안정

공백폭 휴리스틱이 "미착자재 Ⅱ. 고정자산"을 한 항목으로 오분리함을 실측
확인(§1-2). 항목 경계 마커(가나다/숫자/로마숫자 접두)로 나눠도 대손충당금·
감가상각누계액 같은 **접두 없는 부속행**(그 자체로 값은 있음)이 라벨상
구분이 안 돼, 라벨 개수와 값 개수가 어긋난다. **잘못 정렬되면 "결측"이 아니라
"엉뚱한 계정에 엉뚱한 값"이 들어간다** — 이 프로젝트가 R69/R70 내내 지켜온
"결측이 오염보다 안전" 원칙에 정면으로 위배. **미착수, 이번 문서 스코프
아님.**

### 2-2. `total_liabilities`/`total_equity` 개별 복구 — 꼬리 앞 항목 수가 회사마다 다름

"자본총계" 바로 앞에 남는 자본조정 항목 수가 회사마다 다름(실측: 한국팩키지
1개("자기주식") vs 호텔신라·삼표시멘트 2개("자기주식"+"매도가능증권평가손실")).
"끝에서 두 번째 숫자 = 자본총계"처럼 고정 오프셋으로 잡으면 회사에 따라
자본조정 세부항목 값을 자본총계로 오인할 위험 — **미착수**. `total_assets`
하나만 확보해도 자산=부채+자본 항등식으로 부채총계+자본총계의 **합**은 알 수
있지만(자산총계 그 자체가 곧 그 합), 둘을 **각각** 분리하는 건 이번
스코프가 아니다.

### 2-3. IS/CF — "마지막 숫자=주요총계" 가정이 깨짐(실측)

호텔신라 IS(손익계산서) 라벨 꼬리를 확인하니 "당기순이익" 뒤에 **주당순이익
(EPS) 주석이 같은 라벨 셀 안에 인라인으로 이어붙어 있다**
(`...이익(순이익))당반기:257원전반기:216원32기:361원31기:258원`) — "당기순이익"이
라벨 561번째 글자인데 전체 길이는 616자, 즉 끝이 아니다. IS는 컬럼 구조도
BS보다 복잡하다(반기report 실측: 3개월/누적 × 당기/전기 + 연간 두 기 =
**6개 값열**, BS의 단순 "기별 1열"과 다름). CF도 유사한 말미 주석 위험이
있을 수 있으나 미확인. **IS/CF는 이번 스코프에서 전부 제외** — "당기순이익
=마지막 숫자"라는 가정이 이미 반례로 깨졌으므로.

## 3. 코드 설계 — `total_assets` 단일값 복구

### 3-1. 트리거 조건 (전부 만족해야 함, 추가적 폴백 — 기존 경로 무변경)

`fin2/extract/legacy_pre2015.py::detect_pre2015_body_statement_tables()`가
BS(`pending=='BS'` 상태로 `_LEGACY_PENDING_SPAN` 안에 데이터표를 못 찾고
`pending`을 드롭하는 바로 그 지점(현재 L194-196, `pending_age >
_LEGACY_PENDING_SPAN` 분기)에서, 드롭하기 **직전**에 이 폴백을 한 번
시도한다:

1. 이 섹션 구간(`iter_section_span_depth_aware`가 낸 elements) 안에서, BS
   헤딩 매치 이후 다음 헤딩(IS 등) 또는 주석마커 전까지 나온 **모든 TABLE**을
   모은다(이미 `pending` 추적 로직이 순회 중이므로 새 순회 불필요 — 그 구간의
   TABLE들을 리스트로 축적).
2. 그 TABLE들 중 `table_has_amount_rows()`가 **하나도 통과 못 하면**(=진짜
   통짜-셀, 정상표가 섞여있으면 이 폴백 자체가 불필요하므로 발동 안 함)
   §3-2로 진행.

### 3-2. 추출 로직 (신규 함수, 기존 함수 무변경)

```python
_TOTAL_ASSETS_TAIL_RE = re.compile(r"(부채와자본총계|자산총계)$")
_AMOUNT_TOKEN_RE = re.compile(r"[△▲\-]?\d{1,3}(?:,\d{3})+")  # 최소 1개 콤마그룹(4자리+) 요구

def extract_squished_bs_total_assets(tables: list) -> int | None:
    """통짜-셀 BS 표 묶음에서 total_assets(=total_liabilities_and_equity)만
    위치 무관하게 복구한다. §1-4 근거: DART 관행상 '부채와자본총계'가 항상
    마지막 줄이고, 회계항등식상 이 값 = 자산총계.

    실패 시(게이트 불통과) None — 절대 추측하지 않는다.
    """
    label_parts, value_parts_col0 = [], []
    for tbl in tables:
        rows = table_direct_rows(tbl)
        if len(rows) < 2:
            continue  # 헤더뿐인 표(기간정보표) — 스킵
        tds = list(rows[1].iter("TD"))
        if len(tds) < 2:
            continue
        label_parts.append(tds[0].text or "")
        value_parts_col0.append(tds[1].text or "")  # 컬럼0 = 당기(현재 기간)

    label_nows = re.sub(r"\s+", "", "".join(label_parts))
    if not _TOTAL_ASSETS_TAIL_RE.search(label_nows):
        return None  # 게이트 불통과 — 이 표가 실제로 저 서식인지 확신 없음

    tokens = _AMOUNT_TOKEN_RE.findall("".join(value_parts_col0))
    if not tokens:
        return None
    raw = tokens[-1].replace(",", "").replace("△", "-").replace("▲", "-")
    value = int(raw)
    if value <= 0:
        return None  # 총계는 항상 양수 — 음수/0 이면 뭔가 잘못 걸린 것, 버린다
    return value
```

`_AMOUNT_TOKEN_RE`가 `_get_cells`(공백을 압축하는 기존 헬퍼)가 아니라
`.text`를 직접 쓰는 이유 — 공백 유무가 애초에 무의미(콤마가 유일한 진짜
경계)하므로 원문 그대로 정규식에 넣는 게 더 단순하고 안전(중간 처리 단계
없음 = 손상 기회 없음).

### 3-3. `report_lines` 행 구성

한 건 성공 시 `ReportLineRow` 하나만 방출(당기=col_index=0 뿐 — 어차피
`_is_loadable()`이 비교기간은 버림, §"완료된 것" 참고 불필요):

```python
ReportLineRow(
    corp_code=corp_code, rcept_no=rcept_no,
    report_fiscal_year=report_fiscal_year, report_fiscal_period=report_fiscal_period,
    statement="BS", basis=basis,           # 섹션(SEC_SEP_FS/SEC_CONSOL_FS)이 이미 확정
    label_raw="자산총계",                    # account_mapper 기존 alias 그대로 매칭
    col_index=0, context_fiscal_year=report_fiscal_year, period_kind="당기",
    is_cumulative=False, value_won=value, adecimal=0,
    unit_source=SRC_SQUISHED_TOTAL,         # 신규 provenance 태그(아래 §3-4)
    source_ref=None, context_raw=None,
    table_seq=<이 섹션 첫 표의 doc_seq>, node_role="F",  # F=합계(final) — 기존 관례
)
```

`basis`는 호출측(`detect_pre2015_body_statement_tables`)이 이미 섹션
(SEC_SEP_FS/SEC_CONSOL_FS)으로 확정한 값을 그대로 물려받는다(§`classify_
pre2015_statement_heading` docstring과 동일 원칙 — 표제 문구의 '연결' 유무를
안 믿고 섹션 권위를 믿는다).

### 3-4. 단위(unit) 처리 — 기존 `declared_unit`/`_pick_fallback_unit` 그대로 재사용

이 표도 다른 표와 똑같이 로컬 단위선언(`(단위 : 원)` 등)을 가질 수 있다 —
실측(호텔신라 TABLE-GROUP): `"대 차 대 조 표 제 15 기 3분기 2005. 9. 30
현재..."` 처럼 단위선언이 헤딩 텍스트 자체에 섞여 나오는 경우가 있어(원본
`_LEGACY_PERIOD_AFTER`가 이미 이 텍스트를 통과시킨 이력이 있음), 기존
`declared_unit()`/`nearest_section_default_unit()`/`document_default_unit()`
3단 폴백(R67, `_pick_fallback_unit`)을 **그대로** 이 표에도 적용한다 — 새
단위판정 로직을 만들지 않는다(이미 검증된 코드 재사용 = 새 버그면 위험).

**신규 provenance**: `unit_source` 값에 `"squished_total"`(varchar(14) 제약,
14자 이내 확인)을 추가 — 이 값이 통짜-셀 복구 경로에서 나왔음을 영구
기록해, 나중에 이 스코프만 따로 찾아 감사할 수 있게 한다(R67의
`SRC_SECTION_DEFAULT="section_def"` 같은 패턴).

### 3-5. 왜 안전한가

- **완전히 추가적** — 정상표가 하나라도 있으면 이 폴백은 발동 안 함(§3-1
  트리거 조건 2). 기존에 이미 성공하던 문서는 100% 무변경.
  이 폴백이 도는 문서는 **오늘 기준 전부 0행**이라(§1-1, 96.7%가 이 포맷),
  최악의 실패도 "0행 유지"지 "정상값 훼손"이 아니다.
- **위치 독립적** — 몇 번째 항목인지 셀 필요가 없다(§1-4). 라벨 분리 실패
  위험(§2-1)이 이 설계엔 아예 존재하지 않는다 — 라벨 쪽은 오직 "꼬리가
  총계로 끝나는가"라는 **부분 매치 하나**만 본다.
- **회계항등식이 근거지 통계적 추측이 아니다** — "부채와자본총계=자산총계"는
  DART 서식이 유지되는 한 항상 참이다(실측 3건 값 검증 + 무작위 80건 게이트
  100% 재현으로 확인, §1-4/§1-5).
- **거부 게이트 3중**(라벨꼬리 불일치 / 토큰 없음 / 값≤0) — 하나라도 안
  맞으면 조용히 None 반환, 그 필링은 그대로 0행 유지(현재와 동일, 회귀
  아님).
- 표 선택·pending-거리제한(`_LEGACY_PENDING_SPAN`)·주석마커 차단은 **전부
  무변경**(이 폴백은 그 로직이 "포기하기 직전"에 한 번 더 시도하는 것뿐).

## 4. 검증 계획 (구현 승인 후)

1. **드라이런**: fy2004~2006 후보 861건(§1-1) 전체에 이 폴백 적용, DB에 안
   쓰고 회수 건수·거부 사유별 집계.
2. **원문대조**: 드라이런 결과 중 최소 30건 무작위 추출해 DART 웹뷰어 원문의
   "자산총계"/"부채와자본총계" 값과 정확히 일치하는지 **전수 대조**
   (`feedback-verify-against-source` 원칙 — §1-4의 3건 예비검증을 정식
   표본으로 확장).
3. **인접기간 정합성**: 같은 회사의 인접 기간(전기/차기)에 이미 정상값이
   있으면, 복구값이 그 사이에서 상식적 범위(예 ±50%)에 드는지 자동 점검 —
   벗어나면 그 건은 백필에서 자동 제외하고 별도 목록으로 보고(추측 배제
   원칙 재확인).
4. **회귀 테스트**: 신규 pytest 케이스 — 실측 3건(호텔신라·한국팩키지·
   삼표시멘트) 원문 라벨/값 텍스트를 합성 고정문자열로 박아 단위테스트화.
   `pytest tests/ fin2/tests/` 전체 재실행(회귀 0 확인).
5. **Gate B**: 새로 채워지는 자리는 전부 이전에 완전히 비어있던 곳이라
   전이표 비교 무의미 — R69/R70과 같은 논리로 격리성 확인(이 스코프 밖
   문서는 report_lines 무변경 grep으로 확인).
6. `dq_assertions.py` 전수 — 특히 `statement_magnitude_impossible`/
   `bs_identity_gt5pct`(이 폴백은 `total_liabilities`/`total_equity`가 항상
   NULL이라 이 어서션 자체가 적용 안 될 가능성 높음 — 확인 필요) 증가폭이
   이 스코프 안에서만 나는지 확인.

## 5. 백필 계획 (구현·검증 통과 후)

- 배선 불요 — 기존 함수 내부 로직만 고침(R69/R70과 동일 판단).
- 대상: fy2004~2006(+필요시 fy2007~2010 잔존분도 같은 포맷일 가능성 있음,
  드라이런에서 확인) 중 이 폴백으로 실제 값이 나온 rcept만.
- `total_liabilities`/`total_equity`/`revenue`/`net_income` 등은 이 백필
  이후에도 계속 NULL(스코프 밖) — `build_corp()`의 기존 `_resolve()`가 이런

  있는 행이 하류에서 문제 없는지) 드라이런 단계에서 확인 필요.
