## 1. 왜 revenue H1 2026 21건이 fail_a 인가 — 근본원인 2종

`fin2/audit/face_audit.py`(독립검증)가 잡아낸 21건(14개사)을 `combine.py::_map_rows()`
+ `parser/common/account_mapper.py`로 직접 재현·확정. **std_v3 쪽이 오답이다**(R50/R51과
다름 — 이번엔 검증기가 아니라 실값 파이프라인 버그).

### 패턴A(19/21건) — "OOO수익(매출액)에 대한 매출원가" 주석행이 `is.revenue`로 오매핑

IFRS15 매출유형별 주석 표에 있는 **COGS 항목**("재화의 판매로 인한 수익(매출액)에 대한
매출원가" 등, section_path='매출원가')이 `is.revenue`로 fuzzy 매핑된다. 실측(00108001
등, `_map_rows` 직접 호출):

```
label_raw = "재화의 판매로 인한 수익(매출액)에 대한 매출원가"
-> account_code='is.revenue', confidence=0.93, stage='fuzzy', matched_alias='수익(매출액)'
```

**원인**: `account_maps/is_accounts.py:14`의 exact alias `"수익(매출액)"`(정규화 후 7자)이
이 라벨(정규화 후 20자+) 안에 부분문자열로 포함돼 있어, `account_mapper.py::
_fuzzy_match()`의 포함관계(containment) 매칭이 confidence 0.92~0.94로 오매치시킨다.
짧은-alias 오탐 방지 가드(`len_ratio<0.65 and min_len<=4`, `account_mapper.py:326`)가
있지만 **4자 이하만 보호**해서 7자짜리 "수익(매출액)"은 안 걸린다.

같은 IS 테이블에 진짜 매출총액("수익 (주6,22)", 값 73,695,960,222)이 별도로 존재하지만
**이 라벨은 어떤 alias에도 안 걸려 unknown 처리**된다(`_map_label("수익 (주6,22)","is")`
→ `unknown.수익`) — 콤마로 구분된 복수 각주번호("주6,22")가 `normalize_account_name()`의
각주 스트립 정규식이 처리 못 하는 형태로 추정(미확인, §5 참고). 그 결과 이 canonical의
**유일한 후보가 오매핑된 COGS 주석행**이 되고, `_resolve()`의 단일후보 단축경로
(`len(vals)==1 → confirmed`)가 검증 없이 그대로 확정한다.

`"수익(매출액)"` alias 자체는 **제거 불가** — DB 전체 스캔 결과 **1,725개사·71,518행**이
이 라벨을 정확한 매출총액으로 그대로 쓴다(exact-match 필수, load-bearing).

### 패턴B(2/21건, 00305668) — "수입수수료"가 보험대리점 alias에 반대방향 포함매칭

00305668(새론오토모티브, 자동차부품 제조사)의 "수입수수료"(기타이익 섹션, 값=0)가
보험대리점 전용 alias `"보험판매수입수수료"`(`is_accounts.py:30`, 정규화 후 9자)의

패턴A와 방향이 반대(짧은 라벨이 긴 alias 안에 포함)지만 같은 가드 결함.

## 2. 전수 영향도 스캔 (사용자 지시로 구현 전 실시)

### 2-1. 카탈로그 레벨 — 가드 완화 시 시스템 전역 위험

`_fuzzy_match()`의 escape-zone(`len_ratio<0.65`, `4<min_len<=12`)에서 서로 다른
canonical에 속한 alias끼리 포함관계인 쌍을 전수 스캔(768개 alias 전수 O(n²)):
**232쌍**. 상위권은 대부분 `당기순이익`/`비지배지분`/`법인세비용`/`기타포괄손익` 같은
짧고 흔한 개념어가 `controlling_ni`/`noncontrolling_ni`/`ebt` 등 다른 canonical의 긴
alias 안에 포함되는 쌍 — 정확히 R44~R49(계속영업/포괄손익 귀속 시리즈)에서 이미
전용 가드(구조적 후보·identity 대조·섹션 게이트)로 별도 대응해온 그 충돌 지대와 겹친다.
**→ `_fuzzy_match()`의 `min_len` 임계값을 범용으로 올리면 이미 세밀하게 튜닝된 R44~R49
가드 체계와 상호작용해 예측 어려운 회귀를 일으킬 위험이 크다.** 범용 임계값 변경은
비권장.

### 2-2. 실측 레벨 — 패턴별 원문 라벨 등장 범위(fy 전체, DB 전체)

| 패턴 | 라벨 조건 | 행수 | 회사수 |
|---|---|---|---|
| A | `statement='IS' AND label_raw LIKE '%수익(매출액)에 대한 매출원가%'` | 9,698 | 291 |
| B | `statement='IS' AND label_raw = '수입수수료'` | 3,303 | 279 |

**21건(14개사)은 이 중 fy=2026·H1(가장 최근 반기, Gate B가 최근 데이터부터 우선
감사)에서 잡힌 표본일 뿐 — 잠재 영향범위는 훨씬 크다.** 단, 이 라벨이 있다고 항상
`is.revenue`가 오염되는 건 아니다: 같은 basis·기간에 exact-stage 매출액 후보가 따로
있으면 `_resolve()`의 stage-rank가 그 정답을 우선하므로 무해하다. 실제 corrupt는 (a)
그 회사·기간의 진짜 매출총액 라벨이 자체적으로 unknown 처리되고(패턴A의 "수익 (주6,22)"
같은 각주변형) (b) 그래서 오매핑된 COGS/수수료 행이 유일 후보가 될 때만 발생 — 정확한
전사 corrupt 건수는 **std_v3 재계산 시뮬레이션 없이는 확정 불가**(다음 스텝 후보, §5).

## 3. 제안 수정 (범용 가드 변경 대신 canonical-scoped 배제)

`_fuzzy_match()`의 `min_len` 임계값은 건드리지 않는다(§2-1 이유). 대신 기존
`combine.py::_resolve()`/`_map_rows()`에 이미 많은 canonical-scoped curated guard가
있는 것과 같은 패턴으로, **`is.revenue` fuzzy 후보에만** 배제 규칙 추가:

```python
# is.revenue 전용 오매핑 배제(R52, 2026-08-27):
# (a) "...매출원가"를 포함하는 라벨은 COGS 주석행이지 매출이 아니다 — "수익(매출액)"
#     alias(7자)가 IFRS15 매출유형별 주석의 "OOO수익(매출액)에 대한 매출원가" 라벨
#     안에 부분문자열로 들어있어 오매치되는 것 차단(실측 291개사/9,698행).
# (b) "보험판매수입수수료" alias 는 "보험" 접두 문맥이 실제로 있을 때만 신뢰 — 없으면
#     일반기업의 "수입수수료"(기타수익, 보험과 무관)가 반대방향 포함매칭으로 오매치
#     되는 것 차단(실측 279개사/3,303행).
if c == "is.revenue" and res.stage == "fuzzy":
    if "매출원가" in (r["label_raw"] or ""):
        continue  # is.revenue 후보에서 제외
    if res.matched_alias == "보험판매수입수수료" and "보험" not in (r["label_raw"] or ""):
        continue
```

(의사코드 — 실제 삽입 위치는 `_map_rows()`의 `res.confidence < 0.88` 체크 직후가
자연스러움. `matched_alias`가 현재 `cands` dict에 안 실려있어 로깅용으로 필드 추가
필요할 수 있음 — 구현 시 확인.)

### 3-1. 별개 발견 — 진짜 매출총액 각주변형 미포착(제안 범위 밖, 후속 후보)

00305668의 "수익 (주6,22)"처럼 **콤마로 구분된 복수 각주번호**가 붙은 총계 라벨이
`is.revenue`에 전혀 안 걸리는(unknown) 문제는 이번 수정 범위 밖이다. 이걸 고치면
패턴A/B 배제 없이도 진짜 후보가 생겨 자동으로 정답이 이길 가능성이 있지만(단일후보
단축경로가 옳은 값으로 바뀜), **정규식 검증 없이 단정하지 않는다** — 별도 조사 필요.
