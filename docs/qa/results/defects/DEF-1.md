# DEF-1 — 딥링크 첫 진입 시 스퓨리어스 "Page not found" 모달 (기본 페이지 `/company` 한정)

- **심각도**: S3 (표기/UX — 값은 정확, 앱은 크래시하지 않음, Close 버튼 또는 새로고침으로 즉시 해소되고 그 뒤 화면은 완전히 정상)
- **분류**: 앱버그 (Streamlit 프레임워크의 멀티페이지 라우팅과 앱의 `url_path="company", default=True` 조합에서 발생) / 매뉴얼불일치(매뉴얼이 이 동작을 언급하지 않음)
- **상태**: 조사 완료 — 앱 코드로 해소 불가(Streamlit 프레임워크 한계), 무수정
- **발견 체크리스트 ID**: XC-3 (에러 상태 정상 노출) 점검 중 발견 — 실제로는 XC-3 자체는 아니고 페이지 최초 로드 단계의 별도 관찰
- **발견일 / 담당자**: 2026-07-07 / Sonnet(테스트 담당)

## 위치
- **페이지**: `/company` (기본 페이지, url_path 딥링크)
- **탭 / 위젯**: 페이지 최초 로드 시 나타나는 Streamlit 내장 모달(role="dialog", 제목 "Page not found")

## 재현 조건
- **기업**: 해당 없음(기업 선택 이전 단계, 모든 기업에서 동일하게 재현)
- **토글 상태**: 해당 없음
- **기간 구간**: 해당 없음
- **기타 입력값**: 브라우저에서 `http://localhost:8501/company`로 직접 접속(북마크 접속, 새로고침(F5), 또는 새 브라우저 세션에서 이 URL로 최초 진입)

## 재현 단계
1. 앱이 이미 기동된 상태에서, 브라우저(또는 새 시크릿 창)로 `http://localhost:8501/` 이 아니라 **`http://localhost:8501/company`를 직접 입력**해 접속한다.
2. 페이지 로드 완료(부하 이벤트) 후 즉시(또는 최대 10초 대기) 화면 중앙에 **"Page not found — The page that you have requested does not seem to exist. Running the app's main page."** 모달이 뜬다.
3. 모달은 몇 초를 기다려도(테스트: 4초·10초 대기 모두) 스스로 사라지지 않고, 그동안 모달이 페이지 전체 클릭을 가로막아 사이드바 등 어떤 요소도 클릭할 수 없다.
4. 모달의 [Close] 버튼을 클릭하거나 브라우저를 새로고침(F5)하면 모달이 사라지고 그 아래의 `/company` 화면(사이드바+기업 시각화)은 **완전히 정상적으로** 렌더되어 있다.

## 기대결과
- 매뉴얼 근거: `docs/user_manual_app.md` §1 "페이지 딥링크"— "URL_path로 이동: `/company`(기본) `/screener` `/quarter-change` `/valuation` `/compare` `/chart-builder` `/collect` `/help`". `/company`가 **기본(default=True) 페이지**로 명시되어 있으므로, 이 URL로 직접 접속했을 때 정상 화면이 즉시 뜨는 것이 기대 동작이다. "Page not found" 오류가 뜨는 것은 매뉴얼이 다루지 않는 동작이며, 사용자가 실제로 이 URL을 북마크하거나 새로고침할 실제 시나리오에서 매번 겪게 되는 혼란스러운 첫인상이다.

## 실제결과
- `/company`로 최초 접속(또는 새로고침) 시 100% 재현율(총 9회 독립 시행, 모두 재현: 4초 대기 5/5, 10초 대기 1/1, 반복 확인 3/3)로 "Page not found" 모달이 표시된다.
- 대조군: 동일한 방식으로 `/screener`, `/help`, `/quarter-change`에 직접 접속하면 모달이 전혀 뜨지 않는다(각 3회, 0/3 재현) — **`/company`(기본 페이지) 딥링크에서만 발생하는 좁은 범위의 현상**으로 확인됨.
- 헤드리스 자동화 타이밍 문제가 아님을 별도 확인: `wait_until="load"`(networkidle이 아님) + 최대 10초의 넉넉한 대기 후에도 재현되므로 실제 사용자가 겪는 화면임. 모달의 [Close] 버튼 클릭 또는 새로고침 1회로 즉시 해소되고 이후 앱은 완전 정상 동작.

- **콘솔/서버 예외**: 없음(Python 트레이스백이나 Streamlit 서버측 에러 없음 — 순수 클라이언트 라우팅 단계의 현상)

## 영향 범위
- `/company`(앱의 기본 페이지) URL로의 직접 진입(북마크·새로고침·공유링크) 전반에 영향. 사이드바 내부 네비게이션 링크 클릭(SPA 방식 페이지 전환)으로 진입할 때는 전혀 발생하지 않으므로, 앱을 정상적으로 사용 중인 세션 내 이동에는 영향 없음.
- 전수 스윕(Tier-1) 자동화 관점: 회사별 4조합 페이지 로드마다 이 모달을 만날 수 있어, 대응하지 않으면 스윕 스크립트가 멈춘다(본 세션에서 재시도 로직으로 우회 처리함, `scripts/qa/sweep_company_pages.py`의 `dismiss_cold_start_dialog()`).

## 비고
- 근본 원인 추정: Streamlit의 `st.navigation`이 클라이언트 라우터를 초기화하기 전, 브라우저가 먼저 `/company`(default 페이지 자신의 명시적 url_path) 경로를 로드하면서 클라이언트가 "알려진 경로 목록"을 아직 받기 전 상태에서 "존재하지 않는 경로"로 오판했다가, 스크립트 실행이 끝나 실제로는 기본 페이지를 정상 렌더한 것으로 보임(모달 본문 "Running the app's main page." 문구가 이를 뒷받침). `/screener` 등 비-기본 페이지는 다른 클라이언트 라우팅 경로를 타서 이 레이스가 발생하지 않는 것으로 추정.
- 감리 권고: Streamlit 자체 프레임워크 동작일 가능성이 있어 앱 코드만으로 완전히 제거하기 어려울 수 있음 — Streamlit 버전 업그레이드 확인 또는 `default=True` 페이지에 명시적 url_path를 주지 않는(빈 경로만 default로 두는) 우회책 검토 권장.

## 조치 결과 (2026-07-08 개발 조사)
- 감리 권고안(`default=True` 페이지에서 `url_path` 제거)을 실측 검증: `app/main.py`의 `company_page` 등록에서 `url_path="company"`를 제거한 뒤 테스트 인스턴스에서 재확인한 결과, **`/company` 직접 진입 시 모달이 여전히 재현됨**(제거 전/후 동일하게 True). 정상 진입 경로(`/`)는 애초부터 모달이 없었음(제거 전/후 모두 False).
- 즉 이 우회책은 모달을 없애지 못하고 `/company` 딥링크 등록만 잃는 손해뿐이라 **채택하지 않고 원상복구**(`url_path="company"` 유지, 근거 주석만 추가).
- **결론**: Streamlit `st.navigation` 클라이언트 라우터 초기화 타이밍에 기인한 프레임워크 동작으로 확정. 앱 코드 수정으로 해소 불가 — Streamlit 버전 업그레이드 확인을 백로그로 유지.
