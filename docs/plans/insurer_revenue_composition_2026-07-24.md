## 0. 한 줄 결론
IFRS17(2023) 전환으로 보험사 `영업수익` 총계 라인이 사라짐. **표준 revenue = 보험(영업/서비스)수익 +
투자(영업/서비스)수익**(합산), **표준 영업이익 = 원문 `영업이익`**(= 보험손익/서비스결과 + 투자손익, v3
이미 정답). 스크리너는 정규화 합산값으로 교차비교, 개별 tearsheet 은 업종별 네이티브 항목을 표시. 전 보험사
실현성 100% 확인.

## 1. 문제 (IFRS17 매출 단절)
- **≤2022(구기준)**: `영업수익` = 단일 총계(보험 + 투자 포함). 예 삼성생명 2022 = 40.3조.
- **2023+(IFRS17)**: IS 가 `보험손익`/`투자손익` 섹션으로 분리, **총계 라인 없음**. v3 는 `보험서비스수익`만
  집계 → 삼성생명 40.3조(2022)→8.7조(2023) **−78% 착시 단절**(회계기준 변경일 뿐, 사업 붕괴 아님).
- **v2(구 체인)는 비일관**: 같은 회사가 연도마다 보험만 ↔ 합산 오락가락(한화생명 2024=10.9조 보험만,
  2025=27.4조 합산). → v2 를 기준삼을 수 없음. **일관된 정의 필요.**

## 2. 확정 모델 (원문 산술 검증)
사용자 제공 원문(삼성화재 2025·삼성생명 2025 정정보고서)으로 정확히 검증:

| 표준 항목 | 보험사 매핑 | 검증 |
|---|---|---|
| **revenue(매출액)** | 보험(영업/서비스)수익 + 투자(영업/서비스)수익 | 삼성생명 9.9+27.2=**37.1조** · 삼성화재 19.5+5.2=**24.8조** |
| **operating_income** | 원문 `영업이익` (= 보험손익/서비스결과 + 투자손익) | 삼성화재 1.48+1.18=**2.66조=원문** · 삼성생명 0.98+1.60=**2.58조=원문** |

- **operating_income 은 v3 가 이미 100% 정답**(원문 `영업이익` 직접 소싱). **손댈 것 없음.**
- **revenue 만 합산 규칙 추가 필요**(현재 v3 는 보험분만 → 투자분 누락).

## 3. 라벨 패밀리 (생보 vs 손보)
| | 보험 매출 | 투자 매출 | 보험 손익 | 투자 손익 |
|---|---|---|---|---|
| **생보(life)** | 보험서비스수익 | **투자서비스수익** | 보험서비스결과 | 투자손익 |
| **손보(non-life)** | 보험영업수익 | **투자영업수익** | 보험손익 | 투자손익 |

※ 하위항목(일반보험서비스수익·출재보험서비스수익·이자수익 등)은 소계의 자식 → 정규화 exact 매칭으로 자동 제외.

## 4. (b) 실현성 조사 결과 (`layer3_insurer_revenue_survey.py`)
보험사 유니버스 = **12사**. IFRS17(2023+) 기업연도:
- **합산 가능(보험+투자 rev 둘 다 탐지) = 100%** (연결 29 + 단일법인 별도 6[흥국화재·롯데손보]).
  단일법인 손보사는 연결 미공시 → **공시 basis(연결 or 별도) 기준으로 조립**하면 전부 성립.
- **operating_income = 35/35 v3 이미 정답.**
- 실측 합산 예: 삼성생명 30.9/33.8/37.1조(23/24/25) · 삼성화재 20.8/22.7/24.8조 · 코리안리 7.0조 · 한화생명 22.8조.

## 5. 설계 (계층별)
### 계층3 (std_v3) — 데이터
1. **revenue 조립 규칙 추가**(rules.py additive 계열, 보험사 한정):
   - pre-2023 또는 `영업수익` 총계 라인 존재 시: **총계 직접 사용**(현 min-depth 규칙이 이미 처리).
   - IFRS17(총계 없음): **revenue = 보험(영업|서비스)수익 + 투자(영업|서비스)수익**(공시 basis 기준).
   - provenance 플래그(예 `composed_revenue=true` + 성분 rcept) — 단일 라인 아닌 조립값 명시(Gate B 성격).
2. **성분 보존**(tearsheet 용): 보험영업수익/투자영업수익(또는 서비스) 소계를 **별도 컬럼 or provenance JSONB**
   에 저장. → 개별 뷰가 재파싱 없이 네이티브 표시. **[결정필요: 컬럼 vs JSONB]**
3. operating_income: **무변경**.

### 계층4 (앱) — 스크리너/시각화 (PRD 05/06 영역)
- **스크리너**: 정규화 `revenue`(합산)로 일반기업과 교차 스크린.
- **tearsheet/개별뷰**: 업종별 네이티브 항목 표시(보험사=보험/투자영업수익·보험/투자손익; 일반=매출액).
  "매출액" 단일 라벨 강제 금지 — 업종 프로파일별 항목 구성.
- IFRS17 전환선(2023) 시각 표시(마커/주석) — 어떤 정의든 완전 연속성 불가하므로.

## 6. 남은 결정 (사용자)
1. **성분 저장 방식** — std_v3 에 보험/투자 매출 소계 전용 컬럼 추가 vs provenance JSONB `industry_lines`.
2. **업종 확장 범위** — 보험(갭 최대)만 우선 vs 은행(순이자수익+수수료)·증권(수수료+투자)·지주(매출(영업수익))
   동시 설계. 권장: **보험부터, 단 일반 "업종별 구성" 메커니즘으로 설계**(하드코딩 회피).
3. **스크리너 교차업종 비율 주의** — 보험 revenue(총보험료·투자유입 포함)는 제조사 매출액과 경제적 비동일.
   P/S·영업이익률 해석 caveat 표기 여부. (블룸버그도 동일 한계 — 정규화값 + 네이티브 병행)
4. **기타영업수익/특별계정 등 경계** — 합산에 포함 범위(현 설계 = 보험·투자 소계 2개만, 기타는 소계 내 포함분만).
