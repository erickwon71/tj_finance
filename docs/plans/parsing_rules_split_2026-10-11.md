### 규칙 한 건의 표준 서식 (모델 해석 차이 방지)

```
## R<번호> <한 줄 제목>            ← 한 줄. 줄바꿈 금지
- 상태: 유효 | 대체됨(→R..) | 이행중 | 폐지
- 계층: 2 | 3 | 검증 | 운영
- 규칙: (명령형 1~3문장. “~한다/~하지 않는다”)
- 판정 예: 입력 → 기대 결과 (최소 1개, 가능하면 원문 사례)
- 근거: 파일:줄, 사용자 결정 일자
- 어기면: 한 줄
(이하 배경·경위는 “<details>” 성격의 별도 소절 — 판정에 쓰지 않음)
```

핵심: **“규칙”(판정에 쓰는 것)과 “경위·사례”(읽어도 판정에 안 쓰는 것)를 물리적으로 분리**한다.
Haiku가 흔들린 원인이 “경위 속에 섞인 예외 문구”였기 때문이다.

## 4. worktree·모델 일관성 장치

1. **규칙 문서 수정 가능 위치 = main 과 `camp_err_review` 두 곳뿐** (사용자 결정 2026-10-11). `camp_run` 등 다른 worktree는 수정 금지이고 main 에서 받기만 한다. 두 곳 수정이 갈라지지 않도록 수정 후 즉시 서로 반영(merge)한다. (`CLAUDE.md`에 한 줄 명시.)
2. **일치 검사 스크립트** `scripts/check_rules_sync.py` (신규):
   - R번호 중복·누락·깨진 제목(`##` 연속 줄) 검사
   - 색인표 ↔ 실제 파일의 R번호 일치
   - 모든 worktree의 `docs/rules/*`·`verify_prompt.md`·`CLAUDE.md` 해시가 main과 같은지
   - 상태가 “유효”가 아닌 규칙을 `verify_prompt.md`가 인용하는지
3. **verify_prompt.md 연동**: 검증 슬롯이 보는 규칙은 PARSING_RULES가 아니라 verify_prompt다. 둘 사이 공통 규칙(R0-2, R169·R207·R238 단위 예외 등)은 **한 곳에서만 정의**하고 다른 쪽은 R번호 링크만 둔다.
4. **모델 일치 시험 재사용**: 문서 분리 후 `scripts/verify_sim`으로 Haiku×3 / Sonnet×1 일치(14/14 기준)를 다시 확인하고 재개한다. 분리 자체가 해석을 바꾸지 않았다는 증거로 쓴다.
5. **CLAUDE.md 갱신**: “단일 진입점 = PARSING_RULES.md” 문구는 유지하되 “계층 파일: …”로 안내. `CLAUDE.local.md`(worktree별 상이)에는 규칙 본문을 두지 않고 **작업 지시만** 둔다.
