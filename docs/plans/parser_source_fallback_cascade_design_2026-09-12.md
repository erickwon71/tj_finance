# 파서/소스 실패 시 대체 시퀀스 — 설계 (2026-09-12)

**상태**: ✅[0]·[B]·[D] 구현 완료(사용자 지시 "합리적 방향으로 정해서 구현하고 test해봐").
결정 사항: §4-1은 (a)(`_parse_xml_file()` 내부 게이트) 채택, §4-2는 "일반 배선"이 아니라
**재사용 가능한 개별 스크립트**(`scripts/recover_and_report_corrupted_xml_2026-09-12.py`)로
구현(§5 참고 — Category C 하드코딩 스코프는 안 건드림), §4-3 임계치 1%는 실측(200건

**계기**: 같은 세션 두 사고가 "1차가 실패해도 다음 걸 시도하는 절차가 없다"는 같은 뿌리를
가진 걸 확인 — ①R91(같은 XML 안에서 시대별 탐지기 편방향 무재시도, 해결됨), ②솔트웨어
20220802000208(`document.xml` 자체가 DART 서버 archive에서 바이트 손상 — 재다운로드해도
동일함을 직접 확인. PDF 폴백은 텍스트는 멀쩡했으나 `reconcile()`이 신뢰도 부족으로
자동채택 거부, 대기열行). 두 사고가 사실은 "실패 시 다음 단계로 넘어가는 시�퀀스"라는
같은 문제의 다른 계층에서 벌어진 것 — 이 문서는 그 시퀀스를 하나로 정리한다.

## 2. 갭 — "승격 조건(언제 다음 계층을 시도하나)"이 계층마다 제각각이고, 특히 하나가 아예 없다

- A의 트리거(0행)는 명확하다.
- **B의 트리거가 너무 좁다** — "파일이 존재하는가"만 본다. **파일은 있는데 내용이
  손상된 경우**(오늘 사고 — DART 서버 archive 자체가 깨져 있었음, 재다운로드해도 동일)는
  B로 넘어갈 계기 자체가 없다. `extract_report_lines()`는 그냥 "본문 섹션 없음"으로
  찍고 조용히 끝난다 — 0행이라 A는 시도되지만(같은 손상된 XML로 반대 시대까지 다
  시도해봐도 당연히 또 0행), **소스 전환(B)은 아예 후보에 오르지 못한다.**
- C·D·E는 B가 여러 후보를 만들어줘야 작동하므로, B가 안 걸리면 이 밑으로 전부 안 걸린다.

**즉 빠진 건 "0. 원문 손상 감지"** — 지금은 없다.

**핵심 원칙**(오늘 두 사고에서 재확인된 것, 새로 만드는 게 아니라 이미 이 코드베이스
전체를 관통하는 R6/R9와 동일):
- 각 계층의 "자동채택" 기준은 지금처럼 **보수적으로 유지**한다(C의 T1-only 자동채택을
  안 풀어도 됨 — 오늘 솔트웨어에서 이 보수성 덕분에 항등식 안 맞는 PDF 값을 안 실었다).
  바꿔야 할 건 "언제 다음 계층을 시도라도 해보는가"(승격 조건)이지, "언제 자동으로
  믿는가"(채택 기준)가 아니다.
- 모든 승격은 **로그로 남긴다**(R91의 `logger.warning` 관례 그대로) — 나중에 "0단계가
  몇 번 발동했는지" 집계해 이 설계의 실제 가치를 측정할 수 있어야 한다.

## 4. 결정 필요 사항

1. **[0] 원문 손상 감지를 어디에 넣을까**
   - (a) `_parse_xml_file()` 안에 게이트로 넣어 손상 시 `None`(파싱 실패)을 반환 —
     `extract_report_lines()`가 이미 "XML 루트 없음" 처리 경로를 갖고 있어 배선이 가장
     간단하다.
   - (b) 별도 상시 스캔 스크립트로 raw_report 전체를 돌며 손상 파일을 미리 찾아
     `report_recon_candidates`류 대기열에 선제 등록 — 전수 스캔 비용 발생(raw_report가
     NAS라 느림, 메모리 `feedback-bulk-read-use-sdcard` 참고).
   - 추천: (a) — 손상 파일이 실제로 파싱을 "시도할 때"만 비용이 들고, 검사 자체가
     디코딩 이후 문자열 스캔 한 번이라 저렴하다.
2. **B(소스 전환)를 Category C 전용에서 일반화할지** — `sync_pdf_recovery()`가 지금
   `fiscal_year BETWEEN 1999 AND 2003`로 하드코딩돼 있다. 이번처럼 개별 호출
   (`recover_one()` 직접 사용)로 그때그때 처리할지, 아니면 "0단계 손상 감지"가 걸린
   모든 rcept를 자동으로 이 경로에 태우는 일반 배선을 만들지.
3. **임계치·회귀 범위** — 손상 비율 임계치(1% 제안)를 정하기 전에 표본을 더 모아
   검증할지(예: raw_report 일부 표본으로 오탐률 측정), 아니면 이번 실측(정상 0% vs
   손상 11%)만으로 충분히 크게 벌어진다고 보고 바로 적용할지.

## 8. R136 이후 사용자 반문으로 발견된 더 근본적인 구조 결함 — R137 (2026-09-18, 같은 날)

R136로 BS 5개 중 4개는 해결됐지만, 마지막 1개(미처분이익잉여금)는 "계정지도가
의도적으로 제외했다"고 위에서 설명했었다. 사용자가 "그 판단이 왜 저장 자체를
막아야 하느냐"고 반문 — 코드로 확인해보니 정확했다: XML 정상 경로는 계정지도
매핑 성패와 무관하게 원문 라벨을 전부 저장하는데, PDF 복구 경로만 매핑 실패
라벨의 저장 자체를 막고 있었다(설계 결함, `account_mapper` 매핑을 report_lines
저장 게이트로 오용). "저장"과 "캐노니컬 매핑"을 분리하는 근본수정 진행 — 그
과정에서 노출된 리전 경계 결함(마지막 앵커가 주석 섹션까지 안 닫힘) 2건과
헤더 주석열 감지 갭(자간공백 "주 석") 1건도 같이 발견·수정. 상세는
`docs/PARSING_RULES.md` R137. 솔트웨어 최종 상태: BS/CF/IS = 23/10/8행,
전부 `unit_source='pdf'` 자동 추출(manual 삽입 불필요해짐).
