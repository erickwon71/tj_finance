# Track C(PDF-only) 파서 강건성 — 잔여 93건 원인 카탈로그 + 진행 방식

**상태**: 진행 중 — 세션마다 하나씩 보강.
**스코프**: 195건(72개사) 3줄 레이아웃 census 중, 오늘(2026-09-06) 세 차례 백필
(R76→R77→R78) 이후에도 완전히 ok가 아닌 **93건 필링(41개사)**.
**검증대장**: https://claude.ai/code/artifact/7080b708-5ba0-4f75-85c9-3491c35e69e0
(실패 19건 + 결측 74건, DART 링크·현재 DB 값 포함).

## 왜 이 문서가 필요한가

사람이 DART 웹뷰어나 PDF를 직접 열어보면 표가 멀쩡해 보이는데, 파서는 계속
새로운 방식으로 틀린다 — 오늘 하루에만 서로 완전히 다른 원인 3종(R76/R77/R78)이
나왔고, 방금 4번째(아래 §4)가 추가로 나왔다. 이건 "버그 하나를 고치면 끝"이 아니라
**PDF 텍스트 추출이라는 방식 자체가 이 시대(1999~2003년) 문서군에서 구조적으로
불안정하다**는 뜻이다. 사용자 결정(2026-09-06): 93건을 한 번에 일반화해서 고치려
하지 말고, 검증대장을 하나씩 원문대조하면서 **패턴을 카탈로그화하고 사례별로
보강**해 나간다 — 짐작으로 일반화하면 다른 정상 필링을 깰 위험이 있다는 이
프로젝트의 기존 교훈([[feedback-verify-against-source]] 급의 원칙)을 그대로 따른다.

## §4. 신규 미해결 — 라벨열·숫자열 전체가 한 칸씩 밀림(00111218)

**사례**: `00111218`(KD) rcept `20010814000291`, H1 2001, 별도.

라벨은 전혀 안 쪼개져 있고(R78과 다름), 숫자도 정상 포맷인데, **라벨 줄과 숫자
줄의 대응이 문서 중간부터 한 칸씩 밀린다**:

```
2.개    발    비
24,164,567 …          ← 실제로는 "자산총계"의 값
자 산 총 계
13,007,264 …           ← 실제로는 "Ⅰ.유동부채"의 값
Ⅰ.유 동 부 채
2,907,533 …
```

문서 내부 항등식으로 역산한 진짜 값: **자산총계=24,164,567 / 부채총계=14,826,827
/ 자본총계=9,337,740**(14,826,827+9,337,740=24,164,567, 정확히 성립). 지금 DB엔
전부 밀린 엉뚱한 값이 들어가 있다(부채총계 자리에 자본금 값 2,900,000이 들어가는
등, 밀림이 문서 한 곳이 아니라 최소 두 곳에서 발생 — 단순 "전체 한 칸 보정"으로
안 끝날 수 있음).

`extract_tables()`(R78 폴백)로도 확인했으나 도움이 안 됐다 — 이 문서는 표 안에
행 경계선이 전혀 없어서 라벨 전체·숫자 전체가 각각 **하나의 거대한 셀**로 뭉쳐
나온다(줄바꿈으로만 항목 구분). R78이 해결한 "한 항목이 여러 줄로 쪼개짐"과
정반대로, 여기선 표로 봐도 순서 밀림 자체가 그대로 보존된다.

**이 세션 맨 처음(R76 이전) 사용자가 DART 웹뷰어에서 발견했던 것과 같은 계열의
현상**으로 보인다(총계 앞에 라벨 쪽엔 없는 빈 자리가 값 쪽에만 있어 밀린다) —
다만 이번엔 PDF 텍스트 자체에서도 재현된다는 게 새로 확인된 사실이다. 이 문서
고유의 인쇄 결함(원본 소스 자체의 서식 문제)일 가능성이 높다.

**미착수 이유(2026-09-06 최초 기록 당시)**: 지금 확인된 사례가 이 필링 하나뿐이라, 항등식 역산 기반 일반화
복구 로직(`_fix_swapped_grand_total_equity`류)을 만들기엔 근거가 부족하다 —
사용자 결정(2026-09-06): 지금 억지로 일반화하지 않는다. 검증대장을 계속
원문대조하면서 같은 패턴이 몇 건 더 나오는지 확인한 뒤, 패턴이 반복 확인되면
그때 일반화 설계에 착수한다.

### §4-보강(2026-09-07) — KD 3개 필링(H1·Q1·Q3 2001) 전부 원문대조, 동일 패턴 3/3 확인

**연결(consolidated) 행 관련 — 부수 확인**: std_financials_v3를 직접 조회하니
세 필링 모두 `statement_type='consolidated'` 행이 `basis_fallback=True`로
존재하고 값이 `separate` 행과 완전히 동일했다. 이건 새 버그가 아니라 **의도된
폴백**임을 확인 — 세 원문 모두 "4. 연결재무제표: 해당사항 없습니다"가 명시돼

파싱 하나뿐이고, 연결 쪽은 폴백을 통해 그 오염을 그대로 옮겨 받은 이차 피해 —
연결 경로는 별도로 손댈 필요 없음, 별도 건만 고치면 연결도 같이 해소됨.

## 검토 후보(2026-09-07 제기) — PDF 대신 웹뷰어 HTML(=사실상 원본 XML) 직접 스크래핑

**배경**: KD 원문대조 중 사용자가 `dsaf001/main.do?rcpNo=...` 웹뷰어로 같은
필링을 봤더니 표가 깔끔했다("셀 구분이 없어서 파싱이 어려운 거냐"는 질문).
확인 결과:

- 웹뷰어는 DART 서버가 **원본 XML 문서를 그대로 재렌더링**한 것 — 원본 안에
  실제 `<TABLE><TR><TD>` 구조가 있음(로컬 아카이브 XML 파일을 직접 열어
  태그를 확인함). 셀 경계가 명확해 기계 파싱에도 유리할 것으로 보임.
- Track C가 지금 읽는 **PDF는 그 원본을 인쇄용으로 한 번 더 변환한 결과물**이라
  "표" 개념 자체가 없다 — 글자가 페이지 위 (x,y) 좌표에 찍혀 있을 뿐이고,
  `pdfplumber`가 y좌표로 "줄"을 재구성할 뿐 열 구분은 원리적으로 모른다.
  KD의 라벨-숫자 어긋남류 버그가 이 근본 한계에서 나온다.
- 애초에 PDF로 우회하는 이유는 R76(로컬 OpenDART XML 아카이브가 2001년치
  3,625건 중 3,624건 손상)인데, 웹뷰어는 손상된 로컬 사본과 무관하게 DART
  서버가 실시간으로 다시 그려주는 것으로 보여 멀쩡하다.

**다음 세션에 검토할 것**(아직 설계·구현 착수 안 함 — 논의만):
1. 웹뷰어(`dsaf001/main.do`)가 실제로 내부적으로 어느 엔드포인트에서 HTML을
   받아오는지(iframe 소스 확인) — 그 응답이 진짜 원본 XML을 그대로 HTML화한
   것인지, 손상 여부와 무관하게 항상 정상인지 확인.
2. 그 HTML을 `LegacyDartScraper`류로 긁어와 표 구조를 그대로 파싱하는 새 추출
   경로를 만들 가치가 있는지 — 대상 범위가 "2001년 PDF-only 195건"만인지,
   아니면 이 시대 전체(1999~2003년대) PDF 소스 필링 전반에 적용 가능한지.
3. 기존 PDF 경로·`_iter_data_lines_multiline`류 로직과의 관계 — 완전 대체인지,
   HTML 우선·PDF 폴백인지.

**사용자 결정(2026-09-07)**: 검토 대상으로 기록만 해두고, 이번 세션엔 착수하지
않는다. DB증권 원문대조와 함께 다음 세션 후보로 올려둔다.

### 검토 후보 §1~3 실측 확인(2026-09-07, 같은 날 후속) — 결론: 강력히 유효, 착수는 여전히 대기

위 세 질문을 실제로 코드/HTTP 요청으로 확인했다(구현 착수 아님, 순수 조사).
`collector/legacy_downloader.py::LegacyDartScraper`가 **이미** 이 경로의 요청
흐름(`dsaf001/main.do`로 세션+TOC 확보 → `report/viewer.do`로 본문 HTML)을
갖고 있어(원래 목적: OpenDART `[014]` 오류 시 PDF 폴백), 그 내부 메서드
(`_get_view_params()`/`_fetch_html()`)를 그대로 재사용해 실측했다.

**① `dsaf001/main.do`가 실제로 어디서 HTML을 받아오는가**: 메인 페이지 안에
`node1`/`node2` 라는 JS 객체로 이루어진 트리가 있고, 각 노드가 목차 항목마다
`text`(목차명, 예:`"3. 재무제표"`)·`eleId`·`offset`·`length`·`dtd`
(`dart2.dtd`=~2012년 이전 구형, `dart3.xsd`=현행)를 갖고 있다. 사용자가 목차를
클릭하면 그 필드들로 `report/viewer.do?rcpNo=...&dcmNo=...&eleId=...&offset=...
&length=...&dtd=...`를 호출해 그 섹션만 HTML로 받는다 — 즉 **문서 전체가 아니라
섹션별로 나뉘어 서빙**된다(재무제표 섹션 하나만 받으려면 이 트리를 파싱해
`"재무제표"`가 포함된 노드의 offset/length/eleId를 찾아야 함 — 기존
`_get_view_params()`는 **rcept_no와 매칭되는 첫 `viewDoc()` 호출**만 잡는 로직이라
지금은 표지(cover page, eleId=10)만 반환한다는 것도 이번에 확인됨 — 재무제표
섹션을 받으려면 이 트리 파싱 로직을 새로 짜야 한다).

**② 그 응답이 진짜 원본을 그대로 HTML화한 것이고, 손상 여부와 무관하게 항상
정상인가**: KD(00111218) H1 2001(`rcpNo=20010814000291`)의 "3. 재무제표"
섹션(eleId=3126, offset=334223, length=25936)을 실제로 받아 대차대조표 표를
파싱한 결과:

- 라벨 셀 전체가 `<BR/>`로만 구분된 **하나의 거대한 `<TD>`**(§4가 추측했던 그대로,
  원본 자체가 행 경계선 없이 이렇게 조판돼 있었음이 확정됨)이고, 그 옆의 값 셀
  4개(제28기 반기/제27기 반기/제27기/제26기)도 각각 같은 개수로 `<BR/>` 구분된
  거대한 `<TD>` 하나씩이었다.
- 라벨 셀을 `<BR/>` 기준으로 쪼갠 인덱스와 값 셀을 같은 기준으로 쪼갠 인덱스를
  **그대로 1:1 대응**시켰더니 — PDF에서는 밀려서 틀렸던 바로 그 값들이 —
  전부 정확히 일치했다: `[42] 자산총계 → 24,164,567`, `[66] 부채총계 →
  14,826,827`, `[81] 자본총계 → 9,337,740`, `[83] 부채와자본총계 →
  24,164,567`(§4-보강이 원문대조로 이미 확정해둔 진짜 값과 정확히 일치, 항등식도
  성립). 즉 **§4의 KD 밀림 버그는 PDF 텍스트추출 단계에서만 생기는 인공물이지,
  원본 문서 자체의 결함이 아니다** — HTML 경로로 가면 이 버그 자체가 원천적으로
  발생하지 않는다.
- 교차검증으로 R78 발견 필링인 동성제약(00116268) H1 2001
  (`rcpNo=20010813000395`, "3. 재무제표" eleId=2009)도 같은 방식으로 받아봤다 —
  이쪽은 KD와 반대로 **항목마다 정상적인 `<TR><TD>` 행 구조**였다(제출사마다
  원본 조판 관행이 다름을 시사). `자산총계=107,638,242,656` /
  `부채총계=61,277,762,838` / `자본총계=46,360,479,818`로 R78이 원문대조로
  확정해둔 값과 정확히 일치, 항등식도 성립 — PDF에서 라벨이 숫자를 사이에 두고
  줄바꿈되던 R78 버그도 HTML에는 애초에 없다(고정폭 인쇄 컬럼이라는 개념 자체가
  없으므로).
- 결론: **이 경로는 표지 페이지에서만 실측했던 R76 진단("DART 자체 웹뷰어는
  멀쩡하다")이 재무제표 섹션에도 그대로 적용된다**는 것과, **KD류 밀림·R78류
  줄바꿈 두 버그 계열 모두 HTML에서는 구조적으로 재현 자체가 안 된다**는 것 —
  둘 다 이번에 실제 요청으로 확정됐다(짐작 아님).

**③ 기존 PDF 경로와의 관계**: 지금 `collector/pdf_lines_sync.py`는 HTML을
받아도 "이 모듈 범위 밖 — raw_bytes만 보존, 파싱 안 함"(77번째 줄 주석)이라고
명시돼 있다 — 즉 **파서 자체가 아직 없다**. 새로 만들어야 할 것:
  1. `dsaf001/main.do` 트리 파싱(위 ①) — "재무제표"/"연결재무제표" 등 목차명
     매칭 로직(보고서 유형·시대별로 목차명이 다를 수 있어 이 자체가 새로운
     정규식 유지보수 대상이 됨, PDF의 `_PERIOD_MARK_RE`류와 비슷한 성격의 부채).
  2. 두 가지 HTML 레이아웃(①KD류: 라벨/값 각각 거대한 단일 `<TD>`+`<BR/>` 분리,
     ②동성제약류: 정상 `<TR>` 행 구조)을 모두 처리하는 표 리더 — 기존
     `normalize_account_name`/계정 매퍼는 그대로 재사용 가능해 보이나(라벨
     텍스트 자체는 PDF와 동일한 한글 관행), 검증은 안 됨.
  3. 기간/컬럼 판별 — `<TH>` 헤더 행에 "제 28 기 반기"류 텍스트가 그대로 있어
     PDF보다 오히려 쉬워 보이지만, 지금 이 텍스트를 basis/period로 해석하는
     로직(`_PERIOD_MARK_RE` 등)도 새 표 구조에 맞게 다시 짜야 한다.
  → 즉 이건 "패치 하나"가 아니라 **새 추출 모듈 하나를 통째로 신설**하는 작업.
     완전 대체가 아니라 PDF와 나란히 두는 게 안전(이 프로젝트의 R78 설계 원칙 —
     "정상 동작하는 경로를 검증 없이 전면 교체하지 않는다"와 동일).

**아직 확인 안 한 것(생략, 착수 안내 아님)**: ⓐ 2개사·2건뿐이라 이 두 레이아웃
말고 제3의 레이아웃이 더 있을 가능성(전수는 아님) ⓑ dart3.xsd(신형) 시대
문서에서도 같은 방식이 통하는지(XBRL 있는 시대라 우선순위 낮음) ⓒ 서버 부하
(`WEB_INTERVAL=2.0초` 스로틀 기준 필링당 요청 2회 — 93건 규모는 수 분,
1999~2003년대 전체로 확장 시 수 시간 규모가 될 수 있음, 배치 잡으로는 무리
없어 보이나 실측은 안 함).

**결론 요약**: "검토 후보"는 **강하게 유효함이 실측으로 확인됨** — Track C
잔여 93건뿐 아니라, PDF 좌표기반 추출이라는 방식 자체가 갖는 R76/§4/R78류
구조적 결함군 전체를 이 경로가 원천적으로 우회한다. 다만 이번에도 **설계·구현은
아직 착수하지 않는다**(계획 후 대기 원칙 재확인) — 사용자가 다음 단계(설계
문서 작성 후 대기 vs 착수 지시)를 결정.
