## 1. D1 — `int(float())` 정밀도 손실 ★수정 완료

`parser/common/amount_normalizer.py:120` 이 모든 금액을 `int(float(s))` 로 파싱했다.
float64 유효자릿수는 15~17 자리라 **2^53(9,007,199,254,740,992) 초과 정수가 조용히 바뀐다.**

```
원문 TD 병합 '723,570,750 723,570,750'
  → 콤마·공백 제거 '723570750723570750'
  → int(float(...)) = 723,570,750,723,570,688   ← 원문에 없는 값
```

**DB 실측: `report_lines` 14,106 행 + `note_lines` 3,665 행 = 17,771 행이 9,007조원 초과.**
한국 최대 기업 총자산이 약 500조원이므로 전부 물리적으로 불가능한 값이다.

수정: 정수 문자열은 float 를 우회해 `int(s)` 로 정확히 파싱. 소수 표기(환율 `1,106.52`)는
종전 경로 유지. 회귀 20건 + `tests/test_units.py`·`test_checks.py` 12건 통과.

**⚠ 코드만 고쳤고 DB 는 아직 수정 전 값이다** — 전량 재추출·재적재 필요(→ §5).

## 4-3. 파서 강화 R1~R4 (구현 완료)

원문 XML 을 직접 열어보니 **병합은 우리 파싱 버그가 아니었다** — XML 은 깨져 있지 않고
제출인이 두 논리행을 한 행에 접어 넣은 것이다(단일 TD, 중첩 없음):

```xml
<TD WIDTH="135" ALIGN="RIGHT">723,570,750 723,570,750 </TD>   ← 값 2개가 한 칸
<TD WIDTH="199">현금시재액 요구불예금 </TD>                      ← 라벨도 2개가 한 칸
```

`parser/common/amount_normalizer.py`:

| | 규칙 | 근거 |
|---|---|---|
| R1 | 공백으로 갈린 **온전한 숫자가 2개 이상**이면 이어붙이지 않는다. 전부 동일값이면 하나로, 다르면 **거부** | 어느 값이 이 셀 것인지 원문이 말하지 않는다 |
| R2 | 후행 콤마 제거. 콤마 그룹이 깨져도 **값은 채택** | **단일 토큰의 콤마 오배치는 숫자열을 바꾸지 않는다** (`'92,31386,801'`→9,231,386,801 정상) |
| R3 | 타당성 상한 9×10^18 → **1경원** | 숫자열이 실제로 틀리는 건 두 숫자가 붙은 때뿐이고 그때는 자릿수가 폭발한다(`'316,305268,96147,344'`→3경) |
| R4 | 범위 표기(`~∼`) 거부 + `_TRAIL_DECOR_RE` 에서 `~` 제외 | `'2006.02~'`(임원 재직기간)이 2,006원으로 들어갔다 |

검증 36건(R1~R4 18 + 회귀 18: 괄호음수·△▲·전각공백·밑줄장식·배수적용·BLANK) 통과.
