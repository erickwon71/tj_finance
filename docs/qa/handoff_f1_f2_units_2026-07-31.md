## 4. ★사용자 결정이 필요한 것 4건 (재적재 전에)

### D1. 미선언 표의 단위 상속 — 약 **4.9M 셀**이 걸려 있다

원문 실측 서식:
```
<P> (1) … 범주별 금융상품의 내역은 다음과 같습니다.<당분기말>
<TABLE> (단위: 천원)      ← 선언만 담은 표
<TABLE> [자산 데이터표]    ← 단위 획득 O
<P> (빈 요소)
<TABLE> [부채 데이터표]    ← ★미선언으로 value_won 비게 됨(콤마금액 27~29 셀)
```
같은 선언 아래 **두 번째 데이터표부터** 단위를 잃는다. 미선언 데이터표 셀의 **53%** 가 이것이다.

| 안 | 내용 | 위험 |
|---|---|---|
| ① 현행 유지 | value_raw 만 보존 | 금액 4.9M 셀이 계층3 에서 못 쓰인다 |
| ② 항목 내 상속 | 항목 경계 안의 선언을 상속 | 헤더가 침묵하는 주식수 열이 ×1,000 |
| **③ 선언표 한정 상속(권고)** | **데이터 없는 '선언 전용 표'가 앞에 있을 때만** 상속 | 위 서식만 정확히 겨냥 |

### D2. `undetermined` 열을 어디까지 채울 것인가

혼합 선언 + 열 헤더가 침묵하면 지금은 NULL 이다(note 행의 1.0%). '당기/전기' 같은 **기간
표지를 금액 근거로 인정**하면 대부분 채워지지만, `'(단위: 주, 원)'` 주식선택권 표의 기초/기말
열이 주식수라 오염 위험이 있다. 현행은 **안 채우는 쪽**.

### D4. `_table_has_data_rows` 게이트 — **9.5M 셀**이 걸려 있다 (신규, census 로 발견)

"콤마 3자리 금액 데이터행 2 개 이상"을 요구하는 게이트가 **작지만 진짜인 표**를 버린다
(결손금 2셀·이자율 민감도 4셀·신용건전성 6셀). 전수 2,199,735 표 / 9,501,682 셀.

| 안 | 위험 |
|---|---|
| 현행 유지 | 9.5M 셀이 계속 DB 에 없다 |
| `minimum=1` 로 완화 | 표제표·stub 이 섞여 들어올 수 있다 → **완화한 채 표본 30건 원문 대조 후** 결정 |
| 판정축 변경(숫자 셀 수 기준 등) | 설계 필요 |

용량: +9.5M 행(현 스키마 ~3.5 GB · Phase 4 축소 후 ~1.2 GB).

### D3. 수주 진행률형(4.3%)·잔고 0 행(1.7%) 을 적재할 것인가

`수주총액 × (1 − 진행률/100)` 파생은 반올림 오차가 있고, 잔고 0 행은 값이 0 이지만
수주총액·기납품액은 실데이터다. 둘 다 **정보 대 신뢰도**의 문제라 사용자 판단이 맞다.

### ★ 정방향 도구가 아직 구 계약을 본다 (다음 세션에서 먼저 고칠 것)

`scripts/layer2_forward_cells.py:277` 이 주석 표를 아직 **`declared_unit(tb) is None → 폐기`**
로 센다. F1 이후 그 표들은 적재된다(`value_won` 만 비고 `value_raw` 는 채워진다). 그래서
지금 이 도구를 돌리면 **폐기 1,571 표 · 헤더행 오판 드롭 1,483 셀**(표본 60 filing) 같은
**낡은 숫자**가 나온다. 커버리지 94.969% 도 같은 이유로 과소평가다.

고칠 지점 두 곳:
1. 주석 스코프 판정 → `_table_has_data_rows` 만(단위 선언 조건 제거).
2. '방출' 의 정의 → 값이 채워진 셀과 **원문만 남은 셀(value_raw)** 을 나눠 센다.
   그래야 "전사는 됐지만 계층3 이 못 쓴다"를 유실과 구분할 수 있다.

참고: 지금 나오는 `헤더행 오판 드롭 1,483` 은 **본문 경로**다(F2 를 주석만 켰으므로 정상).

같은 이유로 계약이 어긋난 도구가 넷 더 있다(전부 `declared_unit(...) is None → 폐기`):

| 파일·줄 | 영향 |
|---|---|
| `scripts/layer2_forward_cells.py:277` | 커버리지·폐기 수치가 과소·과대 |
| `scripts/layer2_fidelity_full.py:135` | '표:폐기(단위 미선언)' 이 이제 폐기가 아니다 |
| `scripts/layer2_note_drop_audit.py:96` | 같은 이유 |
| `scripts/layer2_note_heading_fix_verify.py:86` | 같은 이유 |
| `fin2/audit/report_line_audit.py:106` | 본문 감사라 영향 작음(본문 계약은 그대로) |

census 판(`audit_unit_declarations.py`)과 `layer2_fidelity_full.py`(③ 주석 표 집계)는 이번에
새 계약으로 갱신했다 — 다른 도구를 고칠 때 그 `scan_filing()` 의 `loaded` 판정을 참고하면 된다.

### ★★재적재 전에는 '추출 ↔ DB' 비교가 어긋나는 것이 정상이다

`layer2_fidelity_full.py` 의 ② 적재 항목은 **추출기 출력과 현재 DB** 를 비교한다. 코드는
F1·F2 를 반영했고 DB 는 아직 구 포맷이므로, 지금 돌리면 표본 8 filing 에서
`누락 12,290 · 값불일치 111` 처럼 큰 수가 나온다. 이건 결함이 아니라 **아직 안 한 재적재**의
그림자다. 재적재 후에 다시 재서 `누락 0 · 값불일치 0` 을 확인하는 것이 순서다.
