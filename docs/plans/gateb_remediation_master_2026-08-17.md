### 순서 근거

- **③이 1순위인 이유**: 판정 로직 무변경 + 전수 동치성 증명이 게이트라 되돌릴 일이 없다.
  넣고 나면 "고칠 때마다 전수로 확인"이 1.1시간짜리 일상 작업이 된다 — 반복 루프를 끊는 도구.
- **2순위가 '전수 재감사'인 이유**: ①·②의 효과를 측정하려면 **깨끗한 기준선**이 필요하다.
  성능 수정과 판정 수정을 **같은 재감사 실행에 섞으면 원인 분리가 불가능**하다(③ §6-C).
- **P0가 4순위인 이유**: 잠복이라 급하지 않고, ②가 뷰의 `WHERE` 절을 다시 건드리므로
  DDL을 두 번 고치지 않으려면 ② 직전이 자연스럽다. **단 앱 가동 전에는 반드시 완료.**
- **②가 5순위인 이유**: 등급 체계(pass/fail_a/fail_b/pending) 자체를 바꾸는 유일한 트랙이라
  ①·③으로 모집단이 정리된 뒤에 설계해야 판단 근거가 깨끗하다.

## 2. 공통 게이트 (모든 트랙)

각 트랙은 아래를 통과해야 종료로 친다. 하나라도 미달이면 **집계로 끝내지 말고 원인 추적**
([[feedback-verify-against-source]], R9).

1. **회귀** — `pytest tests/ fin2/tests/` 549 기준선 유지
2. **fail_a 증가 0**
3. **단조성** — 기존 `pass` → `fail_*`/`pending` 전이 0건
4. **원문 대조** — 표본을 집계가 아니라 원문에서 손으로 확인
5. **문서** — `docs/PARSING_RULES.md` 등재(규칙 신설 시) + 본 문서 상태 갱신
6. **★전수 재감사** — 규칙·표준화를 바꾼 트랙은 **전수 재감사까지 해야 종료**다(§6 근거).
   표본 검증으로 닫으면 그 영향이 다음 전수 때 "신규 결함"으로 되돌아온다.
   **실행 전 기준선 스냅샷을 반드시 먼저 뜬다**(§6-C 에서 이걸 빠뜨려 A/B 로 우회해야 했다):
   `CREATE TABLE face_audit_snap_<날짜> AS SELECT * FROM face_audit WHERE source_version='v3';`

## 6. 전수 재감사 기준선 (2026-08-17, 5-shard)

**이것이 이후 모든 트랙의 비교 기준이다.** 이전 수치(오전 실측)는 4일치 패치워크라
기준선으로 쓰지 않는다.

```
감사 299,651행 (= std_v3 전량, 기업오류 0)
   pass    199,113  (66.5%)
   fail      3,493  →  fail_a 412 · fail_b 3,081
   pending  97,045  (32.4%)
   in-scope 일치율  97.7 ~ 99.0% (shard별)
```

### 오전 패치워크 대비 변화와 그 원인

| | 오전(패치워크) | 전수 재감사 | 차이 |
|---|---|---|---|
| pass | 197,097 | 199,113 | **+2,016** |
| fail_a | 394 | 412 | +18 |
| fail_b | 2,954 | 3,081 | +127 |
| pending | 99,206 | 97,045 | **−2,161** |

**원인 = ③이 아니라 std_v3 재빌드 시점 불일치.** 실측:

```
std_v3 built_at :  08-17  99,587행 · 08-16  42,234행 · 08-15 1,614행 · 08-14 156,216행
기존 face_audit :  08-14  209,261행  ← 이 시점 std_v3 로 판정된 채 방치
```

R29(08-16)·R30(08-16)·R31(08-17)의 백필로 **약 143,000행의 std_v3 가 감사 이후에 바뀌었는데
재감사가 안 된 상태**였다. cogs 실패 257건 중 181건(70%)이 08-16/17 재빌드 행이다.

필드별 실제 변화(오전 상위 30 안에 있어 비교 가능한 것만):

```
cogs            fail_b  155 → 257  (+102)   ← 최대
trade_payables  fail_a   20 →  41  (+21)
controlling_ni  fail_b  118 → 137  (+19) / fail_a 27 → 23 (−4)
그 외           +2 ~ +4 수준
revenue         186/2516 → 186/2516  (변화 0)   ← ③ 무영향의 방증
tax_expense      82/33   →  82/33    (변화 0)
```

> `revenue` 는 최대 모집단이자 텍스트 리더 의존도가 가장 높은 필드인데 **한 행도 안 움직였다.**
> ③이 리더 동작을 바꿨다면 여기가 먼저 움직였을 것이다.

### ★ 이 기준선이 말해주는 것

**"전수 재감사를 안 돌리면 규칙 수정의 실제 효과를 아무도 모른다"** 가 수치로 확인됐다.
R29~R31 은 08-16/17 에 종료 처리됐지만, 그 영향으로 새로 생긴 fail 149건(cogs +102 등)은
**오늘 전수를 돌리기 전까지 face_audit 어디에도 없었다.** 이것이 반복 루프의 실제 메커니즘이다.
→ 앞으로 규칙 수정 트랙은 **종료 조건에 전수 재감사를 포함**한다(§2 공통 게이트에 추가).
