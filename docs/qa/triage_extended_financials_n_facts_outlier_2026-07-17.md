# extended_financials n_facts_outlier 트리아지 — 문제 사례 상세 (2026-07-17)

## 배경

`scripts/dq_assertions.py`의 `extended_financials_n_facts_outlier` 어서션이 원래
149,672건 위반을 검출. `extended_financials` 뷰는 (기업·연도·기준·캐노니컬계정) 단위로
`fact_v2`의 여러 행을 `SUM`해서 하나의 값으로 보여주는데, 정상은 리프 2~3개 합산인데
n_facts(합산된 행 수)가 5개를 초과하면 "동일 캐노니컬에 무관한 라인이 섞여 합산 오염됐을
신호"로 플래그한다.

1차 조치(이미 반영·커밋됨, `19bac3b`):
- 설계상 원래 다항목 집계용인 17개 캐노니컬(`_detail`/`other_*`/`oci`/`cogs`/`capex` 등)을
  어서션에서 제외 → 149,672 → 10,770
- `SUM` → `SUM(DISTINCT)`로 변경(완전 동일 금액의 중복 등장을 1회로 접음) → 10,770 → 9,044

잔여 9,044건 중 `cf.available_for_sale_net`(매도가능금융자산 순증감) 계정이 6,932건으로
최대 비중을 차지해 이 계정을 표본으로 원문(raw XML)·fact_v2를 직접 대조했다. 아래는 그
과정에서 확인한 **구체적 문제 사례**다. 회사명·보고서·항목명을 원문 대조가 가능하도록
정리했다.

**결론(요약)**: 원인이 단일하지 않다 — 최소 3가지 서로 다른 결함 패턴이 섞여 있어
일반화된 단일 해법(예: FactV2 스키마 확장+전수 백필)은 투자 대비 효과가 낮다고 판단됨
(별도 진단: `is_subtotal` 라벨 매칭 적용 시에도 잔여의 94%가 그대로 남음, 아래 §5 참고).

## 1. 사례 A — 표 간 완전 동일값 중복 (AUTOSUM 셀 포함)

| 항목 | 내용 |
|---|---|
| **기업명** | 메가스터디(072870) |
| **corp_code** | 00422284 |
| **보고서** | 2018 사업보고서(annual), rcept_no `20190401004405` |
| **재무제표 구분** | 별도(separate), 현금흐름표(CF) |
| **문제 계정** | `cf.available_for_sale_net` (매도가능금융자산 순증감) |
| **당시 n_facts** | 41개 리프가 하나로 합산됨 |

**구체적 문제**: 23,522,546원이라는 값이 **원문 안에서 4곳**에서 발견됨:
1. 한 주석 표의 "합 계" 행 — `AUTOSUM="COLALL"`(열 합계, DART XML 자동합계 속성)
2. 증감명세 표에서 같은 행의 `AUTOSUM="ROWALL"`(행 합계) 셀
3. 같은 표의 본 데이터 셀(위 2번 값의 원천)
4. 라벨이 하이픈/언더스코어만 다른 별도 표: "당기손익-공정가치측정 금융자산(유동)" vs
   "당기손익_공정가치측정금융자산(유동)"

**즉**: 실제로는 하나의 사실(23,522,546원)인데, DART 보고서 자체가 이 숫자를 요약표·
증감명세표·라벨변형표 등 여러 곳에 반복 게재하고, 우리 추출기(Track B 텍스트 파서)가
그걸 각각 별개 사실로 잡아 41개까지 부풀림. 표본 전체로는 이런 중복 패턴이 7개 값
그룹(9개 초과행)에서 발견됐고, 실제 합계 83억원 대비 약 5천만원(0.6%) 과다계상.

→ **이미 SUM(DISTINCT) 수정으로 완전 동일값 중복은 해소됨.**

## 2. 사례 B — 다른 표(재무상태표 분류주석)의 오염

| 항목 | 내용 |
|---|---|
| **기업명** | DB손해보험(005830) |
| **corp_code** | 00159102 |
| **보고서** | 2023 반기보고서(half), rcept_no `20240221002000` |
| **재무제표 구분** | 연결(consolidated), 현금흐름표(CF) |
| **문제 계정** | `cf.available_for_sale_net` |
| **당시 n_facts** | 33개 |

**구체적 문제**: 33개 항목 중 압도적으로 큰 값 2개가 이질적:

| 라벨(원문) | 금액 |
|---|---|
| `4. 기타포괄손익-공정가치측정금융자산,22,32,42,44>` | 18,146,885,740,325원(18.1조) |
| `2. 당기손익-공정가치측정금융자산,32,42,44>` | 10,770,905,079,283원(10.7조) |

라벨 형태가 **"번호. 계정명,주석번호,주석번호,주석번호>"** 인데, 이건 현금흐름표의
취득/처분 라인이 아니라 **재무상태표 금융자산 분류표(주석) — "구분 1/2/3/4" 항목별
장부금액 + 관련 주석 인덱스**로 보인다(현금흐름표 취득/처분 라인이라기엔 값이 압도적으로
크고, 라벨에 "취득"/"처분" 같은 동사가 없음). 즉 **완전히 다른 표(BS 주석)의 합계 행이
계정명 문자열 유사성만으로 CF 캐노니컬에 잘못 흡수**된 것으로 보인다. 이 두 값만 합쳐도
약 29조원 — 실제 현금흐름 순증감보다 훨씬 큰 이질적 오염.

→ **아직 미해결.** SUM(DISTINCT)로도 안 잡힘(값 자체가 유일해서). "숫자.+계정명+콤마
주석번호목록>" 형태 라벨을 인식해 제외하는 별도 필터가 필요할 것으로 보이나, 이 패턴이
전체 9,044건 중 얼마나 되는지는 미측정.

## 4. 사례 D — 라벨 파편화/줄바꿈 오염 (별도 유형, 미해결)

| 항목 | 내용 |
|---|---|
| **기업명** | 유안타증권(003470) |
| **corp_code** | 00117601 |
| **보고서** | 2020 사업보고서(annual), rcept_no `20210318000778` |
| **재무제표 구분** | 연결(consolidated), 현금흐름표(CF) |
| **문제 계정** | `cf.available_for_sale_net` |
| **당시 n_facts** | 19개 |

**구체적 문제**: 라벨 다수가 **원문 셀 안에서 줄바꿈된 텍스트가 그대로 이어붙어** 저장됨.
예:
```
"당기손익-공정가치\n측정\n금융자산평가손실"   → 32,787,723,000원
"기타당기손익-공정가치측정\n금융자산"          → -4,967,144,000원
"당기손익-공정가치\n측정\n복합금융자산평가이익" → -7,773,126,000원
```
"기타당기손익"처럼 문법적으로 이상한 라벨도 보이는데, 표 헤더(구분/기타포괄손익 등)가
셀 병합(rowspan/colspan) 구조에서 하위 라벨과 잘못 이어붙었을 가능성. 사례 A~C와 달리
이건 **단순 중복이 아니라 라벨 자체의 추출 품질 문제**로, 각 라벨이 실제로 서로 다른
항목을 가리키는지 원문 표를 직접 봐야 판단 가능. 값 자체의 중복은 육안상 뚜렷하지 않음.

→ **미해결, 원인 미확정.** 원문 표(증권사 6-column 형식 특유의 병합 헤더 구조)를 직접
대조해야 정확한 진단 가능.

## 5. 별도 진단 — "합계 우선 채택" 전략의 실효성

`_is_subtotal()`(합계/소계/총계 라벨 판정, 기존 코드 재사용)을 잔여 9,044건에 시뮬레이션
적용한 결과:
- is_subtotal 후보가 존재하는 그룹: 595/9,044 (6.6%)
- 적용 시 아웃라이어에서 실제로 빠지는 그룹: 542/9,044 (6.0%)
- **잔여 8,502건(94%) 그대로 남음**

→ 사례 A/C(완전 동일값 중복)는 이미 해결됨, 사례 B/D 같은 "다른 표 오염"·"라벨 파편화"
유형은 합계 라벨 매칭으로 커버 안 됨. 일반화된 해법보다 **패턴별 개별 대응**이 필요.

**연도 분포**: 잔여 8,502건의 78%(6,623건)가 2018~2024년에 집중(2018년 K-IFRS 1109 금융상품
기준 의무 도입 시점과 일치). 다만 사례 B·C를 보면 신구 분류 혼재가 항상 "중복"은 아니고
(사례 B는 진짜 서로 다른 상품군이 정당하게 공존), 오염 유형이 회사·표 구조마다 다르게
나타나 단일 규칙으로는 못 잡는다.

## 참고 — 조회에 사용한 쿼리 패턴

```sql
-- 특정 rcept의 특정 캐노니컬 계정 원본 팩트 나열
SELECT f.basis, f.source_ref, f.amount_won
FROM fact_v2 f
WHERE f.corp_code = '<corp_code>' AND f.rcept_no = '<rcept_no>'
  AND f.canonical_account = 'cf.available_for_sale_net'
  AND f.col_index = 0 AND NOT f.is_dimensional
ORDER BY f.basis, f.amount_won DESC;
```

원문 XML 위치: `raw_report/{KOSPI|KOSDAQ}/{corp_code}_{회사명}/{annual|half|quarter}/{연도}/{rcept_no}.xml`
(EUC-KR 인코딩)
