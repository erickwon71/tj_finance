## 원문 레이아웃 상세 (00163691 rcept 20010515000229 실측)

### BS/IS — 3줄 패턴 (양쪽 basis 공통)

```
Ⅰ. 유동자산
(971,735,843,010) (851,037,426,728) (829,774,727,588) (877,348,077,730)
(Current Assets)
(1)당좌자산
931,031,052,669 (814,763,588,627) (790,177,224,403) (845,723,858,038)
(Quick Assets)
1. 현금및현금 등가물 (주석 2, 3)
436,850,563,946 232,352,148,393 361,393,258,902 172,265,707,747
(Cash and Cash Equivalents)
```

- **1줄째**: 한글 라벨(각주 참조 "(주석 2, 3)" 등이 붙기도 함) — 숫자 없음.
- **2줄째**: 해당 기간 수만큼 숫자가 공백으로 나열(이 필링은 4기간: 당기분기·전기분기·
  당기연간·전기연간). **로마숫자/괄호번호 헤더 행(소계 미리보기)의 괄호 유무가
  일관되지 않다** — 위 예시에서 "Ⅰ. 유동자산"의 4개 값이 전부 괄호로 싸였는데,
  바로 다음 "(1)당좌자산" 행은 **첫 번째 값만 괄호가 없고 나머지 3개는 괄호**다. 기존
  `_SUBTOTAL_HEADER_RE`(§R73/R74, `fin2/extract/pdf.py:58`)가 "헤더+단일 괄호값"만
  다루므로 이 다중-괄호-다중값 패턴은 새로 설계해야 한다 — 아마 "헤더 행이면 그 줄의
  모든 토큰에서 괄호를 벗겨 파싱"(단일값 가정을 버림)이 맞을 것이다(원문대조로 재확정할 것).
- **3줄째**: 영문 번역 — 한글이 전혀 없어 기존 `_HANGUL_RE.search(line)` 필터에
  **자동으로 걸러진다**(별도 처리 불요, 이미 공짜로 스킵됨).
- 순수 섹션 헤더(예 "자 산\n(Assets)")는 라벨줄 다음이 숫자줄이 아니라 바로 영문줄 —
  2줄짜리 예외로 처리해야 한다(숫자줄 없으면 데이터 아님, 라벨만 스킵).
- **페이지 푸터 잡음**: "전자공시시스템 dart.fss.or.kr Page 66" 같은 줄이 항목 중간에
  섞여 들어온다(한글 "전자공시시스템"이 있어 `_HANGUL_RE`를 통과 — 라벨로 오인될
  위험). 고정 패턴이라 정규식으로 걸러내는 전처리가 필요.
- **기간 열 중 일부가 결측("-")인 경우** — 00124799 FY2000 원문대조([[report_lines_
  sanemax_reject_compaction_shift_design_2026-09-06]] 같은 세션, 별개 결론:
  "제30기 별도 보고" = 원문 자체가 연결 당기 결측)에서 확인했듯, 이 시대 문서는 당기
  컬럼을 "-"(대시)로 비우는 경우가 실제로 있다. **`_NUM_TOKEN_RE`는 숫자가 최소
  1개 있어야 매치**하므로 "-"는 토큰으로 안 잡힌다 — 즉 한 줄에 기대한 4개보다 적은
  수의 숫자만 파싱될 수 있다. **오늘 R74에서 고친 것과 완전히 같은 종류의 함정**이다:
  "몇 번째 열이 비었는지" 확인 안 하고 "왼쪽부터 순서대로 채운다"고 가정하면, 전기값이
  당기 열로 밀려 들어가는 컬럼압축 버그가 다시 생긴다. **반드시 처음부터 열-위치를
  보존한 채 파싱**(토큰과 그 열 인덱스를 함께 기록, 빈 칸은 결측으로 유지)할 것 — 이번엔
  나중에 발견해서 패치하는 게 아니라 설계 단계에서 막을 것.

### CF — 다른 레이아웃(2단 페이지, 이번 트랙 범위 밖이지만 기록)

```
과 목 제 63 기 제 62 기 과 목 제 61 기
Ⅰ. 영업활동으로 인한 현금흐름 636,652,862,818 308,881,234,962 Ⅰ. 영업활동으로 인한 현금흐름 93,068,410,318
1. 당기순이익 (74,460,475,515) 36,798,418,434 1. 당기순이익 22,015,896,088
```

한 물리 줄에 "제63/62기" 블록과 "제61기" 블록이 **좌우로 나란히** 찍힌다(페이지가
2단 레이아웃). 라벨+숫자가 한 줄에 있어 지금 파서가 우연히 그럭저럭 뽑아내지만,
좌/우 블록의 라벨이 같은 항목이라 잘못 병합될 위험은 있다(이번 census는 CF 행수만
보고 "정상"으로 간주했을 뿐, CF 값 자체의 정확성은 검증하지 않았다 — **구현 착수 전
CF도 표본 몇 건 값 대조로 재확인할 것**, 특히 좌/우 블록 라벨 충돌 여부).

## 근본원인 (코드 위치)

`fin2/extract/pdf.py::_iter_data_lines()`(약 161행) — 한 줄 안에서 `_HANGUL_RE`로
라벨을, `_NUM_TOKEN_RE`로 숫자를 **같은 줄에서** 찾는다. 라벨 줄에 숫자가 없으면
`nums_iter`가 비어 그 줄 자체가 버려지고(계속 진행), 숫자만 있는 줄은애초에
`_HANGUL_RE.search(line)`이 실패해 라벨 없이도 스킵된다 — 결과적으로 3줄 분리
레이아웃에서는 라벨과 숫자가 **영원히 만나지 못한다**.

## 구현 방향 (다음 세션 시작점 — 미확정, 논의/검증 대상)

1. **탐지 게이트를 먼저 만든다** — 이 3줄 레이아웃은 문서/표별로 갈릴 수 있으므로
   (오늘 section_def 반례 교훈: "증상이 같다고 정답도 같지 않다"), `_iter_data_lines`를
   **전면 교체하지 말고**, 해당 리전이 3줄 패턴인지 먼저 판별하는 함수를 앞에 둔다
   (예: 연속 N줄 표본에서 "한글줄 다음 숫자만줄" 비율이 임계치 이상이면 3줄 모드로
   전환, 아니면 기존 단일줄 로직 그대로 — 기존에 이미 잘 동작하는 대다수 필링을
   건드리지 않는 게 최우선).
2. 3줄 모드에서: 페이지 푸터 정규식 사전 필터 → (한글라벨, 숫자만줄) 페어 lookahead로
   묶기 → 헤더행(소계 미리보기, `_SUBTOTAL_HEADER_RE`) 판정을 **다중값 버전**으로
   확장 → 각 숫자를 **열 위치 보존**한 채 파싱(빈 칸은 결측 유지, 절대 왼쪽 채움 금지) →
   기존 "BS=col0(당기)" 관례에 맞춰 열 0을 당기로 매핑(단, 열 0이 결측이면 통째로
   결측 처리 — 다른 열 값을 대신 쓰지 않는다).
3. IS의 interim(3개월/누적) 2단 헤더가 이 3줄 레이아웃과 만나는 경우가 있는지 별도 확인
   (있다면 기존 `cum_map` 열 선택 로직과 어떻게 맞물리는지 재검토 필요 — 오늘 R74가
   고친 cum_map 오작동과 같은 함정이 재현될 소지가 있다).
4. CF의 2단-페이지 레이아웃은 **이번 트랙 범위에서 제외**(census가 CF는 "정상"으로
   판정했으나 값 정확성은 미검증 — 구현 착수 전 표본 재확인만 하고, 문제 있으면 별도
   트랙으로 분리).

  현재 수동 스크립트/특정 corp 리스트 기반인지, 자동 신규 필링에도 타는지 — 코드
