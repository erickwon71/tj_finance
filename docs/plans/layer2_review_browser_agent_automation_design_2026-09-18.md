# 계층2 원문대조 캠페인 — 브라우저 에이전트 자동화 설계 (2026-09-18)

★이 문서는 설계안이다. CLAUDE.md 정책대로 **여기서 실행을 시작하지 않는다** — 사용자가
검토 후 별도로 "시작해"라고 하면 그때 착수한다.

## 0. 배경 / 목적

기존 계층2 재적재+원문대조 캠페인(`scripts/layer2_review.py`, 2026-09-08 설계)은
"재적재 → 검산 → CSV 생성 → **사람이 DART 화면과 CSV를 눈으로 대조** → pass/fail"
구조다. 지금까지 2015+ 큐(106,448건 중 101건만 pass)는 이 사람 대조 단계 때문에
거의 진행되지 못했다.

이번 요청: 그 "눈으로 대조" 단계를 브라우저 자동화 에이전트로 대체해 2015+ 전체
큐를 규모 있게(수일~그 이상 걸려도) 돌린다. 단, 반드시 지켜야 할 조건(사용자 명시):

1. **눈으로 확인한 것과 같은 효과** — 파서 코드를 다시 호출해서 "확인"하면 안 된다
   (순환검증, 이번 세션 R138에서 확인한 함정과 같은 종류). DART가 렌더링한 화면을
   실제로 읽고 비교해야 한다.
2. **확인된 것은 재적재에서 제외** — 이미 `layer2_review.py pass`가 하던 일
   (`layer2_review_queue.status='pass'`)을 그대로 쓰되, 이번 세션에 R139로
   이 표시가 **모든** 재적재 경로에서 실제로 강제되도록 고쳤다(완료, 커밋
   `3145b34`). 새 캠페인은 이 인프라를 그대로 재사용하면 된다 — 추가 구현 불필요.
3. **문제 발생 즉시 수정 금지** — 확정 실패(fail) ~10건이 쌓이면 그때 한 번에
   원인규명+파서수정+재적재+재확인한다. 이유: 파서를 고칠 때마다 매번 대규모
   재적재를 돌리면 그 대기시간이 누적돼 캠페인 전체 시간을 잡아먹는다.

## 1. 기존 인프라 (그대로 재사용)

- `collector.models.Layer2ReviewQueue` — 큐 테이블. 2015+ 현재 상태(2026-09-18
  실측): `pending 106,448 / pass 101 / reloaded 1`. 순서는
  `era_rank(2015+ 우선) → corp_rank(시총 큰 순) → screen_severity(사전 스크리닝
  심각도 큰 순) → seq_in_corp`.
- `scripts/layer2_review.py next` — 다음 1건을 실제 파서로 재적재
  (`extract_report_lines` → `store_report_lines`/`store_report_tables`) +
  자동검산(`fin2/audit/layer2_selfcheck.py`) + 대조용 CSV 생성
  (`fin2/extract/review_csv.py`) + DART 뷰어 링크 출력.
- `scripts/layer2_review.py pass|fail --note ...` — 사람 판정을 큐에 기록.
  `pass`는 자동으로 `next`까지 이어간다.
- **R139(이번 세션에 완료)**: `pass`로 확정되면 `store_report_lines()`가
  이제 이 rcept를 재적재로부터 자동 보호한다 — 어느 스크립트가 나중에 그
  rcept를 다시 건드리려 해도 명시적으로 `overwrite_reviewed=True`를 주지
  않는 한 거부된다.

## 2. 무엇을 새로 만드는가 — "사람이 보던 자리"를 에이전트가 대신

핵심 아이디어: **CLI 자체는 안 바꾼다.** 기존 `next`가 만들어주는 CSV와 DART 링크를
그대로 쓰되, 지금까지 사람이 하던 "DART 링크를 열어서 화면을 보고 CSV와 대조" 단계를
에이전트(나)가 Claude-in-Chrome 브라우저 도구로 수행한다.

한 건 처리 루프(의사코드, 실제로는 내가 Bash+브라우저 도구를 직접 순서대로 호출):

```
python scripts/layer2_review.py next   # → CSV 경로 + DART 링크 출력
```
```
navigate(DART 링크)
```
```
(DART 뷰어에서 "재무제표" 문서 선택 → BS/IS/CF/SCE 렌더된 표를 읽는다)
```
```
CSV(=DB 적재값)의 항목별 금액과 화면에서 읽은 금액을 항목명 기준으로 대조
```
```
일치 → python scripts/layer2_review.py pass
불일치 → python scripts/layer2_review.py fail --note "무엇이 어떻게 다른지"
        (멈추지 않고 바로 다음 next로 진행 — §3 배치 규칙)
```

**독립성이 성립하는 이유**: 화면에서 읽는 값은 DART가 원문을 렌더링한 결과이지,
이 프로젝트의 파서(`table_extractor.py`/`report_lines.py` 등)를 거치지 않는다.
따라서 이 프로젝트 파서에 있는 버그가 "검증"에서도 똑같이 재현되는 순환검증
문제가 없다 — 이게 국지적 원문대조(현대해상 표본 등)를 사람이 직접 XML을
열어 읽었던 것과 같은 성격이다.

## 3. 배치 워크플로 (즉시수정 금지)

- 정상 진행 중에는 `fail`이 나와도 **루프를 세우지 않는다** — `fail --note`로
  기록만 하고 바로 다음 `next`로 넘어간다. (참고: 현재 `cmd_fail`의 독스트링에
  "루프를 세운다"고 돼 있는 건 2026-09-08 **사람 워크플로** 전제였다. 코드
  자체는 세션/스크립트를 강제로 멈추지 않는다 — `fail` 이후 바로 `next`를
  다시 부르면 정상 진행된다. 즉 이 부분은 **코드 변경이 필요 없고, 내가
  "fail 나와도 계속 진행"하는 운영 절차만 지키면 된다.**)
- 확정 `fail`이 **10건 정도** 쌓이면: 진행을 멈추고 그 10건을 놓고
  ① 원인 규명(`verify_report_lines.py`/`layer2_fidelity_roundtrip.py`/
  `layer2_forward_cells.py`/`audit_unit_declarations.py` — 이미 `_print_triage`가
  안내하는 그 스크립트들 그대로) → ② 파서 수정(필요 시) → ③ 그 10건만
  `redo`로 재적재 → ④ 다시 브라우저로 대조해 `pass` 확정 → ⑤ 메인 루프 재개.
- 파서를 고친 경우, "이 수정이 다른 이미 `pass`된 필링을 깨뜨리지 않는지"는
  **R139 가드가 자동으로 막아준다** — `pass`된 rcept는 그 수정의 일괄 재적재
  스크립트가 실수로 건드려도 거부된다. 단, 그 수정이 **아직 큐를 안 지나간
  나머지 pending 건**에는 자연스럽게 반영된다(다음에 그 필링을 `next`로
  만날 때 새 파서로 재적재되므로).

## 4. 갭 — 추가로 손봐야 하는 것

1. **SCE가 검토 CSV/스코프에서 빠져 있다.** `fin2/extract/review_csv.py`의
   `SCOPE_ORDER`는 주석에 "본문 3종만(사용자 범위)"라고 명시돼 있고 실제로
   `BS/IS/CF`만 있다(2026-09-08 당시 사용자가 정한 범위). 이번 요청은
   "bs is cf **sce**"까지 대조하라는 것이므로, `SCOPE_ORDER`에
   `("separate", "SCE")`/`("consolidated", "SCE")`를 추가하고 CSV에 SCE
   섹션이 나오게 고쳐야 한다. (작은 변경 — 이 설계 승인 시 먼저 처리)
2. **DART_VIEWER 링크(`dsaf001/main.do?rcpNo=...`)는 "문서 목록" 페이지다.**
   재무제표 본문까지 가려면 그 페이지 안에서 "재무제표" 첨부문서를 찾아
   클릭(또는 좌측 문서선택 트리 탐색)해야 한다 — 단순히 링크 하나 열어서
   텍스트를 긁으면 끝나는 게 아니다. 실제 DART 뷰어 DOM 구조(iframe 안에
   문서가 로드되는 방식 등)를 몇 건 직접 열어보고 확인하는 **작은 사전
   조사(스파이크)**가 필요하다 — 이건 설계보다는 실행 초기 1~2건으로
   바로 확인 가능.
3. **비교 판정 기준**: 사람은 "숫자가 같아 보이면 pass"로 유연하게 판단하지만
   에이전트는 명확한 규칙이 있어야 한다. 제안: 항목명(라벨)을 원문 그대로
   기준으로 매칭하고, 금액은 CSV의 "금액" 칸(표시 그대로, 콤마 제거 후)과
   화면 값이 **글자 그대로 일치**해야 pass. 라벨을 못 찾거나 금액이
   다르면 무조건 fail(추측성 "비슷하니 통과" 금지 — R6 원칙).

## 5. 규모/현실성 — 반드시 짚어야 하는 문제

2015+ 큐는 **106,448건 pending**이다(2026-09-18 실측, 위 §1). "수일이 걸려도
좋다"는 사용자 지침을 그대로 받아들이기 전에, 실제 처리량을 짚어야 한다.

- 건당 처리에는 최소 (1) `next` 실행, (2) DART 페이지 내비게이션+로딩,
  (3) 문서 트리에서 재무제표 찾아 클릭, (4) 화면 텍스트/표 읽기, (5) CSV와
  대조하는 추론, (6) `pass`/`fail` 호출이 들어간다 — 도구 호출만 여러 번,
  가장 낙관적으로 잡아도 건당 30초~1분대.
- 106,448건 × 30~60초 = **887~1,775시간 = 약 37~74일**, 이것도 **쉬지 않고
  연속으로 돌렸을 때** 얘기다. 브라우저 자동화는 활성 Chrome 세션(확장 프로그램
  연결)이 있어야 동작하므로, 이 세션이 며칠씩 무인으로 계속 돌아가는 구조가
  아니다 — 사용자가 컴퓨터/Chrome을 켜두고 있는 동안, 세션을 이어가며
  나눠서 처리하는 형태가 현실적이다.
- 토큰 비용도 무시 못 한다. DART 재무제표 페이지는 표가 많아 건당 읽기+비교에
  최소 수천 토큰이 든다고 보면, 106,448건 전체를 다 돌리는 데 필요한 총
  토큰은 이번 세션류의 예산(십수M 토큰) 여러 배(수십~수백 배) 규모다 — 즉
  **한 세션은커녕 며칠의 세션 몇 개로 끝날 규모가 아니다.**

★결론: "전체 106,448건을 수일 내로 다 본다"는 기대는 실제 처리량과 안 맞을
가능성이 크다. 아래 중 어느 쪽으로 기대치를 맞출지 확인이 필요하다:

- **(A) 그래도 전체를 목표로 하되, "수일"이 아니라 "여러 세션에 걸쳐 꾸준히"로
  기간 기대를 재설정한다.** 큐의 기존 우선순위(시총순×심각도순)를 그대로 써서
  중요한/의심스러운 것부터 먼저 끝난다 — 중간에 멈춰도 그때까지의 성과는
  남는다(R139 보호 덕분에 되돌아갈 일도 없다).
- **(B) 1차로 `screen_severity > 0`인 27,136건(사전 스크리닝이 이미 뭔가
  걸린 것들)부터 끝낸다.** 나머지 79,312건(`severity=0`, 스크리닝 무결점)은
  상대적으로 위험이 낮다고 보고 뒤로 미룬다. 규모가 1/4로 줄어 그래도
  수주 단위지만 (A)보다는 현실적이다.
- **(C) 브라우저 단계 전에 더 싼 자동 스크리닝을 강화해서(항등식 검산
  등, 이미 있는 `layer2_selfcheck.py` 체크를 확장) 의심 신호가 있는
  건만 브라우저로 정밀 확인한다.** 가장 빠르지만, "전체에 대해 눈으로
  확인한 것과 같은 효과"라는 원 요구사항과는 살짝 어긋난다(정말 모든
  건을 브라우저로 보는 게 아니게 됨).

## 6. 결정 사항 (사용자, 2026-09-18)

1. **규모** — (B)로 진행: `screen_severity>0`(2015+ 실측 27,136건)부터 먼저
   끝낸다. 이유(사용자): "파서 수정 건이 나올 수 있을 것 같아서" — 스크리닝이
   이미 뭔가 걸어놓은 쪽에 진짜 결함이 몰려 있을 가능성이 높다. **(B) 이후
   이어서 결국 전체(나머지 `severity=0` 80,369건)도 한 번은 돈다** — (B)가
   전체를 대체하는 게 아니라 우선순위일 뿐. **구현 완료**(R140):
   `scripts/layer2_review.py next/pass --min-severity 1`로 단계(B)만 먼저
   처리하고, 다 끝나면 `--min-severity`를 빼고(또는 `0`) 이어가면 된다.
2. **SCE 포함** — 확정, **구현 완료**(R140): `review_csv.py`가 이제
   BS→IS→CF→SCE 순으로 CSV를 만든다.
3. 배치 크기(확정 fail ~10건)는 §3 그대로 — 별다른 이견 없었음, 실행하며
   필요시 조정.
4. DART 뷰어 내비게이션 방식은 여전히 실행 시작 시 1~2건으로 직접 확인 후
   확정(정보 부족 — 지금 결정할 필요 없음).
