### 2-B. 정답 후보가 애초에 `report_lines`에 없다

`report_lines`에서 이 4개 필링의 IS 본문(`table_seq=0`)을 row_order 순으로 훑으면
(2025H1 예시):

```
row_order=12  당기순이익(손실)          734,801,150   ← 총계(정답, 그대로 살아있음)
             [13/14/15 없음 — "당기순이익(손실)의 귀속"/"지배주주당기순이익(손실)"/
              "비지배주주당기순이익" 행이 통째로 빠져 있다]
row_order=16  기타포괄손익 …
row_order=21  총포괄손익
row_order=23  포괄손익의 귀속 > 지배기업 소유주지분   -814,019,040   ← 이것만 살아남음(CI, 오답)
row_order=24  포괄손익의 귀속 > 비지배지분            -545,011,853
[row_order 없음] 주당손익 > 지배주주당기순이익(손실)   839,946,324   ← EPS 경로로 잘못 들어옴
[row_order 없음] 주당손익 > 비지배주주당기순이익       -16,932,469
```

즉 IS 본문의 진짜 "당기순이익(손실)의 귀속" 행(정답, 404,008,384)은 **`report_lines`에
아예 없다** — combine.py가 아무리 잘 골라도 애초에 후보 풀에 없으면 못 고른다. R24/R25가
쓰는 "후보를 넓히기만 한다" 전략(구조기반 후보보강)도 여기선 안 통한다 — 넓힐 후보
자체가 소스에 없다. `_resolve_ni_attribution`의 항등식 안전망(controlling+noncontrolling
=net_income)도 살아있는 두 후보(CI쌍 vs EPS쌍)가 **둘 다 오답**이라 어느 쌍도
net_income(734,801,150)과 안 맞아 통과 못 시키고, 결국 스테이지 랭크 tie-break로
아무 오답이나 `confirmed`로 승격된다.

### 2-C. 원문 추적 — 왜 정답 행이 `report_lines`에서 빠지는가

원문(`20250813001066.xml`)의 IS 본문 표(정상적인 4열 구조 — "제N기 반기: 3개월|누적,
제N-1기 반기: 3개월|누적", ROWSPAN/COLSPAN 함정 없음, 완전히 clean한 표)에서 해당 행:

```xml
<TE>　지배주주당기순이익(손실)</TE>
<TE ACODE="ifrs-full_ProfitLossAttributableToOwnersOfParent" ACONTEXT="...dHYQ...">839,946,324</TE>
<TE ACODE="ifrs-full_ProfitLossAttributableToOwnersOfParent" ACONTEXT="...dHYA...">404,008,384</TE>
<TE ACODE="ifrs-full_ProfitLossAttributableToOwnersOfParent" ACONTEXT="...PFY...dHYQ...">2,587,307,501</TE>
<TE ACODE="ifrs-full_ProfitLossAttributableToOwnersOfParent" ACONTEXT="...PFY...dHYA...">1,744,628,069</TE>
```

`fin2/extract/report_lines.py`:


"**지배주주당기순이익(손실)**"이라는 라벨은 EPS(주당손익) 라벨이 아니다 — "지배" +
"주주"(주주들) + "당기순이익"(당기순이익)의 조합인데, 우연히 "주"+"주"+"당" 3글자가
이어지며 "주당" 부분문자열을 만든다. ②에서 본류 추출이 스킵되고, ③에서 EPS 전용
패스가 이걸 주워가는데, ④"당기/전기 2열" 가정만 있어 실제 4열(3개월/누적×당기/전기)
중 **앞의 두 칸**(3개월-당기=839,946,324, 누적-당기=404,008,384)을 col_idx=0,1로
저장하고, ⑤블랭킷 규칙으로 둘 다 `is_cumulative=True`를 단다. 이후 `_is_loadable()`
(같은 파일 1104줄, "col_index=0만 저장" — 2026-07-30 결정, 정상 2열 레이아웃에선
맞는 규칙)이 **col_index=0만 남기고 버려서**, 진짜 누적값(404,008,384, col_index=1)은
사라지고 3개월치(839,946,324, col_index=0)만 "누적"이라는 잘못된 딱지를 달고 남는다
— 이 값도 결국 combine.py 후보로는 안 쓰였다(§2-B에서 확인했듯 최종 오답은 CI값
쪽이었다 — EPS쌍은 스테이지 랭크에서 밀린 것으로 보임, 정확한 tie-break 경로는
미추적).

## 3. 스케일 측정 — "주당" 부분문자열 오판의 실제 영향 범위

★★**§5-B 확정 작업(2026-08-15 후속 세션)으로 아래 전부 실측 완료·수치 갱신됨.**

`report_lines`에서 `section_path='주당손익' AND label_raw LIKE '%주주당%'`로 스캔:
**34개사·887행**이 이 부분문자열에 걸린다. 하지만 대부분은 **가짜양성**이다 — 진짜
EPS 라벨도 우연히 같은 부분문자열을 만든다:

- `보통주주당이익(손실)`(00121941) = "보통주"(common stock) + "주당이익"(EPS) → 진짜
  EPS, 우연히 "주주당" 3글자 겹침.
- `지배주주당기순이익(손실)`(00158024, KBI메탈) = "지배" + "주주"(shareholders) +
  "당기순이익" → **NI귀속 라벨(버그)**, 마찬가지로 우연히 "주주당" 3글자 겹침.

**이 둘은 라벨 텍스트만으로 원리적으로 구분 불가능하다** — "보통주주당이익"과
"지배주주당기순이익"은 서로 다른 조어 구조에서 나온 같은 글자열이다(§4에서 상세
검증).

### 3-A. 임계값 실측 확정(§5-B ①)

`section_path='주당손익'`, 2015년 이후, 짧고 깨끗한 라벨(길이<40, `:`·`원` 미포함 —
K-GAAP 텍스트블럽 배제)로 좁힌 뒤 **이미 알려진 버그 회사(아래 §3-B)를 제외**하고
값 분포를 재봤다: **진짜 EPS 약 75,000행의 절댓값 최댓값 = 5,890,065원**(99.99
백분위수 = 277,913원). 즉 "진짜 주당 값"은 실측상 6백만원을 절대 안 넘는다. **임계값
1,000만원(10,000,000)은 이 실측 최댓값보다 1.7배 여유**를 두면서, 버그로 확인된
값들(억~수백억원 단위)과는 자릿수가 수십~수천 배 차이 나 안전하다. **1,000만원으로
확정.**

(참고: 필터링 전 전체 `주당손익` 분포는 p99=57억원까지 치솟는데, 이는 §3-C의 아주
오래된(2003~2007년) K-GAAP 서술형 라벨 오염 때문 — 이번 §3-A 재측정에서 걸러냈다.)

### 3-B. 표본 원문대조 결과(§5-B ②) — 애초 추정 "11개사"는 과대추정, 재확인 필요한 케이스가 섞여 있었다

값 크기(>1,000만원) + 2015년 이후 + 짧은 라벨로 재스캔한 **엄격한 후보군**은
8개사(느슨한 34개사 스캔의 하위집합, `00269852`류 레거시 텍스트블럽은 애초 배제):
`00158024`(KBI메탈, 62행) · `01311055`(쿠콘, 10행) · `00120562`(4행) · `01365825`
(피에스케이, 4행) · `01456011`(4행) · `00531917`(톱텍, 3행) · `00206686`(1행) ·
`00488989`(1행).

**개별 원문대조 + `face_audit`/`std_financials_v3` 실제 상태 확인 결과, 이 8개사가
전부 같은 버그가 아니었다** — §2의 근본원인(④"3개월/누적" 4열을 2열로 오인 + ⑤
`is_cumulative` 블랭킷 규칙)은 **반기/분기(H1/Q3) 보고서에만 성립**한다. 사업보고서
(FY)는 원래 열이 "당기/전기/전전기" 3열뿐이라 그 특정 오류 경로 자체가 발동하지
않는다 — FY 보고서에서 "주당" 오판이 일어나도 **열은 우연히 맞게 들어간다**(재확인:

스크리닝은 **후보를 넓히는 데는 유효**하지만(진짜 버그를 놓치지 않음), **"값이
크다" 자체가 버그를 뜻하진 않는다** — FY 보고서의 "보통주당기순이익"류처럼 정상적으로
큰 값도 있다. **"틀린 값이 fail_a로 확정된 곳"은 지금까지 실측으로 KBI메탈
1개사뿐이다.** 쿠콘·피에스케이는 같은 라벨 오판 메커니즘이 존재할 가능성이 있지만
(원문 직접확인은 못 함, 파일 문제) 현재는 무해하게 pending으로 멈춰 있어 **긴급성이
낮다** — 그래도 Layer 2 근본수정을 하면 "결측 커버리지"가 개선되는 부수효과는 있을
것으로 예상.

### 3-C. `00269852` 및 유사 레거시 패턴

`00269852`는 라벨 자체가 "ⅩⅢ.당기순이익(손실)(보통주주당기순이익당기: -96,
전기:181…)" 같은 **서술형 텍스트 통짜 라벨**(K-GAAP 시대 구서식, 여러 숫자가 괄호
안에 텍스트로 섞여 있음)이고, 저장된 값은 그 행의 "당기순이익 헤드라인" 숫자이지
괄호 안 EPS 숫자가 아니다 — §2의 "4열 XBRL 표" 구조와 무관한 **레거시 서식 문제**다
(2003~2007년경 다수 회사에서 동일 패턴 확인 — §3-A의 필터링 전 상위값 전부 이 부류,
`docs/PARSING_RULES.md` T20류 함정과 유사). **이번 설계 범위 밖 — 별도 조사·설계
필요**(연도가 훨씬 오래돼 controlling_ni Gate B population과 겹칠 가능성도 낮음).

## 4. 왜 라벨 텍스트 기반 수정이 불가능한가 (기각된 접근)

처음 시도한 "`(?<!주)주당`"(직전 글자가 '주'가 아닐 때만 EPS로 인정) 정규식은
**"보통주주당이익"류도 함께 걸러내버려 기각**했다 — "보통주"(3글자, 마지막 글자
'주') + "주당이익"이 만드는 "주주당"과, "지배" + "주주"(shareholders) + "당기순이익"이
만드는 "주주당"이 **문자열 레벨에서 완전히 동일**하기 때문이다(둘 다 정확히
"...주주당..." 5~6글자 윈도우). "주당기"(주당+기) 뒤에 오는 글자로 구분하는 것도
기각 — `기본주당기순이익`/`희석주당기순이익`처럼 **진짜 EPS 라벨의 절대다수가
DART 관행상 "주당기순이익"(당기순이익의 '당기'를 그대로 붙임) 표기를 쓴다**(전수
스캔으로 확인, §3 표 밖 약 40개사 이상). 즉 **정규식/라벨 텍스트만으로는 이 둘을
가르는 신뢰 가능한 신호가 없다** — 값 크기(원/주 vs 원)가 유일하게 실측으로 검증된
구분자다.

## 5. 제안 수정안 (미구현, 승인 필요)

### 5-A. 핵심 아이디어 — 값 크기 기반 EPS 판정 게이트

`fin2/extract/report_lines.py`의 두 지점(§2-C의 ②③) 모두에 **값 크기 상한**을
추가한다 — "주당" 라벨이어도 파싱된 금액이 EPS치고 비현실적으로 크면 EPS 취급을
포기하고 본류(`_emit_section_lines`)로 흘려보낸다.

```python
_EPS_MAX_PLAUSIBLE_WON = 10_000_000  # 원/주, 실측 확정(§3-A) — 이 이상이면 EPS 아님으로 간주

# ②의 스킵 조건(라인 427) 수정:
if not row.account_name or ("주당" in row.account_name and _looks_like_eps(row.amounts)):
    continue

# ③_emit_eps_lines(라인 309) 안에서도 각 amount 파싱 후 동일 상한 적용,
# 상한 초과 시 그 TR 은 emit 하지 않고(→ 본류가 대신 처리하도록 남겨둠) continue.
```

**설계 원칙(이 프로젝트의 기존 규칙과 동일선상)**: 결측 > 오염 — 애매하면 버리지
않고 본류로 흘려보내 정상 IS 라벨 매칭이 판정하게 한다(추측성 재분류 아님, 이미
있는 판정 로직에 위임). 블랭킷 규칙(모든 "주당" 라벨을 없앰) 아님 — 값 크기라는
**독립적으로 검증 가능한 신호**로 좁힌 curated 게이트.

### 5-B. 구현 전 확정 필요 사항 — ★★2026-08-15 후속 세션에서 전부 실측·정리 완료

1. **임계값 실측 — 완료(§3-A)**. 진짜 EPS 값의 실측 최댓값 5,890,065원(2015년 이후·
   깨끗한 라벨·알려진 버그회사 제외, 약 75,000행 모집단) 대비 **1,000만원**으로
   확정(1.7배 여유). 국내 상장사 역대 최고 EPS 수준의 별도 문헌조사는 안 했으나,
   DB 실측치가 이미 충분한 근거.
2. **표본 원문대조 — 완료(§3-B), 단 결과가 가설을 크게 수정함**. 값 크기 기반
   후보(엄격 재스캔 8개사) 개별 확인 결과: **버그가 "틀린 값(fail_a)"으로 실제
   나타나는 곳은 KBI메탈 1개사뿐**. 톱텍(00531917)은 아예 다른 케이스(FY 보고서라
   열 오류 자체가 안 생기고, 큰 값 자체가 정상 — completing이 없어 pending일 뿐)로
   판명돼 **원 설계의 "11개사 버그 후보" 프레이밍은 폐기**. 쿠콘·피에스케이는 같은
   라벨패턴이 있으나 원문 rcept 파일 열람에 실패해(별문제, 미해결) 직접 확인은
   못 했고, 현재 `face_audit`상 controlling_ni fail_a가 0건(전부 pass 또는
   pending)이라 **긴급성 낮음**으로 재분류.
3. **00269852류(레거시 텍스트블럽) — §3-C에서 별도 트랙으로 명시 분리 확정.** 이번
   수정 범위에서 제외(연도도 훨씬 오래됐고 이번 4열 XBRL 구조와 무관).
4. **`_emit_section_lines`(본류)의 4열 인식 여부 — 확인 완료, 이미 올바르게 처리한다.**
   같은 KBI메탈 2025H1 표의 "수익(매출액)" 행(정상 처리된 필드)이 원문 4열 중
   **정확히 누적(HYA) 값**(385,624,927,703, 3개월치 201,243,521,765가 아님)을
   `col_index=0`으로 저장한 것을 원문 대조로 직접 확인(`cum_map` 메커니즘, 405줄).
   즉 **⑤블랭킷 `is_cumulative` 규칙 자체를 고칠 필요는 없다** — §5-A의 "게이트만
   좁혀서 본류로 돌려보낸다"만으로 충분, 본류가 알아서 올바른 열을 고른다.

**남은 리스크(구현 시 재확인)**: 쿠콘·피에스케이가 이 수정으로 pending→pass 전환되는지
는 구현 후 재감사로 직접 확인 필요(사전 원문대조 미완료 상태로 진행하게 됨 — 낮은
리스크로 판단: 수정이 실패해도 최악의 경우 지금과 같은 pending 유지일 뿐, fail_a를
새로 만들 경로가 없다).

### 5-C. 파이프라인 영향 범위 (`docs/runbook_new_parser_pipeline_integration.md` 대응)

- `report_lines.py`는 Layer 2 추출기 — 코드 수정 자체는 **전역**(값 크기 게이트,
  회사 curated 아님)이지만, 실제 데이터가 바뀌는 건 이 패턴에 걸리는 filing뿐이다.
  재추출은 **확인된/의심되는 소수 회사**(KBI메탈 확정 1개사 + 쿠콘·피에스케이 등
  같은 라벨 패턴 보유 회사, §3-B 표 기준)만 corp 단위로 재실행하면 된다(전수 재적재
  아님).
- 이후 **std_v3 재빌드**(`fin2/layer3/combine.py` 경로, corp 단위) 필요 —
  `report_lines` 변경이 자동으로 `std_financials_v3`에 반영되지 않는다.
- 이후 **Gate B 재감사**(`gateb_audit.py --recheck`, corp 단위)로 `face_audit` 갱신.
- 검증: (a) KBI메탈 4개 기간 controlling_ni pass 전환 확인(핵심 목표), (b) 쿠콘·
  피에스케이가 pending→pass(또는 최소 불변, 악화 없음) 확인, (c) `pytest tests/
  fin2/tests/` 회귀 0, (d) EPS 필드 자체(std에 EPS 컬럼 소비처가 있는지 확인 —
  없다면 이 변경이 EPS 값에 주는 영향은 report_lines 레벨에 그침, std_v3엔 원래도
  EPS를 안 씀), (e) 코드가 전역이므로 **영향받는 소수 회사 밖에서도** 무작위 표본
  (다른 회사들의 진짜 EPS 라벨)이 계속 `section_path='주당손익'`으로 올바르게
  남는지(단조성 확인 — 게이트를 좁혔다고 진짜 EPS까지 본류로 새면 안 됨). 전수
  재적재는 안 하더라도 **코드가 전역이라 다음 정기 데일리 수집분부터는 자동으로
  새 판정이 적용된다** — 과거분 소급은 위 (a)(b) 대상 회사만으로 충분한지, 더
  넓게(예: 전체 34개사 원 후보군) 재확인할지는 구현 직후 1회 더 판단.
