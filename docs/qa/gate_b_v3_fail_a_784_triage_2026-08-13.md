## 원문대조 확정 결과 (2026-08-13)

1차 triage에서 우선순위로 꼽은 3개 클러스터를 실제 원문(raw XML)까지 내려가서 확정했다. `[[feedback-verify-against-source]]` 원칙 준수.

### ① revenue 금융업 클러스터 — ★버그 아님, Gate B 방법론 갭
- `fin2/layer3/industry_profiles.py` 확인 결과, **securities profile은 "순영업수익(NET) = 영업이익+판매관리비"를 표준 revenue로 삼는 게 의도된 설계**(사용자 결정 2026-07-24, 코드 주석에 명시). 이유: 증권사 gross "영업수익"(트레이딩 총액 포함)은 회사·연도별 gross/net 표기전환으로 가짜 시계열 절벽을 만듦(예 NH증권 2019 11.5조→2022 net 2.2조).
- **securities profile 154건 전수 재계산 검증**: `db_won == operating_income + sga` **154/154(100%) 일치**. 즉 이 154건은 std_v3가 설계대로 정확히 동작 중이며, Gate B가 "보고서 원문 영업수익"과 비교해서 오탐(false fail_a)을 낸 것. → **Gate B 감사기가 industry_lines profile을 모르고 raw face 값과 단순대조**하는 게 근본원인. 수정 방향: `face_audit.py`가 profile=securities(및 net_op_formula 사용 프로파일)인 행은 gross 총계 대신 (또는 추가로) op+sga 조합과도 비교하도록 예외 처리 필요.
- bank(00382199 신한지주)·credit_finance(00126292) 각 4건: `report_lines`에 "영업수익" 그랜드토탈 라인 자체가 없음(레이어2 커버리지 갭으로 추정 — bank/여신 지주사 특유 IS구조에서 표제/서브토탈 인식이 안 된 것으로 보임) → industry_profiles가 "총계 있으면 그것" 규칙에 따라 정상 폴백(성분합산)했지만 Gate B의 원문 리더는 다른 경로로 총계를 찾아내 대조 → **레이어2 리더와 industry_profiles가 서로 다른 소스를 보고 있어 발생하는 별개 이슈**. 후속 조사 필요(레이어2가 왜 "영업수익" 라인을 못 잡았는지).
- insurance(00126256/00159102): 근접 불일치(1.2%~0.001% 수준) — 세부 서브항목 정의차 의심, 낮은 우선순위.
- insurance(00139214): report_won=12,963,274(원 단위로 보이나 실제는 12.96조여야 함) — **Gate B 원문리더 측 단위(adecimal) 오탐지로 추정**, std_v3 문제 아님.
- 비금융 6개사(01032486 등)는 미확정, 개별 원문대조 필요.

### ② dividends_paid 부호반전 — ★확정된 버그
- `00120021`(LG, 2025FY separate) 원문대조: CF 표에서 "재무활동으로 인한 현금유출액:"(부모, 텍스트에 괄호로 음수 표시 `(633,061)`) 아래 자식행 "배당금의 지급"은 **괄호 없이 양수로 표기**(`632,379`, 단위 백만원) — DART 원문 관행상 "유출액" 섹션 하위 항목은 부모의 음수맥락을 상속하되 자기 셀엔 부호를 안 붙임.
- std_v3는 이 자식 셀을 **문자 그대로(+632,379백만) 적재** → 값의 절대크기는 정확하지만 **부호가 반대**(표준화 규약상 CF outflow는 음수여야 함, 다른 정상 케이스들도 전부 음수로 저장됨을 확인).
- **확정 버그**: 부모-자식 컨텍스트 기반 암묵적 부호 상속을 놓치는 케이스. 표본 4건 모두 동일 패턴(ratio≈-1.0). 수정 대상은 CF 라인 파싱(계층2) 또는 canonical 매핑(계층3)의 부호결정 로직.
- tolerance 오탐 의심 9건(diff가 report 대비 0.005%~1% 수준인데도 fail_a)은 원문대조 안 함 — `face_audit.py:796-822`의 `tol=10**(-adecimal)` 로직이 특정 adecimal 값에서 과소평가되는지 별도 확인 필요.

### ③ trade_payables near-zero — ★확정된 버그
- `00307028`(경남제약, 2024FY) 원문대조: BS 본문엔 "매입채무" 단독 라인이 없고 "매입채무및기타채무" 통합라인만 있음(정상, 많은 기업의 표시관행). 문제는 std_v3가 담은 값(6,000,000원)이 **주석의 "매입채무및기타채무 만기분석" 표에서 "1년초과5년미만"(장기 잔여만기 버킷, 6,000천원) 컬럼**과 정확히 일치 — **장부금액(8,215,379천원) 컬럼이 아니라 만기분석표의 엉뚱한 만기구간 컬럼을 집어온 것**.
- 이 만기분석 노트표는 열이 [장부금액, 계약상현금흐름, 1년미만, 1년초과5년미만] 구조라, trade_payables 매핑 로직이 노트 fallback 시 열(column) 선택을 잘못하고 있는 것으로 확정.
- 같은 corp의 다른 분기들도 전부 작은 정수값(1,000,000/6,000,000 등) — 분기마다 그 분기 만기분석표의 장기버킷 값이 우연히 다른 것뿐, 동일 근본원인.
- **확정 버그**: 노트 fallback(매입채무 BS 단독라인 부재 시) 시 만기분석표 등 다열(multi-column) 노트표에서 열 선택이 "장부금액"이 아닌 엉뚱한 열을 고르는 결함. 21개사/52건이 이 패턴에 해당할 가능성 높음(추가 표본검증 필요하나 메커니즘은 동일할 것으로 추정).
