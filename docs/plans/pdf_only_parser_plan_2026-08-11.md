## 0. 한 줄 요약

계층2(`report_lines`)는 현재 2015+ 원본(1차) + pre-2015 원본(2차, 2026-08-11 완료)까지
XML 소스는 전량 커버한다. 그러나 DART가 **XML/XBRL을 전혀 제공하지 않고 PDF만 제공한
필링**이 활성 유니버스 기준 **3,509건(1,417개사)** 남아 있고, 이 중 `report_lines`나
`fact_v2` 어디에도 적재된 것이 **0건**이다 — 완전히 손 안 댄 백로그. 과거 문서(`known_gaps_
db_coverage.md`, `rearchitecture_4layer_2026-07-19.md`)가 "3,044~3,575건, 신규 PDF 파서
필요, 별도 대형과제(보류)"로 반복 기록만 해온 항목이 바로 이것이다. 이번 문서는 **오늘
실측한 정확한 스코프**와 **기존 코드 자산 재사용 가능성**, **아키텍처 정합성 문제**(핵심
쟁점)를 정리하고, pre-2015 2차 패스와 동일한 Phase 구조로 착수 계획을 세운다.

## 2. 현재 상태 실측 (2026-08-11, DB 직접 쿼리)

```sql
-- filings × download_tasks(status='completed') × corporations.is_active=true 기준
-- has_xml = 해당 rcept_no 에 file_type='xml' completed 다운로드 존재
-- has_pdf = 해당 rcept_no 에 file_type='pdf' completed 다운로드 존재
```

| 구분 | filings | corps |
|---|---:|---:|
| **PDF-only, pre-2015**(filed_at < 2015-01-01) | 1,405 | 839 |
| **PDF-only, 2015+**(filed_at ≥ 2015-01-01) | **2,104** | **979** |
| **합계** | **3,509** | **1,417**(합집합, 두 구간 다 걸리는 회사 있음) |

- pre-2015분 1,405건은 [pre2015_layer2_backfill_plan_2026-08-10.md](pre2015_layer2_backfill_plan_2026-08-10.md)
  §4에서 이미 "별도 트랙(3차)"으로 스코프 제외해 둔 바로 그 숫자 — 이번 트랙이 그 후속.
- **2015+분 2,104건은 이번에 처음 정확히 실측**(과거 문서의 "3,044/3,575"는 더 오래된
  전체·비활성 포함 추정치였다). report_type: annual 300 · half 602 · quarter 1,202.
  is_final: True 1,807 · **False 297**(정정·중간 상태 필링 — §6 결정 필요).
- **fiscal_year 분포가 매우 편중**: 2015~2019 다섯 해에 **1,745건(전체 2015+ 중 83%)**
  몰려 있고, 2020년부터는 연 30~70건대로 급감한다(2020:46·2021:38·2022:35·2023:37·
  2024:35·2025:73·2026:3). **원인 미규명 — Phase 1 최우선 조사 항목.** 가설: 이 구간에
  소형사 XBRL 제출 의무화가 아직 안 걸려 있었거나, DART 시스템 전환기라 일부 필링이
  PDF로만 접수됐을 가능성. 확정 전에는 "구조가 원래 그렇다"고 단정하지 않는다
  ([[feedback-verify-against-source]]).
- **회사 단위로는 "PDF 전용 회사"가 아니라 "산발적 기간 결손"**: 2015+ PDF-only 979개사를
  전수 확인한 결과 **전원(979/979)이 다른 기간에는 XML 필링을 보유**한다(pre-2015 839개사도
  구조상 동일 — 이미 79,205건 XML을 갖고 있는 유니버스의 부분집합). 즉 "이 회사군은 PDF만
  낸다"는 우려는 근거가 약하고, "어떤 회사든 특정 분기·연도 하나가 PDF로만 잡혔다"는 쪽에
  가깝다 — 파일럿 표본 설계(Phase 1)에 반영.
- **기존 적재 0건 확인**: 이 3,509건 중 `report_lines.rcept_no`에 걸리는 행 0건,
  `fact_v2.rcept_no`(구 std_v2/fin2 체인)에 걸리는 행도 0건 — 완전 미착수 백로그임을 재확인.
- (참고, 실측 중 발견한 비관련 사실) "has_xml도 has_pdf도 없는 10건" 초기 쿼리 결과는
  거짓 신호였다 — 전부 `file_type='xbrl_zip'`(XBRL zip 원본, XML과 별개 저장 형식)로
  실제로는 이미 커버돼 있다. 쿼리에 `xbrl_zip`을 has_xml 판정에 포함 안 해서 생긴 조회
  버그일 뿐, 실제 데이터 갭 아님 — 후속 스크립트에서는 `file_type IN ('xml','xbrl_zip')`로
  판정할 것.

**재확인 쿼리** (스코프 갱신 시 재사용):
```sql
WITH filing_types AS (
  SELECT f.rcept_no, f.corp_code, f.fiscal_year, f.filed_at, f.report_type, f.is_final,
         bool_or(dt.file_type IN ('xml','xbrl_zip')) AS has_xml,
         bool_or(dt.file_type='pdf') AS has_pdf
  FROM filings f
  JOIN download_tasks dt ON dt.rcept_no = f.rcept_no AND dt.status='completed'
  JOIN corporations c ON c.corp_code = f.corp_code AND c.is_active = true
  GROUP BY f.rcept_no, f.corp_code, f.fiscal_year, f.filed_at, f.report_type, f.is_final
)
SELECT (filed_at < '2015-01-01') AS pre2015, count(*), count(distinct corp_code)
FROM filing_types WHERE has_pdf AND NOT has_xml GROUP BY 1;
```

## 3. 기존 자산 — 재사용 가능성과 아키텍처 정합성 문제 (★핵심 쟁점)

이미 PDF 파서 코드가 **두 세대** 존재한다. 둘 다 지금 그대로는 못 쓴다 — 이유가 다르다.

**왜 두 세대가 남아 있나(사용자 질문, 2026-08-11 확인)**: 이 프로젝트는 std_v2 → fin2 재작성
(2026-05월) → 4계층 재설계(2026-07-19~) 순으로 **두 번 아키텍처를 갈아엎었다**. PDF-only는
매번 "별도 대형과제, 보류"로 취급됐는데, 그 와중에 재작성마다 그 세대 작성자가 PDF 모듈을
하나씩 새로 짜뒀지만 **매번 XML(본작업) 우선순위에 밀려 끝까지 완성/배선되지 못한 채 다음
재작성이 먼저 왔다** — "최종본 + 구버전" 관계가 아니라 "둘 다 미완성인 채 멈춘 화석" 관계.
**코드로 직접 확인한 결과, 둘 다 현재 프로덕션 경로에서 호출되지 않는다**:
- 데일리 파이프라인(`collect_new.py`)이 부르는 `run.py::process_corp`는 docstring에
  "`download_tasks(status=completed, file_type=xml)` 보유 기업" 대상이라 명시 — PDF 경로
  자체가 애초에 안 걸려 있다.
- §3-1(`parser/pdf/dart_pdf_parser.py`)은 `run.py`의 `_parse_single_pdf`에서만 쓰이는데,
  이는 `process_corp`와 무관한 독립 CLI 서브커맨드 경로 — 매일 자동 실행 안 됨.
- §3-2(`fin2/extract/pdf.py`)는 더 명확하다 — import하는 곳이 `scripts/archive/backfill/`
  (이미 archive 격리된 1회성 스크립트)와 테스트/감사 도구뿐, **프로덕션 호출자 0개**.
- §2의 "기존 적재 0건" 실측과 정합 — 두 세대 다 전량 실행된 적이 없다는 뜻.

즉 std_v2(현재도 뷰 폴백으로 살아있는 소비자가 있어 삭제 전 재확인이 필요했던 사례)와 달리,
이 두 PDF 세대는 **막고 있는 살아있는 소비자가 없다** — "혹시 아직 쓰나?" 재확인 없이도
정리 가능하다는 뜻. §6 Q4에서 "결정 보류"가 아니라 확정 방침으로 못박는다.

### 3-1. `parser/pdf/*` (std_v2 세대, 2026년 초)
`dart_pdf_parser.py`(405줄) · `pdf_section_detector.py`(262줄) · `pdf_table_extractor.py`
(216줄) · `pdf_amendment_handler.py`(427줄, 원본+정정 PDF 쌍 분류: FULL_REPORT/
PARTIAL_COVER/NON_FINANCIAL). pdfplumber 기반, XML 파서의 `ParseResult`/`FactRow`와
동일 인터페이스를 흉내내 **fact_v2에 직접 적재**하는 구조 — std_v2 시대 산물.
- **재사용 가능**: 텍스트/표 추출 로직 자체(pdfplumber 페이지 텍스트·표 bbox 탐지,
  단위 선언 정규식, 이미지 스캔 PDF 감지 = `parse_status='skip'`), 정정 PDF 쌍 분류

  작성돼 애초에 이 불변식을 적용받지 않은 코드다.

### 3-3. 결론 — 이번 트랙이 풀어야 할 진짜 문제
"PDF에서 값을 뽑는 기술"은 이미 두 번 풀렸다(§3-1, §3-2 모두 동작은 했다는 기록).
새로 짤 것은 **"뽑은 값을 report_lines(계층2) 스키마로 어떻게 표현할지"**다. 이게
Phase 2 설계의 핵심 질문이다.

**tree 구조 유지 가능성(2026-08-11, 사용자 질문에 답하며 재검토)**: 처음엔 "PDF엔 들여쓰기
정보가 없다"고 단정하고 §6 결정사항을 "전부 NULL vs 최소 구조 부여" 둘 중 택일로 열어
뒀는데, 이건 성급한 단정이었다. XML 쪽 `depth`도 사실 태그가 아니라 **원문의 전각공백
들여쓰기 개수를 그대로 측정**한 것뿐이다(`report_lines.depth` 컬럼 코멘트: "원문 전각공백
수"). PDF도 원본 문서가 시각적으로는 계정명 앞에 들여쓰기를 두고 렌더링했을 가능성이 높고,
`pdfplumber`는 텍스트를 문자 단위 x-좌표(bbox)로 추출하므로 **그 들여쓰기가 텍스트
레이어에 공백으로 보존되는지, 아니면 좌표 정보로만 남는지**는 "PDF라서 원래 불가능"이
아니라 **아직 실측하지 않은 사실**이다. → **Phase 1에 조사 항목 추가(1-6)**: 표본에서
계정명 라인의 선행 공백(또는 x0 좌표) 분포를 측정해 XML과 같은 방식(들여쓰기 비교 →
depth/node_role, 텍스트 내용은 안 봄)으로 **진짜 관찰된 구조를 복원할 수 있는지** 확인.
보존돼 있으면 그 신호로 XML과 동일한 depth/node_role 산출 로직을 재사용해 **정형화된 tree
구조를 그대로 유지**한다(지어내는 게 아니라 원문에 실제로 있는 시각적 위계를 읽는 것이라
R0 "관찰이지 판단 아니다" 원칙에도 부합).

**들여쓰기가 소실된 세대는 어떻게 하나(2026-08-11, 사용자 추가 질문)**: 곧바로 NULL로
포기하지 않는다. §5 Phase 1-7에서 **대체 구조 신호**(폰트 크기·굵기, 원문 번호매김 접두
기호 "가./나./다."·"1)/2)", 표 셀 bbox 들여쓰기 padding, 줄/문단 간격)를 조사하고, 각각을
**pdfplumber + 규칙 기반(정규식·좌표 임계값)만으로 우리가 직접 구현 가능한 난이도인지**
표본 검출률과 함께 평가한다 — OCR·레이아웃ML 같은 별도 인프라 도입 없이 지금 갖춘 도구로
"능력이 되는지"를 이 Phase에서 먼저 확인하는 것이 핵심이다. 후보가 하나라도 채택되면 그
세대는 그 규칙으로 depth/node_role을 산출하고, 전부 기각된 세대만 최종적으로 NULL 폴백을
쓴다 — "PDF는 전부 NULL"이 기본값이 아니라 **실측 후 세대별·신호별로 갈릴 수 있는 결론**
으로 바꾼다(§6 Q1 갱신).

## 5. Phase 계획 (pre-2015 2차 패스와 동일 구조 채택)

### Phase 1 — 구조 정밀 실측 (읽기 전용)
- 1-1. 층화 표본 설계: 연도(1999~2026, PDF-only가 존재하는 전 구간) × report_type
  (annual/half/quarter) × 시대구분(pre-2015 / 2015-2019 급증구간 / 2020+ 저빈도구간)
  층화표본, 연도·구간당 5~10건, 총 150~200건. **§2에서 발견한 "2015-2019 왜 이렇게
  몰렸나" 질문을 최우선으로 조사**(DART 시스템/제도 변화 여부 — 확정 안 되면 "known-gap"
  단정 금지, [[feedback-verify-against-source]]).
- 1-2. 텍스트 레이어 실측: pdfplumber로 텍스트 추출 가능 여부(이미지 스캔 PDF 비율) —
  §3-1 감지 로직 재사용해 전수(3,509건) 사전 스캔, skip 대상 규모 확정.
- 1-3. face 섹션 앵커 패턴 실측(§3-2 방식 검증 확장): "제목+기간마커" 앵커가 연도별·
  기업규모별로 얼마나 안정적인지, 실패 패턴(목차 오인식, 요약재무정보 오인식, 다단 표
  줄바꿈 깨짐) 카탈로그화.
- 1-4. 표(계정명+금액) 텍스트 구조 실측: 열 정렬이 공백/탭 기반인지, 금액이 괄호(음수)·
  하이픈(공란) 등으로 어떻게 표기되는지, 다段(당기/전기/전전기) 컬럼 구분 가능 여부.
- 1-5. 정정 PDF 쌍 비율 실측(is_final=False 297건 포함, **정정 계보 포함 스코프 확정** —
  §4) — §3-1 3분류가 실측 표본에서도 유효한지 확인.
- 1-6. **★들여쓰기/구조 보존 실측(§3-3, 2026-08-11 추가)**: 표본에서 계정명 라인의 선행
  공백 또는 pdfplumber x0 좌표 분포를 측정 — XML 방식(들여쓰기 비교로 depth/node_role 산출)
  그대로 재사용 가능한지 확인. 세대별(연도·서식)로 보존 여부가 갈릴 수 있음 — "전부 NULL"
  단정 금지, 실측대로 기록.
- 1-7. **★대체 구조 복원 신호 조사 + 직접 구현 가능성 평가(2026-08-11 추가)**: 1-6에서
  들여쓰기가 소실된 것으로 확인되는 세대가 있으면, 곧바로 NULL로 포기하지 않고 **다른
  신호로 구조를 복원할 수 있는지** 조사한다 — 후보:
  (a) 폰트 크기·굵기(pdfplumber `chars`의 `size`/`fontname`) — 소제목·소계 행이 본문과
      다른 폰트를 쓰는지,
  (b) 원문 번호매김 패턴("가./나./다.", "1)/2)/3)", "Ⅰ./Ⅱ." 등 — 계정 라벨 앞에 계층을
      나타내는 접두 기호가 있는지, 있다면 그 기호 자체가 depth 신호),
  (c) `extract_table()`의 열 경계(bbox) — 계정명 열이 셀 내부에서 들여쓰기 padding으로
      표현되는지,
  (d) 줄 간격/문단 간격 — 소계·합계 행 앞뒤로 여백이 다른지.
  **각 후보별로 표본에서 실제 검출률을 측정하고, 규칙 기반(정규식/좌표 임계값)으로 구현
  가능한 수준인지 — 즉 OCR·레이아웃ML 같은 별도 인프라 없이 지금 갖춘 도구(pdfplumber +
  Python 규칙)만으로 우리가 직접 구현할 수 있는 난이도인지 — 를 항목별로 평가한다.**
  산출물에 "채택/기각" 결론과 근거를 남긴다 — 전부 기각되면 그때 비로소 §3-3 NULL 폴백이
  최종안이 되고, 하나라도 채택되면 Phase 2 설계에 그 규칙을 반영한다.
- 1-8. **★이미지 스캔 PDF — OCR로 "최신 방식(구조화된 tree)" 유지 가능성 조사(2026-08-11
  추가, §4·§6 결정사항 2)**: 1-2에서 텍스트 레이어가 없는 것으로 확인된 표본(작은 부분집합
  으로 시작)에 OCR을 시험 적용한다.
  - **환경 확인(2026-08-11 사전조사)**: 현재 `.venv`엔 OCR 패키지 없음, macOS에도 `tesseract`
    바이너리 미설치 — 도입하려면 `brew install tesseract tesseract-lang`(한국어팩 `kor`
    포함, 시스템 바이너리라 `.venv` 밖 — 사용자 직접 설치 필요) + `pytesseract` 등 Python
    바인딩 추가가 필요. `pdfplumber`·`pypdfium2`(페이지→이미지 렌더링용, 이미 설치됨)는
    이미 있어 렌더링 자체는 추가 설치 없이 가능.
  - **정확도 실측(★최우선 — 재무 숫자라 오차 허용 안 됨)**: 소표본에서 OCR 추출값을 실제
    금액과 대조(가능하면 같은 회사의 인접 시점 XML 필링 값 또는 육안 대조) — 계정명 문자
    인식률뿐 아니라 **숫자(금액) 오인식률을 별도로** 측정한다. 라틴 숫자는 한글보다 오인식
    위험이 낮다고 알려져 있으나 확정 전엔 가정하지 않는다.
  - **구조 복원 가능성**: OCR 엔진이 문자 bounding box를 함께 반환하면(`pytesseract.
    image_to_data` 등), 그 좌표로 1-6/1-7과 같은 방식(들여쓰기/폰트/여백 비교)의 depth/
    node_role 산출이 가능한지 확인 — 즉 이미지 스캔 PDF도 "최신 방식과 동등한" 구조화된
    tree로 적재될 수 있는지가 핵심 질문.
  - **비용**: 페이지당 처리 시간(pdfplumber 텍스트 추출 대비 얼마나 느린지), 전체 이미지
    스캔 PDF 예상 규모(1-2 결과) 기준 총 소요 시간 추정.
  - **결론**: 정확도(특히 금액 숫자)·구조 복원 가능성·비용이 기준을 넘으면 Phase 2 설계에
    포함(Phase 4 파일럿에서 재검증), 못 미치면 §3-1 기존 `parse_status='skip'` 그대로 확정.
- 1-9. 산출물: `docs/qa/pdf_only_structure_probe_2026-08-XX.md` — 서식/시대 경계 확정,
  실사용 가능한 파싱 전략별 예상 커버리지, 들여쓰기 보존 여부 세대별 결론, 대체 신호별

### Phase 7 — std_v3 반영 + 문서화

## 6. 사전 결정 사항 — 전부 확정(2026-08-11, 사용자 결정)

1. **계층2 tree 표현 방법 — ☑ 확정**: "PDF는 구조가 없다"고 지레 단정하지 않는다. §5
   Phase 1-6에서 계정명 라인의 들여쓰기(선행 공백 또는 pdfplumber x0 좌표) 보존 여부를
   실측하고, **보존되는 세대는 XML과 동일한 방식(들여쓰기 비교 → depth/node_role)으로
   정형화된 tree 구조를 그대로 유지**한다(지어내는 게 아니라 원문에 실제로 있는 시각적
   위계를 읽는 것 — R0 원칙에 부합). **들여쓰기가 소실된 세대는 곧바로 NULL로 포기하지
   않고**, §5 Phase 1-7에서 대체 신호(폰트 크기·굵기, 번호매김 접두기호, 표 셀 bbox
   들여쓰기, 줄간격)로 구조를 복원할 수 있는지 — 그리고 그걸 지금 갖춘 도구(pdfplumber +
   규칙기반)만으로 **우리가 직접 구현할 능력이 되는지** — 표본 검출률과 함께 조사한다.
   전부 기각된 세대만 최종적으로 NULL 폴백(§3-3).
2. **이미지 스캔 PDF(OCR) 처리 방침 — ☑ 확정(2026-08-11, 범위 확장)**: "OCR은 범위 밖"이던
   초안을 되돌린다. **OCR로 최신 방식(구조화된 tree)과 동등한 결과를 낼 수 있다면 포함
   한다** — Phase 1-8에서 OCR 정확도(특히 금액 숫자 오인식률, 재무데이터라 허용오차 없음)·
   구조 복원 가능성(bounding box로 depth/node_role 산출 가능한지)·비용(설치·처리시간)을
   실측한 뒤 기준을 넘으면 Phase 2 설계에 포함, 못 미치면 그때 "영구 skip"으로 확정한다.
   현재 환경엔 OCR 인프라가 없음(`tesseract` 미설치, `.venv`에 관련 패키지 없음) — 도입
   시 시스템 바이너리 설치(`brew install tesseract tesseract-lang`)가 필요해 **사용자
   직접 실행이 필요한 단계**(Phase 1-8에서 실제로 필요해지면 별도 안내).
3. **정정(is_final=False) 필링 297건(2015+) 스코프 — ☑ 확정**: 정정 계보까지 이번 트랙에
   포함한다. `pdf_amendment_handler.py`의 FULL_REPORT/PARTIAL_COVER/NON_FINANCIAL 3분류
   로직을 계층2 출력(`amended_by` 계보)으로 Phase 2에서 재구현(§5 Phase 2-3).
4. **기존 legacy 코드 처리 — ☑ 확정**: 두 세대 모두 프로덕션 호출자 0개 확인(§3, std_v2와
   달리 재확인 불요할 만큼 명확). 신규 계층2 구현(Phase 3)이 재사용할 로직만 흡수하고,
   `parser/pdf/*`·`fin2/extract/pdf.py` 원본은 Phase 3 완료 시점에 삭제(Phase 3 todo 3-5).
5. **승인 단위 — ☑ 확정**: Phase 1(구조 실측, 읽기 전용)만 먼저 실행하고 결과 보고 후
   Phase 2 착수를 별도로 재요청한다(pre-2015 트랙과 동일 패턴). **이 확정 자체가 Phase 1
   실행 지시는 아니다 — [정책](../../CLAUDE.md)상 실행은 이 문서와 별개로 명시적 요청이
   있어야 시작한다.**

## 7. 리스크

- **PDF는 XML보다 구조 정보가 근본적으로 적다** — §3-2가 이미 겪은 문제("tree 품질 낮음",
  `rearchitecture_4layer_2026-07-19_checklist.md`) 그대로 재현될 수 있다. Phase 1에서
  "파싱은 되는데 계층2 스키마로 못 옮기는" 케이스 규모를 먼저 정직하게 측정해야 한다.
  낙관적으로 잡지 말 것.
- **OCR 재무 숫자 오인식 리스크(2026-08-11, 범위 확장에 따라 신규)** — OCR을 채택하면
  "구조는 복원했는데 금액 숫자가 틀리는" 조용한 오염이 가장 위험하다(예: '8'↔'3', '0'↔'6'
  오인식). Phase 1-8에서 정확도 실측을 **구조 복원 가능성보다 먼저·더 엄격한 기준으로**
  본다 — 검증 없이 채택하지 않는다([[feedback-verify-against-source]]).
- **이미지 스캔 PDF 규모가 크면 OCR로도 이번 트랙 예산 안에 못 들어올 수 있다** — Phase 1
  실측 규모(1-2)·OCR 실현 가능성(1-8)을 함께 보고한 뒤, 정확도/비용이 기준 미달이면 그
  구간만 skip으로 남기고 "전량 무결측"(CLAUDE.md 개발 목표) 원칙에 대해 사용자에게 정직하게
  보고한다.
- **2015-2019 급증 원인 미규명 상태로 착수하면** 오판 위험(예: 실은 다운로더 버그로 XML을
  놓친 것인데 "DART가 원래 PDF만 줬다"고 오판) — Phase 1 최우선 조사 항목으로 못박음(§5).
