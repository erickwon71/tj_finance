# ② Gate B — 증거강도 재정의 + `pass` 근거 계측 설계 (2026-08-17)

> **착수 순위 5** (`gateb_remediation_master_2026-08-17.md` §1).
> **선행**: ③(성능) 완료 · 전수 재감사 기준선 · ①(파생 revenue) 적용.
> 이 순서인 이유 — 등급 체계를 바꾸는 **유일한** 트랙이라, 모집단(fail 3,348→~660)이
> 정리된 뒤에 실측해야 판단 근거가 깨끗하다.
> **핵심 방침**: **계측을 먼저 넣고, 게이팅 규칙은 실측을 본 뒤에 정한다**(§2).

---

## 0. 이 문서가 하는 일 (3줄 요약)

1. `fail_a`/`fail_b` 는 "결함이 얼마나 확실한가" 가 아니라 **"그 보고서를 어느 리더가
   읽었는가"** 를 반영한다. 같은 회사·같은 결함이 연도에 따라 등급이 뒤집힌다(§1-A).
2. `pass` 는 **근거를 하나도 남기지 않는다.** "원문 값과 정확히 일치" 와 "±1 관용/부호반전/
   회계항등식 폴백/휴리스틱 리더 후보와 일치" 가 **전부 같은 `pass`** 로 기록된다(§1-B).
   그래서 "지난 2주가 검증력을 깎았는가" 라는 질문에 **데이터로 답할 수 없다**.
3. 해법은 두 축 분리다 — **판정**(일치/불일치/판정불가)과 **증거강도**(그 판정의 근거).
   Phase 1 은 **기록만** 추가하고 게이팅 산식은 한 줄도 바꾸지 않는다(무해·되돌릴 것 없음).

## 1. 문제

### 1-A. `fail_a`/`fail_b` 는 리더 트랙의 그림자다

계약(`face_audit.py:801-806`)은 이렇게 적혀 있다:

```
fail_a = Track A(XBRL ADECIMAL 권위) 값불일치 = **확정 버그** → 메인뷰 차단
fail_b = Track B(텍스트 reader 휴리스틱) 값불일치 = false-fail 가능 → REVIEW
```

산식(`face_audit.py:810-825`)은 실패 **필드**의 track 을 보는데, track 은
`gateb_audit.py:49-53` 에서 **필드 → statement → 그 rcept 를 읽은 트랙**으로 유도된다.
즉 **보고서 단위 속성**이지 그 필드가 실제로 어떤 후보와 대조됐는지가 아니다.

**실측 — 미래에셋증권 `revenue`, 동일 결함:**

| 연도 | 등급 |
|---|---|
| 2022 | fail_b 202건 |
| 2023 | fail_b 278 / fail_a 1 |
| 2024 | fail_b 226 / fail_a 32 |
| **2025** | **fail_a 101** / fail_b 16 |
| **2026** | **fail_a 50** / fail_b 0 |

결함이 달라진 게 아니라 **그 연도 보고서의 XBRL 태깅 성숙도**가 달라졌을 뿐이다.
→ `fail_a` 394건을 `fail_b` 2,954건보다 우선해 쫓아 온 근거가 **데이터상 없다**.

**부수 결함**: `_supplement_with_text()`(`face_audit.py:580-611`)가 붙인 라인은
`from_gapfill=True`(저신뢰)인데 **보고서 track 은 여전히 "A"** 다. 따라서 Track A 보고서에서
gapfill 후보가 `nearest` 로 뽑혀 `VALUE_DIFF` 가 나면 **"확정버그(fail_a)"로 차단**된다 —
증거는 휴리스틱인데 등급은 최고 신뢰다. (후보가 *전부* gapfill 이면 `GAPFILL_UNVERIFIED`
pending 으로 빠지므로, 혼합 풀에서만 발생하는 좁은 경로다.)

### 1-B. `pass` 는 근거를 남기지 않는다

`gateb_audit.py:213-218` — 저장되는 것은 **불일치와 pending 뿐**이다:

```python
"fail_detail":    [... for f in ra.fields if f.reason == "VALUE_DIFF"] or None,
"pending_detail": dict(pend) or None,
#  pass 는 아무것도 기록하지 않음 (reason=None)
```

그런데 `audit_fields()` 안에서 `match=True` 로 가는 경로는 **최소 8가지**다:

| # | 경로 | 코드 |
|---|---|---|
| 1 | `val in won_vals` — 정확 일치 | `face_audit.py:1015` |
| 2 | `-val in won_vals` — **부호 반전** 허용(표준화 규약) | `:1018` |
| 3 | `abs(nw−val) <= tol` — **표시단위 ±1 관용** | `:1031` |
| 4 | `revenue = cogs + gross_profit` 항등식 | `:990` |
| 5 | `net_income = cf.net_income_cf` 폴백 | `:1001` |
| 6 | `net_income = 지배 + 비지배` 폴백 | `:1008` |
| 7 | `net_income` 항등식(관용오차 포함) | `:1039` |
| 8 | 매칭된 후보가 **`from_gapfill`**(텍스트보충·PDF any-column) | 표시 없음 |
| (9) | ①이 추가할 **업종 프로파일 파생 재계산** | 신규 |

**이 9가지가 전부 같은 `pass`로 기록된다.** 그래서 다음을 알 수 없다:

- 전체 `pass` 197,097건 중 **정확 일치는 몇 건인가?**
- 관용·폴백으로 통과한 비율이 지난 2주간 **늘었는가?**

### 1-C. 왜 위험한가 — 이미 한 번 터졌다

`face_audit.py:776-786`(R23) 주석이 실사고를 기록한다:

> `NoncurrentPayables` 를 concept_map 에 추가했더니 아이텍(00626011)의 그 라인 값이 우연히
> `0` 이었고, std_v3 에 저장된 **진짜 버그값 0** 과 우연히 일치 → **fail_a 로 정확히 잡히던
> 진짜 버그가 가짜 PASS 로 가려졌다.**

발견 경위는 계측이 아니라 **사람이 148건을 손으로 훑다가**였다. 같은 부류가 다른 필드에
있는지는 **지금도 확인할 방법이 없다** — pass 근거가 기록되지 않기 때문이다.

## 2. 설계 원칙 — 계측 먼저, 게이팅 나중

> **Phase 1 에서는 게이팅 산식(`gate_status_for_row`)을 한 줄도 바꾸지 않는다.**

이유:

- 등급 체계 변경과 계측을 동시에 넣으면 **어느 쪽이 수치를 움직였는지 분리 불가** —
  ③ §6-C 에서 성능·판정을 섞지 말라고 한 것과 같은 원칙.
- 게이팅 규칙(무엇을 차단할 것인가)은 **분포를 보고 정해야 할 사용자 결정**이다.
  지금은 그 분포를 아무도 모른다. 모르는 상태에서 규칙부터 정하면 또 짐작이 된다.
- 계측만 추가하는 변경은 **판정 결과를 바꾸지 않으므로 되돌릴 일이 없다**.

## 3. 증거등급 정의

두 축을 분리한다.

**축 1 — 판정(verdict)**: `match` / `mismatch` / `unaudited`
**축 2 — 증거강도(evidence)**: 그 판정의 근거가 얼마나 강한가

| 등급 | 의미 | 해당 경로(§1-B 표) |
|---|---|---|
| **E1_EXACT** | 원문 face 라인 값과 **정확 일치** | 1 |
| **E2_SIGN** | 절대값 일치, 부호만 다름(표준화 규약) | 2 |
| **E3_ROUNDING** | 표시단위 1단위 이내(발행사 반올림) | 3 |
| **E4_IDENTITY** | 회계 항등식으로 **재구성**해 일치 | 4·5·6·7·(9) |
| **E5_HEURISTIC** | 저신뢰 리더 후보(`from_gapfill`)와 일치 | 8 |
| **M1_STRONG** | 불일치 — 최근접 후보가 E1급 출처(Track A 비-gapfill) | 현 `VALUE_DIFF` |
| **M2_WEAK** | 불일치 — 최근접 후보가 휴리스틱 출처 | 현 `VALUE_DIFF` |
| **U\*** | 판정불가 | 현 `_PENDING_REASONS` 그대로 |

> E1~E5 는 **약해지는 순서**로 정렬돼 있다. E4(항등식)를 E5(휴리스틱)보다 위에 두는 이유:
> 항등식은 **원문 성분값으로 재계산해 맞춘 것**이라 근거가 문서에 있고, 휴리스틱은
> **표 선택 자체가 불확실**하다(`face_audit.py:1044-1046` 의 기존 판단과 일치).

### 3-A. `M1/M2` 가 `fail_a/fail_b` 를 대체하는 방식

현재: **보고서**가 Track A 면 그 보고서의 모든 실패 필드가 `fail_a`.
변경 후: **그 필드의 최근접 후보 라인**이 gapfill 이면 `M2_WEAK`, 아니면 `M1_STRONG`.
→ §1-A 의 부수 결함(Track A 보고서 안의 gapfill 후보)이 자동 해소된다.

## 6. Phase 3 결정 선택지 (미리 제시 — 실측 전 결정 금지)

게이팅 규칙 후보. **분포를 보기 전에는 고르지 않는다.**

| 안 | 차단(`fail_a` 상당) | 특징 |
|---|---|---|
| **A. 보수** | `M1_STRONG` 만 | 현재와 가장 가까움. 차단 최소 |
| **B. 균형** | `M1_STRONG` + `M2_WEAK` | 불일치는 출처 무관 전부 차단. REVIEW 개념 소멸 |
| **C. 증거하한** | `M1` + **`E5`만으로 통과한 행을 `pass` 에서 제외** | 약한 근거 통과를 `pass` 로 인정하지 않음. 가장 엄격 |

> C 는 "**결측 > 오염**"([[feedback-verify-against-source]]) 원칙에 가장 충실하지만
> `pass` 모집단을 얼마나 깎는지가 Phase 2 실측에 달려 있다.

## 7. 검증 규약

**A. Phase 1 무해성 (최우선)** — 계측 추가가 판정을 바꾸지 않음을 증명

```
전수 재감사 전후 face_audit 비교
통과선: status / gate_status / n_pass / n_fail / n_pending / fail_fields 전건 동일
        (evidence_detail 만 신규 채워짐)
```

**B. 증거등급 배타성** — 한 필드는 정확히 하나의 등급을 받는다. 합계 = `n_pass + n_fail`.

**C. 단위 테스트** — §1-B 표의 9개 경로 각각이 **의도한 등급**을 받는지 고정
(특히 경로 8: gapfill 후보와 일치 → `E5_HEURISTIC`, 현재는 표시조차 없음).

**D. R23 재현 검사** — 아이텍(00626011) 2025FY separate 를 **curated 제외키를 끈 상태**로
감사해, 그 우연일치 통과가 `E1_EXACT` 가 아니라 실제로 무엇으로 기록되는지 확인한다.
계측이 그 사고를 **탐지 가능하게 만드는지**가 이 설계의 실질 검증이다.

**E. 회귀** — `pytest tests/ fin2/tests/` 549 기준선.

## 9. 미결 / 범위 밖

- `face_line_audit`(라인 전수대조)은 `n_missing` 86%로 사실상 미작동이다. 원인은 `fact_v2`
  커버리지(≈2.4%)이지 등급 체계가 아니다 — **본 문서 범위 밖**. 별도 판단 필요:
  ① XBRL 파서로 `fact_v2` 를 채워 살릴 것인가, ② 지표를 은퇴시킬 것인가.
- `_PENDING_REASONS` 의 U\* 재분류(어떤 pending 이 "영영 감사 불가" 이고 어떤 것이
  "아직 안 한 것" 인가)는 Phase 3 이후 별도.
- pre-2009 53,614행 100% pending 문제는 등급이 아니라 **커버리지** 과제 — 별도 트랙.
