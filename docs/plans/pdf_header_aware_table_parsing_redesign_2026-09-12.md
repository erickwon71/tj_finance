# PDF 표 추출 — 헤더 구조 우선 파싱 재설계 (2026-09-12)

**상태**: ✅구현 완료·검증 완료. 사용자가 "헤더 구조를 먼저 파싱하는 근본적 재설계"
방향을 명시적으로 선택했고(narrower한 "항등식 깨지면 grid 재시도" 안 대신), 구현 중
Phase 1 설계 시점엔 예상 못 했던 **진짜 근본원인**(주석번호 열 오인식 + "반기" 앵커
누락)을 실측으로 추가 확정해 그것까지 고쳤다 — §6 참고.

**계기**: 솔트웨어 20220802000208 PDF 강제적재 CSV에서 사용자가 원본 대조로 발견 —
`fin2/extract/pdf.py`가 "과목/주석/제4(당)반기말/제3(전)기말" 헤더를 전혀 안 읽고,
`extract_text()` 텍스트 스트림을 줄 단위 정규식으로 훑어 **그 줄에 있는 숫자를 순서대로
당기/전기에 배정**한다(모듈 자체 docstring: "any-column 비재사용"). 인접 행 사이 줄바꿈이
유실되면(오늘 실측: "Ⅰ.유동자산" 행과 "현금및현금성자산" 행이 한 줄로 합쳐짐) 숫자가
잘리거나 다음 라벨에 들러붙어 값이 조용히 틀린다.

## 1. 현재 구조 재확인

- **주 경로**(`_iter_data_lines`/`_parse_single_line`, `fin2/extract/pdf.py:161-264`):
  텍스트 줄 → 정규식으로 숫자 토큰 전부 추출 → 등장 순서 = 컬럼 순서로 간주. 헤더 파싱
  없음.
- **격자 폴백**(`extract_tables()`, `fin2/extract/pdf.py:267-340`): pdfplumber 의 셀
  격자 복원 — 열 경계가 좌표 기반이라 이 문제 자체가 구조적으로 없음. 그런데 **"주
  경로가 앵커 라벨(자산총계/부채총계/자본총계)을 텍스트에서 아예 못 찾을 때만"**
  발동한다(`_region_has_anchor_labels`). 솔트웨어는 라벨 글자 자체는 안 깨지고 숫자만
  잘못 붙어서 이 게이트를 통과 못 했다 — "라벨은 있는데 숫자-라벨 정렬이 틀렸다"를
  잡는 게이트가 없다.
- **참고할 기존 패턴**: `parser/xml/table_extractor.py::parse_header_columns()`가
  이미 이 프로젝트의 다른 파서(XML 계층2)에서 정확히 같은 문제를 "헤더를 먼저 읽어
  position→period 맵을 만들고, 애매하면 확장하지 않고 None(폴백)"으로 풀고 있다
  (`HeaderColumn`, "R6 확신 없으면 추측 안 함"). 이번 재설계는 이 철학을 PDF 쪽에
  그대로 이식하는 것 — 새 원리를 만드는 게 아니다.

## 2. 제안 설계 — 헤더를 먼저 파싱해 컬럼 수를 "진실"로 삼는다

### 2-1. 헤더 파싱 함수(신규)

```python
@dataclass
class PdfTableHeader:
    has_note_col: bool          # "주석" 열 존재 여부
    n_period_cols: int          # 기간 컬럼 수(대부분 2 — 당기/전기, 사업보고서는 3)
    period_labels: list[str]    # ["제4(당)반기말", "제3(전)기말"] 등, 참고용(로그/디버깅)

def _parse_pdf_table_header(region_text: str) -> PdfTableHeader | None:
    """앵커(제목+단위) 직후 '과목 [주석] 제N(당/전)기...' 형태 헤더 줄을 찾아 컬럼
    구조를 읽는다. 헤더를 못 찾거나 형태가 애매하면 None(호출측 폴백 — 지어내지 않음,
    parse_header_columns() 와 동일 원칙)."""
```

- 헤더 후보 줄 탐지: `_PERIOD_MARK_RE`(이미 있음, "제 N 기"류)가 **한 줄 안에 2번 이상**
  매치되는 첫 줄을 헤더로 본다(정상 헤더는 당기+전기 마커가 같은 줄에 나란히 인쇄됨).
- `주석`/`Note` 토큰 존재로 `has_note_col` 판정(있으면 데이터 줄에서 note-ref 토큰을
  먼저 걷어내야 함 — `_NOTE_REF_STRIP_RE`가 이미 있음, 재사용).
- `n_period_cols` = 그 줄에서 찾은 기간 마커 개수. IS/CF 의 "3개월 누적" 2단 헤더처럼
  같은 기간에 하위열이 더 있는 경우는 **기존 3줄/멀티라인 로직이 이미 처리 중인
  영역이라 이번 1단계 범위에서는 건드리지 않는다**(아래 §4 범위 참고).

### 2-2. 컬럼 수를 데이터 줄 검증에 쓴다

`_parse_single_line()`/`_iter_data_lines_multiline()`이 한 줄에서 뽑은 `len(nums)`를
헤더의 `n_period_cols`와 대조한다:

- **일치**: 지금처럼 순서대로 배정(무변경).
- **불일치**(오늘 사고처럼 더 많이 나오거나, 반대로 부족한 경우): 그 줄(또는 그 줄이
  속한 리전 전체)을 "텍스트 스트림 신뢰 불가"로 표시하고, **기존 격자 폴백
  (`extract_tables()`)을 재시도한다** — 지금은 "앵커 라벨 못 찾을 때만" 트리거되는
  조건에, "헤더 대비 컬럼 수가 안 맞을 때"를 **추가**한다. 격자 추출 결과도 헤더의
  `n_period_cols`와 다시 대조해 여전히 안 맞으면 그 라벨은 결측 처리(R6 — 틀린 값
  싣느니 결측이 낫다는 이 코드베이스 전체 원칙 그대로).

### 2-3. 왜 "전면 격자 우선 전환"이 아니라 "검증 게이트"인가

사용자가 고른 "근본적 재설계"는 "헤더를 안 보고 진행"하는 근본 원인을 없애는 것이지,
"텍스트 스트림 경로 자체를 버리는 것"은 아니라고 해석했다 — 이유:
- `extract_tables()`는 일부 구형/스캔 PDF에서 표 자체를 인식 못 하는 경우가 있다
  (레이아웃에 진짜 선/격자가 없으면 pdfplumber 가 표를 못 찾음) — 그런 문서는 지금의
  텍스트 스트림 경로가 유일한 수단이다. 전면 전환하면 그 문서들이 오히려 퇴행한다.
- 대신 **헤더 파싱을 항상 먼저 하고, 그 결과(컬럼 수)를 "진실"로 삼아 두 경로 중
  어느 쪽 결과든 검증**하는 쪽이 "헤더를 안 읽는다"는 근본 원인을 없애면서도 기존
  커버리지를 안 깨뜨린다.

## 3. 예상 영향 범위·리스크

- **저위험**: 헤더 파싱 자체는 새 코드 경로이고, "컬럼 수 불일치일 때만" 기존 동작을
  바꾼다 — 지금 이미 맞게 동작하는 대다수 필링(컬럼 수 일치)은 무변경.
- **검증 필요**: Track C 기존 통과 필링들(수백 건, `fin2/tests/test_pdf_*.py` 류
  회귀 스위트)에 새 헤더 파싱이 오검출(헤더를 잘못 찾아 `n_period_cols`를 틀리게
  판정)해 정상 필링을 오히려 결측 처리하는 회귀가 없는지 — 이번 구현의 핵심 위험은
  "탐지 놓침"이 아니라 "탐지 오검출로 인한 신규 결측"이다. §2-1 함수가 "애매하면
  None"을 엄격히 지켜야 하는 이유.
- Category C(1999~2003) 구형 서식은 헤더 문구 변형(구서식은 "과목" 대신 다른 표현,
  또는 헤더 자체가 없는 통짜-셀 표)이 있을 수 있어, 헤더 파싱 실패(`None`)가
  이 시대 문서에서 유독 자주 나올 수 있다 — 실패하면 **기존 동작 그대로**(폴백 없이
  현행 유지)이므로 안전하지만, 얼마나 자주 None이 나오는지 실측해 "이 재설계가 실제로
  얼마나 많은 문서에 적용되는지" 가늠은 필요.

## 4. 이번 세션 범위 (Phase 1) vs 후속 (Phase 2)

**Phase 1(이번 제안 범위)**: §2-1·§2-2 — 헤더 파싱 + 컬럼수 검증 게이트. 기존 3줄/
멀티라인 레이아웃 로직·`extract_tables()` 자체 로직은 무변경, 그 앞단에 검증 계층만
추가.

**Phase 2(후속, 이번엔 안 함)**: 기간 하나에 하위열이 더 있는 서식(3개월/누적 2단
헤더 등, IS/CF 일부)까지 헤더가 완전히 기술하게 확장하고, 그 경우엔 격자 추출을
기본으로 승격하는 것까지 고려. 지금은 범위 밖 — Phase 1 실측 결과 보고 재검토.

## 6. 구현 결과 — 실측으로 드러난 두 가지 "진짜" 근본원인 (2026-09-12)

Phase 1(§2)을 그대로 구현해 실제 솔트웨어 PDF에 돌려보니, 사용자가 원래 의심했던
"행 병합"(줄바꿈 유실)은 **이 파일에서는 실제로 일어나지 않았다** — pdfplumber로
직접 재추출한 텍스트는 줄바꿈이 멀쩡했다. 대신 §2 게이트가 실제로 잡아낸 진짜
원인은 두 가지, 전부 "반기"(半期)라는 단어 하나가 걸림돌이었다:

1. **주석번호 열 오인식** — "현금및현금성자산 4,5,6 2,351,294,869 2,403,931,716"에서
   "4,5,6"(주석 참조번호 목록)이 `_NUM_TOKEN_RE`엔 금액과 똑같은 모양이라 그대로
   숫자로 집혔다(그 결과 컬럼이 밀려 실제 값 대신 "456"/"45,718" 같은 엉뚱한 값이
   나왔었다). **수정**: `_looks_like_real_amount()` 신설 — 진짜 금액은 천단위 콤마
   그룹(첫 그룹 1~3자리, 나머지 정확히 3자리)인데 주석번호 나열은 자릿수가
   불규칙하다는 차이로 구분. `_parse_single_line()`/`_parse_numline_tokens()`
   (텍스트·격자·3줄 경로 전부 공유) 양쪽에 적용.
2. **"반기" 복합어로 인한 앵커 누락(더 심각)** — 기존 `_PERIOD_MARK_RE`("제 N 기"/
   "제 N 분기"만 인식)는 "제4(당)반기"("반"이 "기" 앞에 낌)를 전혀 못 잡는다. 이
   반기보고서는 포괄손익계산서·자본변동표·현금흐름표 제목이 전부 이 형태를 써서
   **앵커 자체가 하나도 안 잡혔다** — 그 결과 유일하게 잡힌 BS 앵커의 리전이 다음
   앵커 없이 문서 끝까지 뻗어나가, 현금흐름표·주석의 합계·소계까지 전부 "재무상태표"
   값으로 섞여 들어갔다(오염된 CSV 20~27행의 진짜 정체). **수정**: §2-1에서 이미
   만든 헤더용 정규식(`_HEADER_PERIOD_MARK_RE`, "반기말"/"분기말"/"반기"/"분기"까지
   인식)을 `_find_anchors()`의 앵커 확정에도 재사용 — 기존 패턴의 상위집합이라 이미
   맞던 필링은 그대로, "반기" 표현 때문에 앵커를 놓치던 필링만 추가로 잡는다.

**종단 검증**: 수정 전 27개 사실(대부분 오염 — 다른 표/노트 값이 BS로 섞임, 항등식
불성립) → 수정 후 별도 BS 17행(내부 정합: 자산총계=부채총계+자본총계 정확히 일치)
+ 별도 CF 11행(현금흐름표 전용 앵커로 정상 분리)으로 정리됐다. **`reconcile()`이
이제 이 basis를 T1(확신)로 자동채택**(`decision='pdf'`, 이전엔 'unresolved'로 사람
확인 대기열行이었음) — 강제 우회 없이도 자동 파이프라인이 신뢰할 만큼 좋아졌다는
뜻.

**검증**: `pytest tests/ fin2/tests/` 966 passed(구현 전 959 대비 +7 전부 신규, 기존
무관 실패 2건 그대로). 신규 테스트 8개(`fin2/tests/test_pdf.py`) — `_looks_like_
real_amount` 정오탐 각 1건, `_parse_pdf_table_header` 성공/None 각 1건,
`_lines_disagree_with_header` 1건, "반기" 앵커 회귀 1건, 실제 솔트웨어 PDF 종단
테스트 1건(파일 없으면 스킵).

**변경 파일**: `fin2/extract/pdf.py`만(`PdfTableHeader`/`_parse_pdf_table_header`/
`_lines_disagree_with_header`/`_looks_like_real_amount`/`_HEADER_PERIOD_MARK_RE`
신설, `_find_anchors`/`_parse_single_line`/`_parse_numline_tokens`/`facts_from_text`
수정). `docs/PARSING_RULES.md` R93으로 등재.

**Phase 2는 여전히 후속(§4 그대로)** — 이번 구현으로 실제 발견된 문제들은 전부
Phase 1 범위(헤더 파싱 + 검증 게이트) 안에서 해결됐다.

★**이 결론은 §7에서 정정됨** — BS/CF만 원문대조하고 IS는 확인을 안 해서 놓쳤을
뿐, Phase 2 사례(3개월/누적 2단 헤더)가 바로 이 필링에 실제로 있었다.

## 7. 후속(같은 날) — "손익계산서는 왜 누락되었나?" 질문으로 드러난 3중 원인
(R94, 2026-09-12)

§6 종단검증에서 "별도 BS 17행 + CF 11행"까지만 확인하고 IS는 확인하지 않았다.
사용자가 물어봐서 원문(page 16, 요약반기포괄손익계산서)을 다시 보니 **바로 이
필링에** §4가 "후속(Phase 2)"으로 미뤘던 3개월/누적 2단 헤더가 실제로 있었다 —
즉 "이번 사례엔 없었다"가 아니라 "확인을 안 해서 못 봤다"였다.

**세 원인이 순서대로 겹쳐 있었다** (하나씩 고칠 때마다 다음 원인이 드러남):

1. **헤더 서브컬럼 미인식** — 1단 헤더줄("제4(당) 반기 제3(전) 반기")엔 기간마커가
   2개뿐이지만, 바로 아래 2단 헤더줄("3개월 누적 3개월 누적")에서 각 기간이 다시
   둘로 갈라져 실제 데이터는 4컬럼이다. `_parse_pdf_table_header()`가 1단만 보고
   `n_period_cols=2`로 확정 → §2-2 최종필터가 진짜 4컬럼 데이터줄을 전부 걸러내
   IS가 통째로 0행이었다. 기존 `_is_interim_cumulative()`(누적열 채택용으로 이미
   있던 탐지)를 재사용해 이 신호가 있으면 컬럼수를 2배로.
2. **`_ANCHOR_LABELS["IS"]`가 흑자 워딩만 있었음** — ①을 고쳐도 여전히 0행. 이
   회사(SPAC, 손실기업)는 "영업손실"/"당기순손실"을 쓰는데 화이트리스트엔 "영업이익"/
   "당기순이익"류만 있어 "영업수익" 1건만 걸리고(≥2건 필요) 앵커 라벨 게이트 자체를
   못 넘었다 — §2 게이트(“진짜 본문표인지 확인”)는 정당하지만 화이트리스트가 흑자만
   대칭이었을 뿐. 적자 대응어 추가.
3. **BS 전용 부호규칙이 IS/CF에도 적용됨(가장 위험, 조용한 부호소실)** — ①②를
   고치니 IS 7행이 나왔는데 전부 양수(부호 소실)였다. `_parse_numline_tokens()`의
   "로마숫자 헤더행 = 괄호는 미리보기(양수), 진짜 음수 아님" 관례가 pre-2015 K-GAAP
   BS 전용으로 만들어졌는데 `statement` 구분 없이 라벨 패턴만으로 걸려 있었다 — IS의
   "Ⅲ.영업손실"/"Ⅷ.당기순손실"도 로마숫자로 시작하지만 미리보기가 아니라 그 자체가
   최종 소계이고 괄호는 진짜 음수다. ★같은 필링의 CF "Ⅰ.영업활동으로 인한
   현금흐름"도 이미 이 버그로 부호를 잃고 있었다(§6 시점부터 잠복 — IS 조사 중
   우연히 같이 드러남). `statement` 파라미터를 관통시켜 BS일 때만 이 관례를 적용.
