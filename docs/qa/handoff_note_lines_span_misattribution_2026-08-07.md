## 0. 한 줄

같은 날 앞선 세션이 "외화 열 헤더 인식 실패"라고 진단한 §4-1(POSCO INR 사례)을 원문과
나란히 대조했더니 **완전히 다른 원인**이었다: `parser/xml/table_extractor.py`의
`_get_cells()`/`extract_rows()`(본문 행 추출)가 **ROWSPAN·COLSPAN을 전혀 확장하지 않는다.**
헤더 쪽(`fin2/extract/report_lines.py::_build_col_labels`)은 (row,col) 그리드로 제대로
복원하는데, 데이터 행 쪽엔 그 로직이 없어서 원문에서 실제 `<TD>` 개수가 줄어드는 행마다
값이 엉뚱한 열 라벨을 달고 저장된다. **note_lines 전수 재파싱으로 정밀 계측 완료**:
값 2억4,550만 개 중 **2,819만 개(11.48%)가 잘못된 열에 귀속**, 필링의 **99.0%**가 영향권.
코드 수정은 아직 안 함 — **다음 세션 첫 작업 = 수정 로직 설계.**

**재검증 후 확정 요약(§8~§11)**: 결함·규모는 원문→DB 끝단 대조로 확정. 단
① 오귀속 11.48% 중 **값 자체가 망가진 것은 전체 값의 0.24%**(+누락 0.75%), 나머지 89.6%는
크기는 맞고 **열 정체(당기/전기 등)가 틀린 것** — 계층3에서는 여전히 실질 오류.
② **범위는 주석 경로 한정** — 본문 표는 실측 **0건**(코드 경로가 달라 자동 흡수).
③ "F1 회귀" 가설 기각(pre-F1 13.10% > post-F1 11.07%) — 구조적 결함.

**수정 계획(§15, 미실행)**: 원인은 한 지점이 아니라 **결합된 3개**(A 본문행 span 미확장=확정 /

## 1. 원인 — 2가지 독립 메커니즘, 같은 코드 결함

### 1-1. ROWSPAN 이어짐 (POSCO홀딩스 `20171114002151`)

지급보증 주석. 헤더 8열: `보증회사(ROWSPAN)|피보증회사(ROWSPAN)|보증제공처|통화|외화금액|
원화환산금액|외화금액|원화환산금액`. "SC Bank 등" 행은 앞선 행의 ROWSPAN(보증회사·
피보증회사)이 이어지는 행이라 실제 `<TD>` 개수가 6개뿐이다. 코드는 이 6개를 **항상
왼쪽부터 0번으로** 취급해 `외화금액`(7,350,000,000, 원문 그대로 병합 아님)이
`col_index=1, col_label="보증제공처"`라는 엉뚱한 자리에 들어가고, 그 라벨은
`NON_MONEY_COL_RE`에 안 걸려 백만원 배수(×1e6)를 그대로 먹어 `7,350,000,000,000,000`
(7.35경원)이 됐다.

### 1-2. COLSPAN'd 라벨 (풍강 `20150429000186`)

차입금 명세 주석. 헤더 5열: `차입금종류|차입처|이자율(%)|당반기말|전기말`. "합계" 행은
`<TD COLSPAN="3">합계</TD>`로 라벨이 3열을 병합한다 — 실제 `<TD>`는 라벨 포함 3개뿐인데,
코드는 여전히 "라벨 1개 + 나머지"로 가정해 `당반기말` 금액(6,713,681)이
`col_index=0, col_label="차입처"`(텍스트 전용 열)에 들어간다.

> ⚠**정정(§8 재검증)**: 초판은 여기에 "천원 배수(×1e3)를 그대로 먹었다"고 썼으나, **진짜 열
> (`당반기말`)도 같은 천원 열**이라 배수는 우연히 일치한다 — 즉 이 사례는 **값 오류가 아니라
> 라벨(열 정체) 오류**다. 값이 실제로 망가지는 것은 §1-1(POSCO) 유형뿐이며 그 비중은
> §9 의 `mult_bogus`(전체 값의 0.24%)다. 다만 라벨 오류도 계층3 에서는 실질 오류다(§9 참고).

→ **두 사례 모두 헤더 정규식 문제가 아니라 같은 근본 원인**: 헤더 그리드 복원
(`_build_col_labels`)은 ROWSPAN/COLSPAN을 계산하는데, 본문 행 추출(`_get_cells`/
`extract_rows`)은 매 행을 "물리적 `<TD>` 개수 = 논리적 열 개수"로 가정하고 위치만
본다. 원문에서 이 가정이 깨지는 모든 행(ROWSPAN 이어짐·COLSPAN'd 라벨)마다 그 이후
모든 값이 왼쪽으로 밀린 채 저장된다.

## 2. 폐기된 접근 — "행 모양(shape) 비교" 휴리스틱은 안 통한다

DB에 저장된 `col_index` 집합만으로 "다수 행과 다른 모양이면 결함"이라 잡으려 했더니
표본 4,000건 필링 중 **99.5%가 걸렸다** — 명백한 오탐. 원인: 열이 비어 있는 것(원문에
값이 없어 그 열이 자연히 안 채워짐)과 열이 밀린 것(값이 있는데 엉뚱한 자리로 감)을
`col_index` 존재 여부만으로는 구분할 수 없다. **DB에 이미 저장된 (밀린) 데이터로 밀림
자체를 재검출하려는 시도는 순환논리라 실패한다** — 원문 재파싱 없이는 진짜 정밀한 수를
낼 수 없다.

## 3. 정밀 전수조사 — 방법과 결과

### 방법

원문 XML을 다시 열어 헤더 알고리즘(`_build_col_labels`)과 **같은 (row,col) occupied-grid
방식을 본문 행까지 연속으로 확장**한 그리드를 별도로 구성했다(스크립트는 조사 전용,
파이프라인 코드는 무변경). 각 물리적 `<TD>`가 진짜로 차지하는 그리드 열(ROWSPAN 상속
칸은 건너뛰고, 자신의 COLSPAN만큼 칸을 차지)을 계산해 **현재 코드가 가정하는 열
(`offset + 물리적 위치`)과 대조** — 다르면 결함 1건으로 센다. 대상은 `assign_note_tables_
with_titles` + `_table_has_data_rows(minimum=1)`로 **실제 파이프라인과 동일한 표 모집단**을
사용했다(note_lines에 있는 필링과 1:1 대응).

검증: POSCO·풍강 두 확인 사례를 이 방법으로 돌리면 각각 352건·79건의 결함 값이 나와
원문 대조 결과와 일치.

### 결과 (101,327개 필링 전수, 오류 0건)

```
스캔한 값(주석 표 금액 셀)      : 245,499,415
컬럼 오귀속(진짜 열 ≠ 저장된 열) : 28,189,281   (11.48%)
오귀속이 발생한 행               : 12,011,666
결함이 하나라도 있는 필링        : 100,272 / 101,327   (99.0%)
소요                             : 8프로세스 병렬, 약 58분
```

⚠**"오귀속" ≠ 반드시 "value_won 값이 틀림"**: 진짜 열과 저장된 열의 단위(배수)가
우연히 같으면 숫자 자체는 맞을 수 있다(라벨/의미만 틀림 — 계층3 해석 단계에서는 여전히
문제). "값(magnitude) 자체가 틀린 것"만 별도로 센 숫자는 **아직 없음** — 필요하면
후속으로 산출 가능(진짜 열과 저장된 열의 `unit_source`/배수가 다른 경우만 별도 집계).

## 8. 결함 자체는 확실하다 — 원문 마크업으로 확정

### 8-1. census 가 파이프라인을 정확히 모델링했는지 (코드 대조)

`_emit_note_lines`(`fin2/extract/report_lines.py:614~661`) 는
`extract_rows(keep_all_amount_cells=True)` → `label, amount_cells = cells[0], cells[1:]`
(`table_extractor.py:254`) 로 **물리적 위치 그대로** 담고, `col_idx = enumerate(row.amounts)`,
`col_label = note_col_labels.get(col_idx)` 로 붙인다. `note_col_labels` 의 키는
`grid_col - offset`(`_build_col_labels:527`). 따라서 **저장 열 = `offset + (k-1)`** 이고,
이는 census 의 `assumed_col` 과 정확히 같다. 모델링 오류 없음.

**census 인공물 검사도 통과**: `for td in tr`(TR의 모든 자식)와 `_get_cells`(TD/TH/TE/TU만)
의 인덱스가 어긋나면 false positive 가 되는데, 결함 행 전수에서 **어긋남 0건**.

### 8-2. ★원문 → DB 끝단 대조 (텔코웨어 `20240814002630`)

```
원문 헤더 : <TD COLSPAN=2>구 분</TD> <TD>당반기말</TD> <TD>전기말</TD>
원문 행1  : <TD ROWSPAN=6>유동</TD> <TD>단기대여금</TD> <TD>398,691</TD> <TD>328,996</TD>
원문 행2  :                          <TD>미수수익</TD>   <TD>442,190</TD> <TD>470,100</TD>

DB 실제   : 미수수익 col_index=0 col_label='구 분'     442,190,000
            미수수익 col_index=1 col_label='당반기말'  470,100,000  ← 원문상 전기말 값
```

`ROWSPAN=6` 인 `유동` 이 이어지는 행이라 셀이 한 칸 밀렸고, **전기말 값이 `당반기말` 라벨을
달고 저장**됐다. 같은 표 안에서 같은 논리적 열이 행에 따라 col_index 0↔1 을 오간다 —
계층3가 col_index 로 묶을 수 없다는 뜻이다.

원문 마크업으로 같은 메커니즘을 확인한 필링(연도·업종 분산):
유진증권 `20220316000791`(구분 COLSPAN=2) · 미래에셋생명 `20170814001998`(구분
COLSPAN=2+ROWSPAN=2) · 유비벨록스 `20151113001035`(관계기업 ROWSPAN=5) ·

## 9. 규모는 맞다 — 다만 "11.5% 가 틀린 값"은 아니다

독립 재측정(무작위 표본, 원문 재파싱):

| 표본 | 값 | 오귀속 | 비율 |
|---|---|---|---|
| 150 필링 | 376,909 | 41,759 | 11.08% |
| 400 필링 | 986,909 | 101,892 | 10.32% |
| 250 필링 | 606,728 | 67,181 | 11.07% |
| **전수 (§3)** | 245,499,415 | 28,189,281 | **11.48%** |

→ 전수 census 수치는 **재현된다.** 과대계상 아님.

**★그러나 "오귀속"의 대부분은 값이 아니라 열 정체의 오류다** (400필링 표본, 결함 101,892건):

| 유형 | 결함 중 | 전체 값 중 | 뜻 |
|---|---|---|---|
| `label_diff` | 89.6% | 9.25% | 값 크기는 **맞고** 열(대개 당기/전기) 귀속이 틀림 |
| `mult_dropped` | 7.2% | 0.75% | `value_won` NULL — `value_raw` 남아 **회수 가능** |
| `mult_bogus` | 2.4% | **0.24%** | 비금액 열 배수를 먹여 숫자가 무의미(POSCO 7.35경 패턴) |
| `label_same` | 0.8% | 0.09% | 진짜 열과 저장 열의 라벨이 같음 — **무해** |
| `mult_scale` | 0.0% | 0.00% | 서로 다른 금액 배수 — 표본 0건 |

즉 **숫자 자체가 망가진 것은 전체 값의 0.24%, 누락 0.75%.** 나머지 89.6%는 크기는 맞고
**정체가 틀린** 것이다. ⚠**이것이 무해하다는 뜻은 아니다** — `fin2/layer3/note_da.py`
(`note_periods` 의 COL_LABEL 규칙)가 `col_label` 로 기간(3개월/누적·당기/전기)을 판정하고,
`fin2/extract/units.py` 가 `col_label` 로 배수를 정한다. 표본 대표 사례가
`stored '당기' / true '전기'` 였다.

밀림 방향 분포: `+1` 81.1% · `+2` 13.3% · `+3` 4.0% · `+4~+6` 1.6% · `-1/-2` 5건(무시 가능).

## 10. ★범위는 주석에 한정 — 본문 표는 실측 0건

§5 가 "추정"으로 남긴 것을 실측했다. 방법: 본문 섹션(`DART_BODY_SECTIONS` +
`SEC_LEGACY_FS`)의 모든 표에 대해, ⓐ 파이프라인이 물리적 셀로 산출하는 금액 배열과
ⓑ ROWSPAN/COLSPAN 을 **확장한 행**으로 산출한 금액 배열을 행 단위로 비교(동치성 검사).

```
표본 250 필링 · 본문 표 1,867 · 행 66,099 · 값 145,045
span 확장이 산출 금액을 바꾸는 행 : 0 (0.000%)
바뀌는 값 슬롯                    : 0 (0.000%)
```

**0건인 이유는 "본문 표가 단순해서"가 아니라 코드 경로가 다르기 때문이다.** 본문은
`extract_rows(keep_all_amount_cells=False)` → `_split_label_amounts` 가 **비숫자 셀을
걷어내고 금액을 왼쪽으로 당긴다.** ROWSPAN 이어짐으로 앞 셀이 없어져도 결과 금액 배열이
같아진다(자동 흡수). 주석만 F1(2026-07-31)로 **위치를 보존**해서 노출된다.

→ **수정 범위는 주석 경로로 한정해도 된다.** 본문 재적재 불필요. (SCE 는 여전히 미측정.)

**부수 확인 — "F1 회귀 아니냐" 가설은 기각.** 같은 표에 pre-F1 방식(`_split_label_amounts`
+ `_build_col_labels(all_cells=False)`)을 적용해 같은 그리드 정답과 대조한 결과:

```
post-F1 (현재) : 67,181 / 606,728 = 11.07%
pre-F1  (종전) : 78,287 / 597,658 = 13.10%
```

**F1 이전이 오히려 더 나빴다.** F1 은 원인이 아니라 소폭 개선이었고, 이 결함은 처음부터
있던 구조적 결함이다. (역으로 "F1 을 되돌리면 된다"는 선택지는 없다.)

> ⚠**§11 의 후보 규칙은 이후 측정으로 반증됐다** — "L = 선행 비금액 열" 은 결함 없는 표의
> 8.5% 에서 현재 `offset` 과 불일치해 **멀쩡한 표를 새로 망가뜨린다.** 대체 규칙 확정은
> `docs/plans/note_span_fix_plan_2026-08-07.md` **Phase 1(T1.1)** 로 이관.

## 11. ★수정 설계 함정 — `offset` 도 같이 재정의해야 한다

`_build_col_labels` 의 `offset = width - n_amounts` 에서 `n_amounts` 는
**데이터 행의 물리적 셀 수 최댓값**(`max(len(_get_cells(tr)) - 1)`)으로 구한다
(`report_lines.py:487~494`). 본문 행을 span 확장하면 이 수가 바뀌므로,
`_get_cells`/`extract_rows` 만 고치고 `_build_col_labels` 를 그대로 두면
**열 라벨 사전이 통째로 어긋난다**(값은 제자리를 찾는데 라벨이 밀리는 반대 방향 사고).

실측 예(유진증권 `20220316000791` table 4): 그리드 폭 4, 라벨 영역이 행마다 다르다
(COLSPAN=2 인 행 / 2열로 쪼개진 행 혼재) → `n_amounts=3`, `offset=1` 이라
`col_labels[0]` 이 금액 열이 아니라 `'구 분'`(라벨 열)이 된다. span 확장 후에는
"앞쪽 몇 열이 라벨 영역인가"를 물리적 셀 수가 아니라 **확장된 그리드**에서 정의해야 한다.

또 하나: 풍강 table 27 처럼 ROWSPAN 이어짐 행은 **행 라벨 자체도 상속**된다
(`<TD>단기차입금</TD><TD>5,000,000</TD>` 의 진짜 행 정체는 `토지,건물,기계장치` 행의 하위).
`label_raw` 를 어떻게 할지도 설계 대상이다 — 값 열만 고치면 행 정체는 여전히 부분적이다.
