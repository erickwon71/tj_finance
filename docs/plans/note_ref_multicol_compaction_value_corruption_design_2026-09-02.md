# 계층2 — 다열(multicol) 압축 경로 주석번호 값오염 설계 (2026-09-02)

배경: [[std-v3-upstream-defects-r62-and-monotonicity-2026-09-02]] 후속 후보②
(잔존 단조성위반 TINY_VALUE_BUG 클래스, 56건) 표본 원문대조 중 우연히 발견한
**별개의, 훨씬 큰 계층2(layer2) 원천 버그**. 이 문서는 원인규명+범위추정
결과를 정리한다. **구현 미착수 — 설계·범위확정까지만(CLAUDE.md 정책).**

## 1. 근본원인(확정, 재현 코드로 검증)

`fin2/extract/report_lines.py::_emit_body_lines()`(또는 동등 함수)의 "보험/
증권 기간당 다열(multicol) 포맷" 압축 경로:

```python
elif multicol:
    # 기간당 다열: 비어있지 않은 금액을 압축 → [당기, 전기, 전전기] 로 매핑.
    present = [a for a in row.amounts if a is not None]
    pairs = list(enumerate(present[:n_periods]))
```

`row.amounts`는 `parser/xml/table_extractor.py::_split_label_amounts_ex()`가
만든다. 이 함수의 "주석번호 열 건너뛰기" 로직(R19, 2026-08-24 Gate B 버그①로
이미 한 번 강화됨)은 `table_has_note_column`이 True일 때만 작동하고, 이 값은
`_table_has_comma_note_column()`이 **그 표 안 어딘가에 콤마로 묶인 다중
주석참조("10,37" 등)가 있어야만** True를 준다.

**갭**: 어떤 필링에서는 매 행이 주석을 하나씩만 인용하고(콤마 다중참조가
단 한 번도 안 나옴), `table_has_note_column`이 영원히 False로 남아 안전장치가
발동하지 않는다. 그러면 라벨 바로 다음 칸의 주석번호("5"/"21"/"22" 등, 콤마
없는 단일 숫자)가 진짜 금액 후보로 그대로 살아남고, multicol 압축이 "None
아닌 값 순서대로"만 위치를 매기다보니 주석번호가 `present[0]`(col_index 0,
"당기" 슬롯)을 차지해버린다. **진짜 당기 금액은 한 칸씩 밀려 다음 슬롯("전기")
으로 오분류**되고, FY(사업보고서) 기간에서는 col_index≥1 이 "전기 재게재"로
간주돼 하류에서 버려지는 경로가 있어(추정, 미확정) **진짜 금액 자체가
소실**되는 경우도 확인됨(§3-1).

### 1.1 재현(합성 XML, DB 비의존)

```python
# _table_has_comma_note_column()+_split_label_amounts_ex()+extract_rows() 를
# [라벨, 주석="5", 공란, 당기금액, 공란, 전기금액] 6열 행에 직접 호출:
row.amounts == [5, None, 45830369541, None, 50367549269, None, None, None]
# multicol 압축: present[:2] = [5, 45830369541]
# → col_index0=5(오염), col_index1=45,830,369,541(진짜 당기값, "전기"로 오분류)
```

## 3. 규모 추정 — 2단계(고신뢰 vs 광의)

### 3.1 고신뢰 신호: "같은 표 안에서 서로 다른 라벨 2개 이상이 완전히 동일한
극소값(1~500원)을 공유"

서로 다른 계정과목이 우연히 정확히 같은 원 단위 극소값을 갖는 건 실질적으로
불가능(같은 주석번호를 여러 계정이 공유하거나, 순번이 같은 표 안 다른
소계에 흘러든 경우만 설명 가능) — 오탐 위험이 극히 낮다.

```sql
-- col_index=0, value 1~500, EPS(주당) 라벨 제외, statement in (IS,CF,SCE) 기준
-- 같은 (rcept,statement,basis,table_seq)에서 같은 value_won 이 2개+ 라벨에 나타나는 그룹
```

**결과: 3,610개 (표,값) 그룹 / 296개사 / 1,116개 필링 / 8,783개 셀.**

표본 재확인(6건, IS+CF 섞어서, 2007/2016/2019/2023 다양화):
- 00113191(2019 CF consolidated): "손익조정항목"=34, "자산ㆍ부채의 변동"=34 —
  둘 다 원래 하위 세부항목들의 **소계**여야 하는 섹션 헤더 행인데 완전히
  동일한 극소값 — 주석 순번 공유로 강하게 의심.
- 00104856(2016 CF consolidated): "(2) 손익조정사항"=32, "(3) 자산ㆍ부채의
  증감"=32 — 같은 패턴.
- 00113058(2023 IS consolidated, 보험사): "I. 보험영업손익"=21, "II.
  투자영업손익"=21 — 같은 패턴, **보험사 특유 6열 구조 문서에서도 재현**
  (원래 R19 문서가 "보험/증권" 을 명시적으로 언급한 그 업종군).
- 01108442(2019 CF separate): "당기손익인식금융자산의처분"=9, "기타포괄손익
  -공정가치측정금융자산의처분"=9, "당기손익-공정가치측정금융자산의취득"=9,
  "기타포괄손익-공정가치측정금융자산의취득"=9, "매도가능금융자산의취득"=9
  — **서로 다른 5개 계정이 전부 "9"** — 같은 주석(아마 "금융상품" 주석
  9번)을 공유하는 게 실제로는 자연스러운 회계관행이라, 이 경우엔 **극단적
  다중공유가 오히려 진짜 버그의 증거**(우연으로는 설명 불가).

### 3.2 광의 신호(느슨, 오탐 섞임): "col_index=0에 극소값(1~500, EPS 제외) 3개+
와 거액(≥100만원) 3개+가 같은 표에 공존"

**결과: 997개 표 / 184개사 / 668개 필링 / 8,695개 셀**(주당 라벨 제외 기준).
표본 확인 결과 이 신호엔 **진짜 미세 금액**(중단영업손익이 우연히 300원대
등, 00249982 표본)도 일부 섞여 있어 §3.1보다 오탐률이 높다 — 상한선으로만
참고.

## 4. 오탐 가드(§3.1/§3.2 조사로 확정된 것)

- **EPS(주당) 라벨은 반드시 제외**(`label_raw like '%주당%'`) — 옛 포맷
  필링은 EPS가 본류 IS에서 안 걸러져 남아있는 경우가 있어(2012년 이전 표본,
  §3 원본 조사 참고), 진짜 작은 원/주 값이 대량 오탐을 만든다.
  ★2026-07-31 F1 이후 신규 경로는 "주당손익(EPS)은 별도 EPS 패스로 전사"
  하지만(`report_lines.py` 495~500줄), **옛 필링·구경로엔 이 분리가 적용
  안 됐을 가능성**(미확인) — 후속 조사 필요.
- **중단영업손익류(discontinued operations)** 는 진짜 근소값(수백원 단위)일
  수 있음(00249982 표본) — 탐지규칙에서 완전 배제는 안 되지만 "다른 계정과
  값이 겹치는지"(§3.1 신호)로 걸러지면 오탐 가능성 낮음.

## 5. 제안 탐지·수정 방향(미검증, 다음 세션 설계 확정 필요)

### 5.1 근본 수정 — 헤더 기반 주석열 확정(제안, 미검증)

`_table_has_comma_note_column()`이 데이터 행의 콤마 다중참조에만 의존하는
대신, **헤더 행(THEAD)의 TH 텍스트에 "주석"이 있는지**를 1차 신호로 추가.
00537337/00132202 둘 다 헤더에 `<TH>주석</TH>` 명시 확인됨 — 구조적으로 훨씬
신뢰도 높은 신호. **확인 필요**: `table_direct_rows()`가 THEAD 행을 포함하는지
(현재 `_table_has_comma_note_column()`엔 TBODY 행만 전달되는 것으로 보임,
`report_lines.py:262`의 `trs` 소스 재확인 필요).

### 5.2 대안 — multicol 압축 경로 자체에 주석열 인식 추가

헤더 신호가 안 미더우면, multicol 압축 시점(`present = [a for a in
row.amounts if a is not None]`)에서도 **라벨 다음 칸이 콤마 없는 소수(小數)
자릿수 정수**면 압축 전에 별도 스킵하는 규칙을 추가(단, "진짜 소액금액"과
구별 안 되는 R19의 원래 딜레마가 여기서도 그대로 적용됨 — 헤더 신호와
병행이 안전).

### 5.3 미결정사항

1. 5.1(헤더기반)과 5.2(값기반 폴백) 중 무엇을 우선 적용할지, 혹은 병행할지.
2. 계층2 재추출 범위 — 영향받는 게 §3.1 기준 최소 1,116개 필링인데, 이
   필링들만 표적 재추출할지, 전수(모든 필링) 재검사가 필요한지(탐지규칙
   자체가 바뀌므로 **잠재적으로 이 신호에 안 걸렸던 필링도** 재검토 대상일
   수 있음 — 예: 값 자체가 겹치지 않게 우연히 배치된 케이스는 §3.1로도
   못 잡음).
3. FY 기간 col_index≥1 "전기 재게재로 간주해 버림" 경로의 정확한 위치·조건
   확인(§1의 "진짜 금액 소실" 메커니즘 완결에 필요, 아직 코드 라인 특정 안 됨).
4. std_v3/Gate B 파급범위 재검토 — revenue/영업이익/당기순이익/법인세비용 등
   DIRECT_MAP 핵심계정이 다수 걸려 있어 R63급 이상으로 클 가능성.
