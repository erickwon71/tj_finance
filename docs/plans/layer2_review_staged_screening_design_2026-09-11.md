# 계층2 재적재+원문대조 캠페인 — 시대 구분 + 스크리닝 우선순위화 (설계, 2026-09-11)

**상태**: ✅1단계(2015+) v1 구현 완료 + 검증 완료(2026-09-11, 사용자 지시로 착수).
사용법은 §7 참고.

**배경**: 기존 [[layer2-reload-review-campaign-2026-09-08]] 캠페인은 시총순 × 회사 내
최신→과거로 **전수를** 순서대로 검토한다. 삼성전자 2015 사업보고서까지 진행하며 몇 건
파서 버그를 발견·수정했는데, 그 발견 계기가 "BS/IS/CF 항목수가 비정상적으로 적거나
많다"는 사람의 육안 판단이었다. 2015+ 구간만 정기공시 **107,468건**(전체 190,973건 중)
— 이 규모를 전부 순서대로 눈으로 보는 건 비현실적이라, 자동 스크리닝으로 의심되는
건부터 먼저 확인하도록 우선순위를 재편한다.

## 1. 시대 구분 (4단계, `docs/PARSING_RULES.md` R13/R14 근거)

| 단계 | 구간 | 근거 |
|---|---|---|
| **1단계(지금)** | 2015~현재 | 현행 XBRL 표준서식(`ifrs-full` 위주) |
| 2단계 | 2011~2014 | R14: 구형 IFRS taxonomy, `TITLE` 태그 소멸 — XBRL 과도기 |
| 3단계 | 2007~2010 | 2007 taxonomy(IFRS 이전 K-GAAP), pre-2010 EUC-KR 경계 |
| 4단계 | 1999~2006 | SGML/PDF 위주, Category C(html_viewer Track C 93건과 겹침) |

**★사용자 결정 1차(2026-09-11, 삼성전자 2015+ 완료 시점)**: 처음엔 "회사 진행
순서(한 회사를 끝까지 본 뒤 다음 회사로)는 그대로 유지, 시대구분은 스크리닝
스코프에만 적용"으로 결정 — 삼성전자가 2015+를 마쳐도 다음 회사로 안 넘어가고
1999~2014를 이어서 보는 **미구현** 상태였다.

**★★사용자 결정 2차(같은 날, 뒤집음)**: "기간 구간으로 나눠서, 중요도 있는
기간부터 먼저" — **시대(era)를 회사 순서보다 상위 우선순위로 게이트화**하기로
확정. `_pick()`의 `ORDER BY`에 `era_rank`(위 표 그대로: 2015+=1, 2011~14=2,
2007~10=3, 1999~2006=4)를 최우선으로 추가 — **모든 회사의 2015+ pending 이
전부 없어져야** 2011~2014 로 넘어간다(같은 시대 안에서는 시총순 그대로).
별도 상태·플래그 불요 — ORDER BY 한 줄로 자동 성립(그 시대 pending 이 남아있는
한 그 시대 행의 era_rank 가 항상 더 작아 먼저 뽑힌다). 구현: `scripts/layer2_
review.py::_pick()`. **적용 즉시 효과**: 지금 판정 대기 중인 삼성전자 2014Q3
(reloaded)를 pass/fail 하고 나면, 다음 `next`는 삼성전자의 1999~2014 잔여
62건이 아니라 **다른 회사의 2015+ pending**(예: SK하이닉스 2015FY 걸린 건,
실측 확인)으로 넘어간다 — 회사가 바뀌는 게 정상 동작이다.

2~4단계 정확한 경계는 1단계 진행하며 필요시 조정. 지금은 **1단계만** 설계.

## 2. 사용자 결정 (2026-09-11)

- 스크리닝에서 안 걸린("깨끗해 보이는") 건은 **전수 검토 원칙은 유지하되 뒤로 미룬다** —
  건너뛰거나 자동 pass 처리하지 않는다. 걸린 건부터 먼저 사람이 직접 확인.

## 3. 스크리닝 방법 — 기존 자산 재사용 + 저비용 사전 스캔

**핵심 설계 결정**: 스크리닝 단계는 **파일을 다시 파싱하지 않는다.** 지금 DB에 이미
적재된 `report_lines`(과거 파서 버전 결과일 수 있음) 위에 순수 SQL/Python으로 계산한다
— 이유: 107K건을 전부 실제로 재추출(원본 문서 다시 읽고 파싱)하면 무거운 배치가 되는데,
어차피 사람이 실제로 검토하는 시점(`layer2_review.py next`)에 **현재 파서로 재적재**가
다시 일어난다. 스크리닝은 "어디부터 볼지 순서만 정하는" 저비용 사전 신호면 충분하다.

**재사용(신규 코드 최소)** — 전부 `fin2/audit/layer2_selfcheck.py`에 이미 존재:
1. `check_row_count_outlier` — 같은 회사 내 다른 기간 대비 행수 ±50% 이탈
2. `check_scope_presence` — 있어야 할 BS/IS/CF/SCE가 통째로 빠짐
3. `check_bs_balance` / `check_cf_closing_cash` / `check_bs_rollup` / `check_is_waterfall` — 항등식 불일치
4. `check_unit_sanity` / `check_duplicate_rows`
5. 전사 로그-IQR 스캔(`docs/qa/report_lines_row_count_outlier_scan_2026-09-08.md` 방법론) —
   같은 statement × 기간유형 전체 회사 분포에서 벗어난 값. 2015+ 스코프로 재실행.

**선택(1단계 필수 아님, 후보로만 남김)**:
6. 원본 문서 크기 대비 추출 행수 비율(절단/인코딩 방어선)
7. DART 웹뷰어(`fin2/extract/html_viewer.py`) 재추출 대조 — 2015+ 레이아웃 미검증, 파일럿 필요
8. DART Open API 표준계정과목 API를 검증 전용(적재 아님) 제3신호로 — "로컬 문서에서만
   적재" 원칙과 별개 문제이나 사용 여부는 미결정, 필요시 별도 승인받고 착수

## 4. 스키마/실행 변경 (초안 — 구현 시 확정)

- `Layer2ReviewQueue`에 신규 컬럼: `screen_flags`(JSON, 어떤 check가 왜 걸렸는지)
  `screen_severity`(정수, 정렬용). 기존 사람 판단 컬럼(`status`/`note`/`reviewed_at`)과
  기존 진행순서 컬럼(`corp_rank`/`seq_in_corp`)은 건드리지 않는다(ReconCandidate 관례 유지).
- `init`을 2015+ **전체 유니버스**로 확장 실행(지금은 상위 21개사만 큐에 있음) — 이때
  스크리닝 계산을 같이 돌려 `screen_severity`를 채운다.
- `next`의 선택 순서(`_pick`/`_current`)에 `screen_severity DESC`를 1순위로 추가하고,
  기존 `(corp_rank, seq_in_corp)`는 2차 정렬로 유지 — "걸린 건부터, 그 안에서는 시총 큰
  회사부터"가 되도록.
- 실제 재적재·CSV·확정 pass/fail 흐름은 **지금과 완전히 동일**(`next`/`pass`/`fail`/`redo`) —
  바뀌는 건 순서뿐, 검토 절차 자체는 안 바뀐다.

## 5. 실행 방식

- 스크리닝 배치(신규 스크립트, 가칭 `scripts/layer2_screen_2015plus.py`)는 읽기 전용 SQL
  집계 위주라 가볍지만, 107K건 스캔은 그래도 시간이 걸릴 수 있어 사용자가 직접 터미널에서
  실행하도록 안내한다([[feedback-long-running-commands]]).
- 결과는 큐 갱신(위 §4) + 요약 리포트(걸린 건수/사유별 분포)로 사용자에게 먼저 보여주고,
  그 다음 `next`부터는 순서만 바뀐 채로 지금 쓰던 흐름 그대로 진행.

## 5-1. 파일럿 검증 (2026-09-11, 삼성전자 2015+ 46건 = 사용자 확인완료 그라운드트루스)

읽기전용으로 직접 실행해 확인:
- 기존 8종 자동검산(`check_status`, 이미 저장돼 있던 값) — 46건 전부 `ok`.
- §3-5(전사 log-IQR, 2015+ 스코프로는 이번에 처음 실측) — 2015+ 전체(BS/IS/CF ×
  FY/H1/Q1/Q3, 버킷당 표본 최소 43,082건)로 상하한 계산 후 삼성전자 46건×276개
  (statement,basis) 셀 대조 → **걸린 것 0건**(오탐 없음, 스크립트:
  `screen_pilot_samsung.py`, 세션 스크래치패드, 재현 가능하나 휘발성이라 필요시 재작성).

**★반례 발견 — item-count 스크리닝의 사각지대**: 이번 캠페인이 삼성전자 2015+에서
실제로 찾은 진짜 버그 R85/R86/R88(위 §미조치 참고, `docs/PARSING_RULES.md`)은 전부
"행수는 그대로인데 값이 다른 기간 컬럼과 뒤바뀐" 유형(2단헤더 3개월/누적 혼동·주석열
오판정으로 인한 전기↔당기 둔갑·표구조 사후추측 컬럼밀림)이다. **행수 기반 스크리닝
(§3의 1~5번 전부)으로는 이 세 버그 중 어느 것도 원리적으로 못 잡는다** — row count가
불변이기 때문. 즉 item-count 스크리닝은 결측/중복/통째로 빠진 표 유형(예: 기존
LS네트웍스 IS 7행 결손 사례)에는 유효하지만, 이번 캠페인의 실제 성과였던
"기간-컬럼 뒤바뀜" 유형에는 무력함이 실측으로 확인됨.

**보완 기법 제안(§3에 9번으로 추가) — R85 재현으로 회수율 검증 완료(2026-09-11)**:
9. **기간 연속성 대조** — 어떤 필링의 "당기" 값을 그 다음 필링(다음 분기/연도
   보고서)이 같은 기간을 "전기"로 표시한 값과 비교. 정상이면 일치해야 하는데
   R85/86/88류는 이게 어긋난다. `fin2/reconcile.py`/Gate B의 "형제 rcept 대조" 패턴
   (예: [[gateb-trade-payables-stale-subline-r42-2026-08-21]])을 report_lines
   레벨로 가져오는 형태.

   **★중요 제약(구현 시 필수)**: `store_report_lines()`는 **당기(col_index=0)만
   적재한다**(사용자 결정 2026-07-30) — DB `report_lines`에는 전기/전전기 컬럼이
   아예 없다. 그래서 이 기법은 SQL 한 방으로 안 되고, **비교 대상 필링(다음
   분기/연도)을 그때그때 `extract_report_lines()`로 재추출(저장 안 함, 메모리限)
   해서 그 전기 컬럼만 뽑아 비교**해야 한다 — §3의 1~8번(순수 SQL, 무거운 재파싱
   불요)과 비용 성격이 다르다.

   **회수율 검증(R85, git worktree로 버그 재현 후 실측)**: `9fed388~1`(R85 수정
   직전 커밋) 코드로 20250814003156(삼성전자 2025H1)을 재추출 → 별도 기본주당이익
   "당기"(col=0) = **411**(버그값, 실제로 이 코드였다면 이 값이 DB에 저장됐을
   것). 다음 필링(20260814003699, 2026H1, 이미 신코드로 재적재·pass 확정)을
   재추출해 그 "전기"(col=1, context_fy=2025) 컬럼만 뽑으면 = **1360**(현재 DB에
   실제 저장된 올바른 값과 정확히 일치). **411 ≠ 1360 — 3배 이상 어긋나 즉시
   걸린다.** item-count 스크리닝은 이 버그를 못 잡았지만(§5-1 위 내용), 기간
   연속성 대조는 **잡는다**는 것을 실측으로 확인.

   **R86/R88도 같은 방식으로 재현·검증(2026-09-11)**:

   - **R86(20200330003851, 2019FY)**: 재현 성공 — OLD가 "당기(2019)"로 채운 값들
     (예: BS별도 장기매도가능금융자산=973,353,000,000)이 NEW에서는 전부
     **context_fy=2017(전전기)**로 정확히 재배치됨(당기(2019)엔 None=진짜 결측).
     같은 실패군(컬럼 오선택) 확인. 다만 **여기 걸린 계정들("매도가능금융자산"
     계열)은 2018년 IFRS9 전환으로 이후 필링에서 아예 없어진 구계정**이라, 다음
     필링(2020FY, `20210309000744`)을 재추출해도 이 라벨 자체가 **한 줄도 안
     나옴** — "다음 필링의 전기 컬럼과 직접 대조"가 성립할 비교 대상이 없다.
     → **보완 규칙 필요**: 그 라벨이 인접 필링 어디에도 전혀 재등장하지 않는데
     "당기"값이 찍혀 있으면 그 자체로 의심 신호(직접 값대조가 안 되면 "무대조
     상태로 당기 클레임" 자체를 플래그).
   - **R88(20170515003806, 2017Q1)**: 재현 성공, 더 극적인 사례 — OLD가
     "당기(2017)"로 채운 값(예: 단기매도가능금융자산의 처분=650,743,000,000)이
     NEW에서는 **context_fy=2016**(통째로 1년 밀림)이고, NEW는 추가로 2015·
     2014년치까지 복원(OLD는 4개 열짜리 표를 3개로 뭉개 가장 오래된 열을 유실).
     이 표는 표준 분기 CF(당기/전기 비교)가 아니라 **다년도 요약참고표**로
     보이는 특수 표라, 다음 분기(2018Q1, `20180515001699`)를 재추출해도 이
     라벨들이 **한 줄도 안 나옴** — R86과 같은 한계.

   **종합 판단**: "기간 연속성 대조"는 R85처럼 **매 필링 표준 주기(EPS/BS/IS/CF의
   일반 당기·전기·전전기 컬럼)로 반복 등장하는 라벨**에는 직접·확실하게 통한다
   (실측 확인). R86/R88에서 우연히 뽑힌 구체적 사례들은 **비주기적(1회성 요약표·
   폐지계정)** 라벨이라 "다음 필링과 직접 대조" 자체가 성립하지 않았다 — 기법의
   실패가 아니라 **적용 범위의 한계**(주기적 라벨만 직접 대조 가능, 비주기 라벨은
   위 보완규칙 "무대조 당기 클레임 자체를 의심" 정도로만 커버). 세 버그 다 실제
   버그였다는 점에서 스크리닝 가치 자체는 재확인됨.

   **★구현 중 발견한 세 번째 한계(2026-09-11, 재사용가능 도구로 일반화하며 발견)**:
   BS는 분기/반기(interim) 필링에서 전기·전전기 컬럼이 "1년 전 같은 날"이 아니라
   **직전/전전 회계연도 말**이다(국내 IFRS 관행 — 예: 2025H1의 전기말은
   2024-12-31, 2024H1이 아니다). 그래서 "다음 필링, 같은 fiscal_period"규칙을
   BS에 그대로 적용하면(H1↔H1) 전 항목이 오탐으로 뜬다(실측: 자산총계까지
   포함해 BS 항목 전부가 "불일치"로 나왔다가, BS를 FY 필링에만 적용하도록
   제한하니 해소). **IS/CF는 영향 없음**(당기/전기가 항상 "같은 기간, 1년 전"이라
   원래 가정이 맞음 — 2025H1↔2026H1 IS/CF 116개 항목 중 102개 정확 일치로 확인).
   구현에 반영: `scripts/layer2_period_continuity_check.py`가 대상 필링이
   FY가 아니면 BS는 검사 대상에서 뺀다.

## 6. 열린 질문 → 구현 시 결정 확정

- ✅회사 단위는 시총순 그대로 유지, **회사 안에서만** screen_severity>0 인 보고서를
  먼저 본다(기본안대로 확정·구현). 전체를 severity로 뒤섞는 안은 채택 안 함 — 원하면
  `scripts/layer2_review.py::_pick()`의 `ORDER BY` 한 줄만 바꾸면 되므로 나중에도 쉽게
  바꿀 수 있다.
- ✅`screen_severity` = 걸린 check들의 가중치 합(차단=3/의심=2/참고=1, 전사 log-IQR=2).
  실측하며 조정 가능(모두 §7의 스크립트 상수 하나 값).

## 7. 구현·사용법 (2026-09-11, v1 완료)

**변경 파일**: `collector/models.py`(`Layer2ReviewQueue` 컬럼 3개 추가), `collector/db.py`
(마이그레이션), `scripts/layer2_review.py`(`init --fiscal-year-min`, `_pick()` 순서),
`scripts/layer2_screen.py`(신규 — item-count 스크리닝), `scripts/layer2_period_
continuity_check.py`(신규 — 기간 연속성 대조, 단건 트리아지용).

**검증**: SK하이닉스(00164779) 2015+ 51건 스캔 실측 — 2건 걸림(cf_closing_cash
차 30,000,000원, `screen_severity=3`), `_pick()` 순서가 그 2건을 seq_in_corp 순서보다
앞으로 끄집어내는 것 SQL로 직접 확인. `layer2_period_continuity_check.py`는 R85
필링(2025H1)에서 재검증(102/116 일치, 1건 불일치)·R86 필링(2019FY)에서 재검증
(204/214 일치, 2건 불일치) — 둘 다 낮은 오탐률로 동작 확인(전부 §5-1에 기록한
BS-interim 한계 수정 반영 후).

**실행 순서**:

```bash
python scripts/layer2_review.py init --fiscal-year-min 2015 --top 0
```

```bash
python scripts/layer2_screen.py scan --fiscal-year-min 2015
```

```bash
python scripts/layer2_screen.py report --top 30
```

```bash
python scripts/layer2_review.py next
```

첫 명령은 큐를 2015+ 전체 유니버스(약 2,500개사)로 확장, 두 번째는 그 전체를
스크리닝(시간 걸림 — 직접 실행 권장, [[feedback-long-running-commands]]), 세 번째는
결과 미리보기, 네 번째부터는 **기존과 완전히 동일한 흐름**(`next`/`pass`/`fail`/
`redo`) — 순서만 회사 안에서 걸린 건 우선으로 바뀐다.

특정 건이 걸린 이유가 "값은 있는데 기간이 뒤바뀐" 쪽인지 의심되면(항등식/행수는
정상인데 뭔가 이상해 보일 때) 단건으로:

```bash
python scripts/layer2_period_continuity_check.py --rcept <rcept_no>
```
