# 주석↔본문 재무제표 분리 재설계 — 계획서 (2026-07-17)

> **상태: 계획(미실행).** CLAUDE.md 정책에 따라 이 문서는 검토용이며, 실행은 사용자의
> 별도 명시 요청이 있을 때만 시작한다.

## 0. 배경 — 이 조사를 촉발한 질문

`extended_financials_n_facts_outlier` 트리아지
(`triage_extended_financials_n_facts_outlier_2026-07-17.md`) 중, 사용자 질문:
**"보고서 파싱하고 DB 적재할 때 주석에서 read한 재무 관련 data는 어떻게 처리하나?"**
→ 확인 과정에서 **주석 데이터가 본문 재무제표 필드를 오염시켜 소비계층까지 도달**한
사실을 발견했다. 사용자 요구: *"주석에서 읽은 내용은 주석에서만, 본문 재무제표와 완전히
구분되어야 한다. 전체 재파싱·DB 재구성 각오도 되어 있으니 명확하게 구분할 수 있어야 한다.
프로젝트 목표는 정확한 재무데이터 확보다. 주석의 내용도 같이. 하지만 주석은 주석."*

## 1. 확정된 사실 (전부 실측·검증됨)

### 1-1. 현행 설계 원칙은 올바르다
- **1차 경로**(`fin2/extract/text.py::_detect_body_statement_tables`)는 표제 앵커
  (`fin2/extract/statement_titles.py`)로 주석을 배제한다. `_TITLE_EXCLUDE`(주석|요약|명세…),
  `_FACE_TITLE_START`(재무제표명이 표제 **시작**에 와야 함), `_PERIOD_AFTER`(직후 기간마커).
  코드 주석에 "주석표 천원 단위 값이 face 를 ×1000 오염시켜서 넣은 가드"라고 명시돼 있다.
- **의도적 주석 수집**은 `note.*` 네임스페이스로 격리한다(현재 fact_v2 에 11종·약 4.3만 팩트:
  note.da_total 11,592 / note.employee_benefits 10,578 / note.raw_materials_used 7,710 /
  note.depreciation 7,221 / note.amortization 4,757 / note.rou_depreciation 993 …).
  `rules.py::rule_additive_da` 가 `_DEP_CANON` 에 note.* 를 포함해 소비 → 본문에 D&A 가 없는
  보고서의 EBITDA 를 복원. 이중계상 방지 가드(`depreciation IS NULL` 타겟팅)와 매출 앵커
  단위보정도 이미 있다.
- ⟹ **정책 자체는 "주석은 주석"이 맞다. 문제는 그 경계가 새는 구멍이다.**

### 1-2a. ★★ 정정(2026-07-17 저녁) — 원인은 하나가 아니다 (사용자 원문 대조로 발각)

**사용자가 3S 원문을 직접 확인해 제보 → 초기 진단("전부 주석 누수")이 틀렸음이 드러났다.**
불가값 307행의 원인은 **최소 2가지**로 갈린다:

| 유형 | 대표 사례 | source_ref | 재추출로 고쳐지나 |
|---|---|---|---|
| **A. 주석표 누수** | DB손해보험 2023 H1 | `BS_S/5. 이익잉여금,39>` | ✅ 예 (1-3 메커니즘) |
| **B. 원문 단위 오기** | 3S 2023 Q3 | `BS_C/자산총계` (**정상 본문 라인**) | ❌ **아니오 — garbage-in** |

**유형 B 상세(3S, corp 00378363, rcept 20230209000202)**: 같은 보고서 안에서 **동일한 값
`72,650,807,169` 이 두 표에 나오는데 단위 표기가 다르다.**
- `1. 요약재무정보 > 가. 요약연결재무정보` → **`(단위 : 원)`** → 726억 ✅ 정답
- `2. 연결재무제표 > 연결 재무상태표`(본문) → **`(단위 : 백만원)`** → ×10⁶ → 72,650조 ❌

즉 **3S 가 본문 재무상태표 표제에 단위를 잘못 기재**했고(실제 값은 원 단위), 우리 추출기는
표기를 그대로 신뢰해 `adecimal=-6` 을 적용했다. 추출기는 **본문 라인을 정확히 잡았다**
(주석 누수 아님). **원문이 틀렸으므로 재추출만으로는 절대 고쳐지지 않는다.**

⟹ **대응이 유형별로 다르다**:
- A → 섹션 기반 추출(1-9)로 구조적 차단
- B → **교차검증 필요**: 같은 문서의 `요약재무정보`(단위가 옳게 적힌 경우가 많음) 또는
  인접 기간과 대조해 단위 이상을 탐지. **같은 문서 안에 정답이 있었다**는 점이 핵심.
  (탐지는 가능, 자동교정은 신중히 — 어느 쪽 표기가 옳은지 판정 규칙 필요.)

⚠ 이 정정에 따라 Phase 1 어서션의 `desc` 문구("주석표 단위 오염이 소비계층 노출")도
**부정확**하다 — 커밋 전 수정 필요.

### 1-2. ★ 근본 원인 ① — 1차 앵커의 사각지대 (정규식 격리로 정확히 규명)
`statement_titles.py::_FACE_TITLE_START` 는 접두사로 `(?:연결|별도|개별)?` 만 허용하고
**`반기`/`분기` 를 빠뜨렸다.** 또 재무제표명 **내부 공백**(`반 기 재 무 상 태 표`)도 처리
못 한다. 실측:

| 표제 | 판정 |
|---|---|
| `재무상태표 제 57(당)기 반기말 2023년 6월 30일 현재` | ✅ 통과 |
| `연결재무상태표 제 57(당)기 …` | ✅ 통과 |
| **`반기재무상태표 제 57(당)기 …`** | ❌ **거부** |

### 1-3. ★ 오염 메커니즘 (DB손해보험 실사례 · 원문 대조 완료)
- 대상: DB손해보험(005830, corp 00159102) **2023 반기보고서** rcept `20230927000457`
- 이 보고서의 본문 표제는 전부 `반 기 재 무 상 태 표 … DB손해보험주식회사 (단위 : 원)`(표109),
  `반 기 연 결 재 무 상 태 표 …`(표1) 형태 → **1차 앵커가 6개 섹션을 전부 거부(0개 검출)**
- ⟹ BS/IS/CF × 연결/별도 **6섹션 전부가 폴백**(`detect_sections`+`find_section_tables`, 앵커
  없음)으로 떨어짐
- ⟹ 폴백이 BS_S 로 **빈 표제의 주석표**(백만원 단위)를 집음
- ⟹ `fact_v2.source_ref='BS_S/5. 이익잉여금,39>'`, `amount_won=8,564,682,463,043,000,000`
  (**8.5경원** = 정답 8.56조 × 10⁶)

**즉 인과는 "폴백이 나쁘다"가 아니라 "1차 앵커가 정상 서식을 거부해서 폴백으로 밀려나고,
앵커 없는 폴백이 주석표를 집는다"이다.** 폴백은 증상, 앵커 사각지대가 원인.

### 1-5. ★ 왜 기존 방어선이 전부 뚫렸나
- **DQ 게이트**: 항등식 `자산=부채+자본` 을 보는데, 주석 오염이 양쪽을 **균일하게 ×10⁶**
  부풀리면 **항등식은 그대로 성립** → DQ=1(정상) 판정.
- **dq_assertions.py**: `shares_out_impossible`·`market_cap_impossible` 은 있으나
  **재무제표 본체 금액의 크기(magnitude) 어서션이 없다.** → 293행이 조용히 통과.
- **Gate B(보고서↔DB 대조)**: 오염된 표의 값도 "보고서 안에 실재하는 숫자"라 일치 판정될 수
  있다(어느 표에서 왔는지를 안 보므로).

### 1-6. ★ 현재 구조로는 오염 규모를 측정할 수 없다 (재추출이 필요한 핵심 이유)
- **fact_v2 에 출처(provenance) 컬럼이 없다.** `source_ref` 는 `'BS_S/5. 이익잉여금,39>'`
  처럼 **섹션코드+라벨**만 담고, "본문 face 표인가 주석표인가", "1차 경로인가 폴백인가"를
  **기록하지 않는다.**
- 지문(fingerprint) 추정은 **무용**: 주석참조번호 패턴(`,39>`) 보유 기업 39개 vs 불가값
  기업 53개, **교집합 단 1개**(DB손해보험). 즉 불가값 기업 53개 중 52개는 이 지문이 없다.
- 표 단위 지문 분류도 **양방향 부정확**(아래 1-7의 C 분류 참고).
- ⟹ **"명확하게 구분"하려면 출처를 스키마에 기록해야 하고, 그건 재추출을 요구한다.**

### 1-9. ★★★ 사용자 제안 검증 — DART 섹션 구조가 정답 (400건 실측)

사용자 제안: *"요약재무정보는 제외하고 연결재무제표 부분과 재무제표 부분만 연결·별도 재무제표
본문으로 사용하면 될 텐데."* → **실측 결과 사실상 보편적이며, 표제 정규식 땜질보다 압도적으로
우월하다.**

DART 문서는 `<SECTION-2><TITLE>` 로 이미 완벽히 구획돼 있다(3S rcept 20230209000202 실측):

**보편성(400건 무작위, Track B, fy≥2015)**:

| 항목 | 결과 |
|---|---|
| 5개 섹션 전부 보유 | **399/400 (99.8%)** |
| 본문 섹션(연결재무제표+재무제표) 둘 다 보유 | **399/400 (99.8%)** |
| 본문 섹션 없음 | **1건** (리메드 20240516001212 = **감사보고서**, `주석`+감사 섹션만 있는 별개 서식) |

**⟹ 전체 표의 96%가 주석 섹션에 있다.** 현행 추출기는 156,060개 표를 전부 후보로 놓고
표제 정규식으로 149,831개를 걸러내려 시도한다 — 그러다 뚫린 것이 DB손해보험 사례다.
**섹션으로 자르면 후보가 6,229개로 25배 줄고, 주석표는 본문 후보에 진입조차 못 한다.**
`반기`/`분기` 접두·내부 공백(1-2) 같은 표제 사각지대를 **개별 방어할 필요 자체가 사라진다.**

또한 `fin2/extract/text.py::_extract_summary` 는 **요약재무정보를 실제로 파싱**하며(본문 섹션을
하나도 못 찾았을 때 발동), 그 팩트를 **본문과 동일한 `fs_type`/`source_ref` 형식**
(`BS_C/자산총계`)으로 저장한다 → **사후 구분 불가**(provenance 부재의 또 다른 근거).

## 2. 목표 — ★ 사용자 확정 결정 (2026-07-17)

> **불변식(invariant): 주석표는 절대 `bs.`/`is.`/`cf.` 팩트를 생산하지 않는다.
> 주석표는 오직 `note.*` 만 생산한다. 그리고 이 불변식은 추정이 아니라 스키마로 강제·검증
> 가능해야 한다.**

### 2-1. 확정 결정 ①: 섹션 기반 4분할 적재
DART `<SECTION-2>` 경계로 **4개를 명확히 구분해 적재**한다:

| 섹션 | 적재 대상 | basis |
|---|---|---|
| `2. 연결재무제표` | `bs.` / `is.` / `cf.` (본문) | consolidated |
| `4. 재무제표` | `bs.` / `is.` / `cf.` (본문) | separate |
| `3. 연결재무제표 주석` | **`note.*` 전용** | consolidated |
| `5. 재무제표 주석` | **`note.*` 전용** | separate |

- `1. 요약재무정보` → **본문으로 사용하지 않는다**(적재 제외).
- 주석 수집은 유지하되(사용자: "주석의 내용도 같이") **네임스페이스로 완전 격리**.

### 2-2. 확정 결정 ②: 본문 없는 기업·기간은 제외 + 별도 리스트
- **요약재무정보만 있고 본문 섹션이 없는 보고서 → 그 기업·기간을 적재에서 제외**한다.
  (현행 `_extract_summary` 폴백 = 요약을 본문으로 둔갑시키는 경로 → **폐지**.)

- ⚠ **★ 판정 단위 주의(2026-07-17 리메드 사례로 발견)**: 제외 판정은 **보고서 단위가 아니라
  (기업, 기간) 단위**로, **모든 후보 보고서를 본 뒤** 내려야 한다.
  리메드(01275665) FY2023 은 보고서가 3개다 — 원본 `20240320001869` + **[첨부정정]** 2개
  (`20240327001062`, `20240516001212`). **첨부정정본은 첨부(감사보고서)만 담고 있어 본문
  `III. 재무에 관한 사항` 구조가 없다**(주석 240표 + 감사 섹션만). 400건 표본에서 "본문 섹션
  없음 1건"으로 잡힌 것이 바로 이것 = **결함이 아니라 첨부정정 서식의 정상 특성**.
  실제 std_v2 는 온전하다: **연결은 첨부정정본(20240516001212)에서, 별도는 원본
  (20240320001869)에서** 각각 이겼다(자산 551/544억·매출 185/180억·DQ=1) — `reconcile` 이
  BS/IS/CF × 연결/별도를 **독립 승자 선택**하는 설계가 정확히 작동한 것.
  ⟹ 어떤 보고서에 본문이 없다는 이유만으로 그 기업·기간을 제외하면 **정상 데이터를 파괴**한다.
- 제외된 (기업, 기간)은 **별도 리스트로 남긴다** — 데이터가 조용히 사라지지 않도록 가시화.
- **이 리스트의 처리 방침은 나중에 다시 논의**(사용자 지시: "별도 list 기업 기간 처리를 다시
  고민하자"). 후보: 요약값을 별도 저장소/플래그로 보존 · DART API 보완 · 영구 결측 인정 등.
- ⚠ **규모 미측정**: 400건 표본에선 본문 섹션 없음 1건(0.25%, 그마저 감사보고서 서식)이었으나,
  "섹션은 있으나 본문 표가 비어있는" 경우는 별도 집계 필요 → **실행 전 전수 측정 필요**.

### Phase 1 — 출혈 차단 (저비용·독립·선행 가능) ⭐

### Phase 2 — ★ 근본 재설계: 섹션 기반 추출 (사용자 확정 방향)

**표제 정규식을 땜질하는 대신, DART `<SECTION-2>` 경계로 추출 범위 자체를 자른다**(1-9·2-1).

- `2. 연결재무제표` / `4. 재무제표` **섹션 내부의 표만** 본문 face 후보로 삼는다.
  → 주석표 149,831개(전체 96%)가 **후보 진입 자체 불가**. `반기`/`분기` 접두·내부공백 등
  표제 사각지대(1-2)를 개별 방어할 필요가 사라진다(표제는 섹션 **내부**에서 BS/IS/CF 를
  구분하는 용도로만 축소 사용).
- `3. 연결재무제표 주석` / `5. 재무제표 주석` 섹션 → **`note.*` 전용 경로**로 분리.

  - 3S 20230209000202 → 본문 라인은 정상 추출되나 **단위 오기(유형 B)는 여전히 남음**을 확인
    (Phase 3 대상)

### Phase 3 — 단위 오기(유형 B) 탐지 — ★ 신설 (1-2a 정정 반영)

**섹션 기반으로도 안 잡히는 유형**: 원문이 단위를 잘못 기재한 경우(3S = 본문 표제
`(단위 : 백만원)` + 원 단위 값). 재추출로 고쳐지지 않는 garbage-in.

- **교차검증 신호**(같은 문서 안에 정답이 있음):
  - `1. 요약재무정보` 의 동일 계정값과 대조(3S 는 요약이 `(단위 : 원)` 으로 **정확**했다)
